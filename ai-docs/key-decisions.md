# Key decisions

Decisions with the reasoning that produced them, so a later reader does not re-litigate a settled trade-off. Game-design decisions live in [`docs/DESIGN.md`](../docs/DESIGN.md) and are **not** duplicated here; this page carries the engineering and repository decisions, each pointing at its source.

Format: **KD-N — decision** · *why* · *consequence* · *source*.

## Stack

**KD-1 — Go.** Compilation and static types, a cheap instance (native binary), concurrency and networking in the standard library. Rust with `teloxide` was evaluated and rejected: incomplete Bot API surface plus framework opinionation. *Consequence:* the harness gates are `go build` / `go test -race` / `golangci-lint`. *Source:* `docs/DESIGN.md` §11.

**KD-2 — `telego` (mymmrac/telego), low-level layer only, pinned at `v1.11.2`.** Types and methods are generated one-to-one from the official documentation, so coverage is complete by construction. The helper layer is not used; a thin project-owned layer (`internal/tg`) adds retries with a never-retry-on-doubt classifier, rate limiting, an outbound gate, one typed error and one observation point. *Fallback if it disappoints:* `go-telegram/bot`. **Never** `go-telegram-bot-api` (frozen). *The pin, and what it is not:* `v1.11.2` declares `go 1.25.7`, while `v1.12.0` and `v1.12.1` declare `go 1.26.7` and the go command therefore refuses them *before* compiling — the installed toolchain is `go1.26.5` and `GOTOOLCHAIN` is `local`, here and in CI. **That is a configuration ceiling, not an incompatibility, and a later reader must not record `v1.12.x` as technically unusable:** its code builds clean under `go1.26.5` once its own directive is lowered, and `GOTOOLCHAIN=auto` dissolves the block outright by fetching a newer toolchain. Adopting `v1.12.x` also raises *this* module's `go` directive to `1.26.7`, which every local build and every CI runner would then have to satisfy — so raising the toolchain and moving to `v1.12.x` is **deferred to its own task** by the owner's decision rather than folded into the transport task. *The swap is half a runtime option and half a build tag, and only the runtime half is taken here.* §11's "replace `fasthttp`/`go-json` with `net/http` and `encoding/json`" resolves against `v1.11.2` into two different levers. **Taken:** `telego.WithAPICaller` installs this project's `net/http` caller, which also decodes the response envelope, and `telego.WithRequestConstructor` installs its `encoding/json` request marshaller — so every byte this project marshals or unmarshals itself goes through the standard library. **Not taken:** telego decodes the already-extracted `result` payload into its own generated types through a vendored reimplementation of `encoding/json`'s API, selected by the `stdjson` **build tag** rather than by an option. The tag works and removes `grbit/go-json` from the build graph, but adopting it changes what every `go` gate command *is*, and the Propagation Rule routes that to `AGENTS.md` § Build & Test, every skill's `allowed-tools` line and the `/task` gate checklist — a sweep found the bare gate commands spelled out across most of `.claude/**` and several `ai-docs/**` pages. **The owner's decision is a separate focused PR whose whole content is that propagation:** the residue is a recorded deferral, not an oversight, and half-threading the tag would leave a silently divergent second build configuration. `fasthttp` and `fastjson` remain in the module graph either way, tag or no tag; what a guard test asserts is that no file under `cmd/` or `internal/` imports them. *Consequences:* `internal/tg` is the only package that may name `telego.NewBot` or a `telego.With*` option, and a guard test enforces it — `telego.BotOption` is an exported function type, so any holder of the bot pointer could otherwise install its own caller and bypass the gate, the limiter and the observation; this module is the entire population of such code (no downstream importers, `AGENTS.md` § API Stability), which is what makes the guard a complete cover rather than a sample. Resolving the pin upgraded `github.com/stretchr/testify` to `v1.12.1`, indirect. *Source:* §11; the pin, the swap and the `stdjson` deferral from the Bot API transport design D1/D3, issue #19. *Decided:* 2026-09-04.

**KD-3 — Postgres + `pgx` + `goose` (`github.com/pressly/goose/v3`).** One database holds the ledger, the world, sessions, the event log and the scheduler queue — which is what makes a self-check like "opening + turnover == closing" meaningful at all. §11 named two migration tools (golang-migrate or goose); the owner chose goose: one SQL file per migration, embedded via `fs.FS`, applied by `store.Migrate` through `stdlib.OpenDBFromPool`. **Forward-only:** no `-- +goose Down` section anywhere — rolling a ledger table back is data loss, so a mistake is corrected by the next forward migration. *Source:* §11; goose and the no-`Down` policy decided 2026-09-02.

**KD-4 — A self-written scheduler on Postgres, not a job framework.** `scheduled_task` plus a worker on `SELECT … WHERE run_at <= now() FOR NO KEY UPDATE SKIP LOCKED`, each task executing in one transaction with its effects. ~100 lines, canonical pattern, horizontally scalable by adding a worker. `gocron` rejected (in-memory; one-shot tasks must survive restarts), Temporal rejected (overkill). *Escape hatch if it grows features:* River. *Source:* §11.

**KD-5 — Double-entry ledger with a global World account.** Append-only postings, zero-sum per kind enforced at write time, balances materialised only for controlled accounts, daily close for point-in-time balances. Pure event sourcing was rejected (a tax on every read); materialising a balance for *every* account was rejected (a hot row on World would be a global mutex on the economy). *Source:* §11, [`domain-invariants.md`](domain-invariants.md).

**KD-6 — A second machine for items with identity.** Instance-carrying items are never ledger kinds; ownership is a chain of movements. *Source:* §11.

**KD-7 — Lazy ticks instead of cron.** State is computed from timestamps at read time, so the bot is a stateless update handler over Postgres and restarts are trivial. The single true cron is the daily ledger close; the standing timer is the designed exception and rides the scheduler. *Amended by #24 — "restarts are trivial" is now true by construction on the scheduler side too, and it took one explicit step to keep it so:* lazy ticks make *state* restart-proof, but a persisted timer is not state computed at read time — every edge that came due during an outage is still sitting in `scheduled_task` when the process returns, and firing them all at once is the opposite of a trivial restart. The composition root's restart-hygiene step absorbs that: it measures the gap against a persisted liveness instant and, past a configured threshold, moves every overdue pending row forward by that gap. *Source:* §11. *Amended:* 2026-09-10.

**KD-8 — Raid session as an explicit FSM row.** No goroutines or in-memory timers; a restart is invisible to sessions; every transition is a basis document, so the transition log is a ready-made raid trace. *Amended by #24 — what "invisible" now means exactly:* a restart still costs a session nothing, because no edge is lost and no in-memory timer had to survive; what a *long* restart does move is the wall-clock instant an overdue edge arrives, since the restart-hygiene step shifts every overdue pending row forward by the measured downtime rather than firing the backlog in one salvo. A session is therefore invisible-to-restarts in the sense the row model buys — its transitions and its guard are untouched — and a mechanic must never assert that an edge fired at the instant it was scheduled for. *Source:* §3.5. *Amended:* 2026-09-10.

## Infrastructure

**KD-9 — Self-hosted `telegram-bot-api` from day one.** Motivation is a lived incident: the shared `api.telegram.org` frontend can wedge a specific bot for hours with no 429 and no error, and reissuing the token does not help because the state hangs on the bot id. A local instance talks MTProto to the DC directly and exposes `/stats`. It does **not** relax message rate limits — those are enforced by Telegram's core. *Source:* §12.2.

**KD-10 — Long polling, not webhooks.** Only outbound traffic is needed: no public IP, no domain, no TLS — so the whole thing can live on a home machine until a Mini App (radar) forces a public HTTPS endpoint. *Source:* §12.1.

**KD-11 — The test bot runs against cloud `api.telegram.org` while production runs on our instance.** Two independent paths to Telegram: "test bot works, production hangs" localises an incident instantly. Isolation is by configuration, never by code — same image, different env. *Source:* §12.5.

**KD-12 — A restore into testing is always sanitised.** Chat/user ids rewritten, outbound queue drained, updates offset reset — otherwise the test bot messages real people on the first tick. The same script doubles as the backup-restorability check, so that duty stops being a separate task. *Concrete as of #22:* the offset clause now names `ingest_offset`'s singleton row, the id clause reaches `ingest_dead_update.chat_id`, and there is a **fourth** obligation this three-clause summary does not cover — blank `ingest_dead_update.last_error`, whose free error prose can embed a real chat or user id that a column-targeted rewrite walks straight past ([`domain-invariants.md`](domain-invariants.md) § 6). *Source:* §12.3, §12.5.

## Repository and harness

**KD-13 — Module path `github.com/maratik123/lab-game`.** The repository is named for the project directory, not for the game's future name (which is an open question, §16.6), so finding the name later costs no import rewrite. *Decided:* 2026-08-29.

**KD-14 — Private repository, no server-side protection.** GitHub refuses branch protection and rulesets on a private repository on the free plan (`403: Upgrade to GitHub Pro or make this repository public`). The design document's economy and anti-abuse rules are not published while the repository is private. *Consequence:* `main` is protected only by the local commit hook and honour-system rules — see `AGENTS.md` § Permissions. Revisit when the repository goes public or the plan changes. *Decided:* 2026-08-29.

**KD-15 — The harness is ported from `graphite-gp` (itself evolved from `quartzite`), not reinvented.** What travels is the process — spec-driven `/task` flow, the learning loop, the propagation rule, the review agents. What is rewritten is every language-bound surface (gates, style, test and doc conventions, hooks) plus new domain rules for the ledger, telemetry and Telegram safety. Citations inherited from those projects are namespaced (`graphite-gp`'s log, `maratik123/quartzite#N`) rather than left as bare `#N`, which would resolve against *this* repository and lie. *Decided:* 2026-08-29.

**KD-16 — Strict `golangci-lint` from the first commit.** Enabled beyond the default set: `exhaustive` (an FSM switch must be total), `rowserrcheck` / `sqlclosecheck` (database correctness), `errorlint`, `nilerr`, `bodyclose`, `noctx`, `gosec`, `revive` with exported-doc rules; and, from the goroutine-ownership pass (#80), `containedctx` (a context stored in a struct field), `fatcontext` (a context nested in a loop or a function literal), `forbidigo` (`context.Background`, `context.TODO`, `time.Tick` and `time.After`, outside `main` packages and tests), `gocritic`'s `deferInLoop` and `govet`'s `nilness`. A finding is fixed, not silenced; `nolintlint` requires a specific linter and a stated reason on any exception. *The settings that keep the gate reporting are pinned with it:* `run.relative-path-mode: gomod`, without which an exclusion rule's `^cmd/` anchor stops meaning the module root; both issue-truncation caps at `0`, without which the gate stops reporting a class after its first few findings; and `issues.uniq-by-line: false`, without which it keeps only one finding per source line across linters — and "every site is handled" stops being a measurable claim under any of them. *Consequence:* an exclusion rule carries a `linters` list or it switches every linter off for its path, and a guard in `internal/gateguard` reads `.golangci.yml` and fails when the enabled set, the exclusion scoping or any pinned setting drifts; the enumeration with a reason per linter lives in [`code-style.md`](code-style.md) § *Linter posture*. *Decided:* 2026-08-29; extended 2026-09-12.

## Ledger core (2026-09-02)

**KD-17 — Account model: owner → scope → account, with two catalogs.** An `owner` has a kind from the open enum `owner_kind` (`world` — exactly one row; `player` and `chat` — identified by `telegram_id`, partial unique on `(kind, telegram_id)`); a `scope` belongs to an owner and points at a `scope_definition`; an `account` belongs to a scope and points at an `account_definition`, which carries the account's `ledger_kind` and its `controlled` flag. Kind therefore lives on the account definition, never on a posting. Scopes and accounts are singletons per `(owner, definition)`. *Why:* an open list of owner kinds and scopes (attributes, backpack, inventory, storage, constructions …) that grows by seeding a catalog row, without a per-kind column on `owner`. *Consequences:* singular table names and identity columns throughout; every referencing-side FK is covered by an index (a migration test enforces it); the transaction entity is `journal_entry`, 1:1 with its basis document (`player_operation` or `manual_correction`, exclusive arc) and the only holder of the timestamp; every controlled account gets its `account_balance` row at owner creation, so `Post` moves a balance with a plain `UPDATE` (an upsert would evaluate `CHECK (balance >= 0)` on the proposed row and refuse a covered debit) and a zero-row `UPDATE` is a broken invariant, never an overdraft; append-only is enforced in code only — the owner declined a database trigger. No composite FKs and no move-control: such moves are not planned by design, and the owner judged the declarative guard illusory. *Amended by #25 — «No composite FKs and no move-control» is scoped to the account model's own tables, not to the schema as a whole, and the owner ruled that scoping explicitly when the item machine's design raised it:* an account never moves, so a declarative guard against moving one guards nothing — but an item instance moves as its whole purpose, and there the guard is the mechanic. `item_movement` therefore carries a self-referential composite foreign key from `(prev_movement_id, item_id, from_holder_id)` to a predecessor's `(id, item_id, to_holder_id)`, alongside a `NULLS NOT DISTINCT` successor index, so "every movement's `from` equals its predecessor's `to`, and an instance sits at exactly one holder" is a database refusal rather than a convention. The same change gives `account_definition` a nullable `capacity_role` (`free` / `used`), which is what lets a capacity kind resolve to one account pair per holder without a branch on holder kind. *Amended:* 2026-09-12. *Source:* the ledger-core spec (`ai-docs/plans/2026-09-02-ledger-post-core.spec.md`), owner's redesign, 2026-09-02.

**KD-18 — Amounts are `numeric(30,5)`, and Go handles them as `shopspring/decimal`.** `posting.amount` and `account_balance.balance` are `numeric(30,5)`: balance tuning may produce fractions, and thirty digits is a reasonable ceiling. The Go side is `github.com/shopspring/decimal` with `github.com/jackc/pgx-shopspring-decimal` as the pgx codec — amounts will be operated on in game mechanics, so a decimal library beats integer minor units. *Consequence:* the codec is registered once per connection in `store.NewPool`'s `AfterConnect` (registering per call prepends to the type map every time); no `float32`/`float64` appears on the ledger path. *Decided:* 2026-09-02.

**KD-19 — Container images are pinned to the major tag.** `docker.io/library/postgres:18`, never `postgres:18.6` — the owner's standing preference for every container image, not only Postgres. *Why:* a patch tag pins what the image store already resolves to the same id, and it goes stale on every upstream release. *Decided:* 2026-09-02.

**KD-20 — Tests provision Postgres through testcontainers-go, and never skip.** `internal/testdb` starts a `postgres:18` container by default; `LAB_GAME_TEST_DSN` points the suite at an existing server instead (CI, or a developer with a server running). With neither, `testdb.Main` exits non-zero — "a job that did not run is not a passing job". Every test gets its own schema (`testdb.Schema`), so tests are order-independent and run in parallel against one server. The local development instance is not used by any committed file — the owner retired it for this purpose. *Consequence:* the container runtime never enters `cmd/bot`'s import graph — `go list -deps ./cmd/bot` must stay free of `testcontainers`, and since #24 that is a **gate**, not a documented hope: `make import-guard` (`cmd/importguard`) runs `go list -deps` over a rule table and fails on a forbidden module prefix, in `verify` and in CI's Build job. `depguard` was considered and rejected — it decides a file's own package imports, so a future `internal/` package that imported the runtime and was itself imported by the bot would pass it, which is a weaker proposition than the transitive one this invariant states. **That is the invariant, and it is not the same proposition as "only `_test.go` files import `internal/testdb`"**, which the amendment below stopped being true; a reader who carries the second one forward will read a legitimate importer as a violation. *Decided:* 2026-09-02. *Amended by #67 (design D2, D3, D3a):* **one server now serves the whole suite, and the per-binary path becomes the fallback rather than the default.** `cmd/testpg` wraps a gate command and exports the DSN into it, in a fixed decision order: a `LAB_GAME_TEST_DSN` already set by the caller is used exactly as it stands (a capacity shortfall is *reported* and the run proceeds — the contract is that the gates execute against the server the caller named); otherwise a long-lived server recorded by `make test-db-up` is used, but only if it answers *and* admits this run's computed need, falling through with a message when either check fails; otherwise the wrapper starts an **anonymous** container sized for the run and removes it on every exit path, an interrupt included — anonymous because only a server this invocation started may be removed, so two concurrent runs can never pull one out from under each other. `make test`, `make test-race` and the coverage ratchet all route through it, so a whole-module run starts **one** container instead of one per database-backed test binary; `make test-db-up` / `make test-db-down` keep a named long-lived server across runs, under a name derived from the checkout itself — the base name of the project directory the wrapper runs in plus `-test-postgres`, so a checkout at `~/lab-game` addresses `lab-game-test-postgres` and one at `~/lab-game2` addresses `lab-game2-test-postgres` — addressed by a DSN file under the ignored scratch directory; and `make test-fallback` — a bare whole-module run with the variable explicitly cleared, run as its own CI step — is what keeps the per-binary path executed now that no default gate reaches it. *The connection arithmetic of the shared configuration,* because one server must admit every client at once and a literal sized for one host is wrong on the next: `testdb.Ceiling(clients, parallel)` returns `clients × Binaries × parallel × (schemaMaxConns + 1) + ceilingSlack`, and that number is the `max_connections` the container is started with. `clients` is how many whole-module runs share the server **at the same time, all at the same `parallel`** — the product form is correct only under that condition — and defaults to 1, `make test-contention` being the one target that passes 2. `Binaries` is how many test binaries provision a database through `testdb.Main` (**5** today), bounded above by `go test -p`'s own default, and a manifest test re-derives it from the tree so a fifth database-backed package fails by name instead of by exhaustion. `parallel` is how many tests run at once inside one binary, defaulting to `runtime.GOMAXPROCS(0)`; a target that pins its child's `-parallel` passes the same value to the wrapper, or the product funds neither client. `schemaMaxConns + 1` is the per-test pool cap `testdb.Schema` sets (**4**) plus one slot for the transient admin and dropper pools it opens around each schema. `ceilingSlack` is **32**: the server's own reserved slots (3 on this image) plus the one test that raises its pool cap above the per-test cap. The result is floored at the image's own default of **100** — computing less would only give back capacity the server already offers — while **the top is not a clamp**: above `ceilingMax`, **1000** and measured rather than guessed, the wrapper refuses to provision at all, printing the computed value, the terms it came from and the flags that lower it, because silently granting less than the formula asks for is how a host quietly runs a population its server cannot admit. Two residues are stated rather than closed: `max_connections` is the server's *total*, not its free capacity, so a server that is large enough but already busy with another run passes the check and can still exhaust — the answer is to size it (`make test-db-up CLIENTS=2`), not a point-in-time free-slot count that would be racy and would make one gate's start depend on another gate's phase; and the fallback path keeps the image default, where one server serves one binary and the per-pool cap's own arithmetic still holds. *Amended by #24:* the composition root's own smoke condition made `cmd/bot` a database-backed test binary, so `Binaries` moved from 4 to 5 in the same commit that added the caller — the manifest test that re-derives it from the tree is what forces that pairing. *Amended by #91 (design D1, D3, D5, D6):* **the long-lived server's name is derived per checkout instead of being one fixed name for the host.** `cmd/testpg` takes the base name of its own working directory — the repository root every caller already invokes it from — and appends the fixed `-test-postgres` suffix, on `--up` and `--down` alike; `testdb.SharedContainerName` is deleted, so the wrapper is the only thing in this module that names a container. Two checkouts on one host therefore each own a server, and a `--down` in one leaves the other's running. The parent path contributes nothing, so two checkouts whose project directories carry the same name deliberately address one server — the owner's decision, not a residue. A base name the container runtime would refuse is never sanitised, because sanitising would map distinct checkouts onto one name and re-create the contention this removes; it fails instead before the reaper is touched or anything is provisioned, with a message naming the directory and the rule, which the runtime's own refusal does not carry. The anonymous fallback container stays anonymous: it is already per-invocation, so a name would buy no isolation and would cost the property that only a server this invocation started may be removed. *Amended by #110:* **the same `clients` input now sizes the PGDATA mount, not only the connection ceiling.** PGDATA and its WAL share one fixed-size tmpfs whose cap was a compile-time constant measured for a single client, while `Ceiling` scaled connections by `clients × parallel` — so the one target that passes `--clients 2` put two clients' schemas on a mount sized for one and exhausted it, and `make test-contention` had no working path at all: it died as an instrument failure (`No space left on device`, SQLSTATE 53100) before it could report anything about contention either way. `testdb.MountOptions(clients)` now returns the mount options the container is started with, granting `perClientMountMB` per client — **512**, the value a single client was always granted, kept byte-for-byte so the one-client default is unchanged — and a count below one sizes for one, so a zero `ServerOptions` stays usable. `walRetentionMB` is deliberately **unchanged at 64**: the mount grows per client while the retention target holds, which only widens the headroom the two numbers share, so they remain one decision rather than two. *What keeps the pair honest* is a budget assertion carrying a `clients` term, reading the literal counts out of the build file so raising `--clients` anywhere without sizing the mount fails by name instead of as disk exhaustion at run time; its per-client figure is a measured **peak under sustained load**, not the cluster residue the earlier assertion used, because the residue is 0.60 of the peak (193 MB against 320 MB per client) and would green-light a mount the run still overruns — a guard passing for the wrong reason. *One residue, masked rather than closed:* a container reused under its name keeps the ceiling **and** the mount it was created with, so resizing either needs a down-and-up; `runUp` catches that today by reading the running server's capacity back and refusing, but it catches a short *mount* only **above the ceiling's floor**: `Ceiling` is floored at `imageDefaultCeiling`, so it is non-decreasing in `clients` but not strictly increasing, and at a small enough `parallel` several client counts compute the identical floored ceiling while the mount keeps growing — measured against the shipped functions, `parallel=1` gives ceiling 100 for both one and two clients while the mount goes from 512 MB to 1024 MB, so `actual < ceiling` passes a server whose mount is half the request. Above the floor a larger client count always computes a larger ceiling and the capacity check does catch a short mount along with it. Nothing checks the mount itself, and that gap is known and unmeasured rather than closed. *And the mount scales with `clients` only, never with `parallel`*, though peak disk also depends on how many schemas exist at once; that is the chosen direction, not an oversight. *Source:* the shared-test-server design D2/D3/D3a, issue #67; the per-checkout name from the container-name design D1/D3/D5/D6, issue #91; the per-client mount sizing from issue #110. *Amended:* 2026-09-13.

## Configuration layer (2026-09-04)

**KD-22 — YAML parser: `go.yaml.in/yaml/v3`, a direct production requirement.** The balance-set format is YAML by owner instruction, and the loader needs the parser's *node tree* (`Kind`, `Tag`, `Value`, `Content`, `Line`) rather than a struct binder: no balance number may have a compiled-in fallback, and any binder that decodes straight into a Go value cannot separate "the key was absent" from "the operator wrote 0" — a YAML null decodes into `int`, `time.Duration` and `decimal.Decimal` with no error and a zero result. *Why this fork:* the incumbent `gopkg.in/yaml.v3` is archived upstream and has no release past `v3.0.1`; the YAML org's fork is the maintained continuation of the same API, with no non-stdlib requirements of its own. The fork's `retract [v3.0.0, v3.0.1]` directive is **not** a third argument — it retracts those version strings under the *new* module path and says nothing about the incumbent release. *Rejected:* `github.com/goccy/go-yaml` — maintained and dependency-free, but a different API and a far larger parser; it is the **escape hatch** if the fork ever stalls. `sigs.k8s.io/yaml` — strictly more modules to reach the same parser, and it routes YAML through `encoding/json`, discarding the tags and positions the key-path errors depend on. `knadh/koanf/v2` — its `mapstructure` binder lands on exactly the absent-vs-zero problem, and recovering the missing-key errors on top of it reproduces the schema table anyway; it is the **escape hatch** if the balance set ever needs layering or overlays, since its dotted key syntax is the one this schema already speaks. `spf13/viper` — package-level state plus `SetDefault`, i.e. a silent compiled-in fallback for every key. *Consequences:* the parser is imported from the balance-loading file alone, so a swap stays contained to one file; `gopkg.in/yaml.v3` **stays** in `go.mod` as a test-only indirect requirement through testify and must not be tidied away as "now unused". *Source:* the config-layer design D2/D3, issue #18. *Decided:* 2026-09-04.

**KD-23 — The configuration sources are disjoint by domain; there is no override chain.** The process environment owns secrets, runtime settings and the file-system path of each file source; the balance YAML owns every game constant; the world set owns world content and is not decoded by the loader at all. No key may be set through a second source. *Why:* precedence is the expensive half of a configuration layer, and nothing here needs it — the owner settled the question before the design started. *Consequences:* no generic key-path override machinery and no environment-vs-file merge step; and `.env.example` is exactly the loader's own variable set — a test asserts set equality between that file's keys, `config.EnvKeys()` and the keys the loader actually consults, failing by name in both directions. A variable read by anything *other* than the loader — `LAB_GAME_TEST_DSN` (KD-20) is the standing example — is documented where it is consumed and does not go in `.env.example`; adding it there breaks that test on purpose. *Source:* the config-layer spec Key decisions (owner, rounds 1 and 4). *Decided:* 2026-09-04.

**KD-24 — Configuration is read once at start-up, and the balance set comes from an operator-supplied path, never a `go:embed` copy.** `cmd/bot` loads and validates everything before any other work and exits non-zero naming every rejected or missing key; nothing re-reads configuration while the process runs. *Why:* an embedded copy would be a second source of truth for the same numbers and a silent fallback whenever the file is absent — the defect the no-compiled-in-fallback rule exists to prevent. One path, one failure mode. *Consequences:* each file path is a **required** environment variable with no compiled-in default — the "default path" is the value `.env.example` documents, resolved against the process working directory — so a deployment ships the balance file and the world set alongside the binary; and an edited balance number takes effect no earlier than the next start-up ([`domain-invariants.md`](domain-invariants.md) § 8). Moving balance without a *deploy* is designed; moving it without a *restart* is not. *Amended by #24 — the sentence still holds, and now it has a position:* `config.Load` is **step 2** of the composition root's written start-up order, after the signal registration and before anything that touches the database, and no later step re-reads it. "Before any other work" is therefore checkable rather than aspirational, and "the next start-up" now names a concrete event — a drain to exit, then a fresh assemble ([`process-lifecycle.md`](process-lifecycle.md)). *Source:* the config-layer spec Key decisions (reload policy) and design D8. *Decided:* 2026-09-04. *Amended:* 2026-09-10.

## Bot API transport (2026-09-04)

**KD-25 — The outbound rate limiter is project-owned: one schedule per key, holding every window.** A *schedule* is the whole state for one limiter key — its set of window constraints `(count, per)` plus the emission instants it has already granted — and its invariant is that no half-open interval of length `per` ever contains more than `count` grants. A pacing rate and a quota cap are the same kind of constraint under that model, which is what lets one mechanism hold both: `1/1s` is `(1, 1s)`, `20/1m` is `(20, 60s)`, and a pacing key contributes both `(1, ceil(per/count))`, which fixes the *shape* — one emission per interval instead of a burst — and `(count, per)`, which states the bound itself. The acquisition rule is **decide the emission instant against every constraint first, commit to every constraint at that same instant, never commit before the answer is final and never partially undo**; the two schedule kinds differ only in their answer to "earliest admissible instant", the per-`(chat, class)` key being **ordered** (the candidate is raised to that key's own newest grant, so its emission order is its arrival order) and the class-global key **unordered** (a class ceiling carries no ordering obligation, and imposing one held a quiet chat behind a busy chat's backlog). *Why:* an earlier design composed separate limiter legs and produced four defects of one shape across three review rounds — a leg committing at an instant another leg then moved, so a bound held on reservations rather than on emissions. The rule above removes the shape instead of patching its instances, and the mechanism is checked by a postcondition asserted after every insertion plus a brute-force oracle, not by an argument in a design document. *Why not a package* — `AGENTS.md` § Dependency Versions requires this comparison and KD-4 is the model: the requirement is to **shape** (answer *when*, never drop), to honour a context deadline and report refusal as this project's own typed error, and to hold **more than one window on one key**; every maintained candidate read fails the first clause, the third, or both. *Rejected:* `golang.org/x/time/rate` — a token bucket of size `b` refilled at rate `r` admits `b + r·W` in a window of length `W`, so no `burst` value makes it mean "at most `c` per `per`", and using it for one window while owning another is exactly the composition this decision forbids; `throttled/throttled/v2` — **policing**, not shaping: `RateLimitCtx` answers *allowed?*, not *when*, and its `RateQuota` carries the same burst parameter; `ulule/limiter/v3` — policing again, its whole `*Limiter` surface being `Get`/`Peek`/`Reset`/`Increment`, each returning a `Reached` verdict; `go.uber.org/ratelimit` — a genuine shaping leaky bucket, but `Take() time.Time` takes **no context**, so a call parked behind it cannot be cancelled; `github.com/sethvargo/go-limiter` — policing, `Take` returning an `ok` flag documented "If `ok` is false … the caller should NOT service the request". **No module is added for this**: `golang.org/x/time` is not a dependency of this project. *Escape hatch, in KD-4's spirit:* if a maintained package appears that shapes to a deadline with a context and expresses more than one window on a key, the schedule is one unexported type behind an internal call and is replaceable without touching the caller. *Two properties it deliberately does NOT provide, both reached the hard way.* **No grant reclamation:** a call cancelled after its instant is committed leaves that instant behind, because removing a grant for a call *outcome* is the shape that has already failed twice — once where the undo was not the inverse of the do, once where a refusal that removed its own instant shrank the window's memory. The only removal is ageing out, a function of the window set and the clock alone, which is what makes that defect structurally impossible rather than merely repaired; and the hole is safe in the one direction that matters, since a leftover grant can only push later grants *later*, so the limiter emits at or below its configured rate and never above it. It costs throughput under saturation, never flood safety, and it ages out after `per`. **No per-key locking:** one mutex covers the whole limiter, because per-key locks with a fixed acquisition order would restore the multi-component state commitment that produced every defect above; the critical section is a walk over a small window set and one insertion, which at MVP scale (one chat) and at fan-out scale (one bulk sender) is not a contention surface worth that risk. Contention is the thing to measure if it is ever revisited, and any replacement must keep decide-then-commit intact rather than merely shard the map. *Consequences:* retention is by **time**, never by count — a count bound is sound only on an append-only ordered schedule and would silently discard still-live grants on an unordered one — so the retained set is O(calls in flight); the registry holds one schedule per `(chat, class)` of a bounded class and does not evict, a known bound whose trigger to revisit is #43's fan-out, and whoever adds eviction must make it time-based, because dropping a key discards its grants and resets every window it was enforcing; an unbounded class (`off`) contributes no window, so it never blocks and allocates no history; and nothing persists — the state is in-process and touches no table, no disk and no migration, the durable queue staying #43's. *Source:* the Bot API transport design D9, after the owner's redirect away from composed legs; issue #19. *Decided:* 2026-09-04.

**KD-26 — Tests use `testing/synctest`; production code carries no clock abstraction.** The transport spec asked for an injectable clock *or an equivalent*, and the standard library ships the equivalent: inside a `synctest` bubble the whole `time` package is a fake clock, each bubble with its own. Production code therefore calls `time.Now` and `time.NewTimer` **directly** — no clock interface is threaded through the limiter or the caller — while the tests still get exact, instantaneous virtual time. *Why:* fewer moving parts in production *and* stronger assertions at once; and the limiter's whole contract is a statement about instants, so a test that cannot pin instants exactly cannot check it. Demonstrated on the exact stack the tests use rather than a nearby one — a real `*http.Transport` whose `DialContext` returns a `net.Pipe` connection with `DisableKeepAlives`, no listener and no socket — where a handler sleeping two virtual seconds completed in `0.00s` of wall time, clean under `-race`; the strategy turns on a pipe conn being durably blockable inside a bubble while a real listener is not, so a probe over a real socket would not have shown it. *Consequences:* the retry, `retry_after`, backoff, deadline and cancellation scenarios simulate hours and run in hundredths of a second; and three bubble rules bind the test code — `t.Run`, `t.Parallel` and `t.Deadline` must not be called inside a bubble, so a table-driven test puts `synctest.Test` **inside** each subtest and calls `t.Parallel()` outside it, which leaves this repo's table-test convention intact; a goroutine still blocked when the bubble's root returns is a hard failure, so the in-process fake Bot API server (`internal/tgtest`) disables keep-alives, closes its side of every pipe and registers its cleanup through `t.Cleanup`; and time advances only when every bubble goroutine is durably blocked, which is also the lever that makes arrival order deterministic, since releasing N concurrent callers one at a time with `synctest.Wait()` fixes the order in which they reach the limiter. *Source:* the Bot API transport design D14, issue #19. *Decided:* 2026-09-04.

**KD-27 — Operational tuning variables are an optional-with-default environment class, and its boundary is exact.** The fourteen `LAB_GAME_TG_*` transport variables — the retry attempt cap, the base and maximum backoff delay, the retry growth factor, the per-attempt timeout, and a global / per-chat-rate / per-chat-cap limit for each of the message, edit and other method classes — are **optional**: absent, each takes a default compiled into `internal/config`; present, each is parsed and validated like any other key, an invalid value producing a start-up `*KeyError` that names the variable. *Why:* these are operational tuning values an operator must be able to change without a code change. The message-class defaults are the figures Telegram publishes, verified upstream together with their modality — `30/1s` globally and `20/1m` into one chat are stated as enforced, `1/1s` into one chat is stated as advice — and the edit and other classes default to `off` because the same page states no figure for them: throttling on an unciteable number would delay gameplay against a limit Telegram may not impose, while a 429 is honoured exactly and is safe to retry. `docs/DESIGN.md` §11 carries the global and per-minute figures but not the per-second one, and the owner declined to edit §11, so that incompleteness is known and accepted rather than unnoticed. *The boundary, stated exactly:* the relaxation reaches **only** operational tuning keys — these fourteen, the seven `LAB_GAME_SCHEDULER_*` keys the Postgres task scheduler later added as the second member of this same class (issue #20), the seven `LAB_GAME_INGEST_*` keys update ingestion added as the third (issue #22), the four `LAB_GAME_HEALTH_*` keys the health surface added as the fourth (issue #23), and the four `LAB_GAME_PROCESS_*` keys the composition root added as the fifth (issue #24). Secrets, the base URL, the chat allowlist and the balance-file and world-set paths stay **required** with no default, and **no balance number gains a fallback** — KD-23 and KD-24 are untouched, because a rate limit is neither a file path nor a game constant. *Consequences:* the class is read by a dedicated `loadTransport` reader and is deliberately **not** added to the unexported `envKeys()` helper, which the required-variable suites iterate — an optional member there fails them immediately, and the tempting repair (loosening the assertion) would be a direct attack on the very requiredness those suites exist to hold; `EnvKeys()` appends the transport keys instead, so `.env.example` still lists exactly the loader's own variable set and the source-disjointness test still passes, each new line carrying its default as the value because one test requires every value to be non-empty and another requires the whole file to load. Every transport key is queried unconditionally on every load, so an absent optional key still appears in the recorded key set. And the two live sentences this class falsified — `internal/config/env.go`'s "every variable is required; none has a compiled-in default" and `Config`'s doc comment — were rewritten in the same change to name the variables they were written for alongside the new class. *Amended by #22's round-6 amendment:* each of the three scopes gained a retry growth factor key — `LAB_GAME_TG_RETRY_FACTOR`, `LAB_GAME_SCHEDULER_RETRY_FACTOR` and `LAB_GAME_INGEST_RETRY_FACTOR`, each declared last in its own scope's retry family and each defaulting to `backoff.DefaultFactor` — which is why the counts above read fourteen / seven / seven rather than thirteen / six / six. The key is per adopter rather than shared, because the three ramps measure different things and are already tuned apart: one shared key would move the scheduler's persisted retry cadence and the ingestion loop's head-of-line stall budget along with the transport wait an operator actually asked to soften. KD-31's amendment clause carries the ramp side of the same change. *Amended by #23, and the amendment names two keys rather than widening a clause:* the health surface's four `LAB_GAME_HEALTH_*` keys — the `/metrics` listen address, the canary interval, and the cloud reference leg's own bot token and base URL — join the class as its fourth member, and **two of them are named exceptions to the required-with-no-default sentence above**: `LAB_GAME_HEALTH_CANARY_CLOUD_TOKEN` is this project's first optional **secret** and `LAB_GAME_HEALTH_CANARY_CLOUD_BASE_URL` its first optional **base URL**. The reason the sentence does not reach them is that it was written about credentials the process cannot run without, whereas these two configure an optional *diagnostic leg* whose absence is a supported operating mode — an absent **or present-but-empty** cloud token loads without error, disables the cloud canary leg, builds no client for it and leaves the own-instance leg running; the empty spelling is admitted for this one key because an operator who writes the key with no value plainly means "off", and because it is the **only** way to switch the leg off for an operator who started from `.env.example`, where every value must be non-empty and deleting the line diverges from a manifest a test asserts. The bot token and the DSN stay required and gain no default, the instance base URL stays required and gains none, and the clause stands unchanged for every other secret and every other base URL — a future optional secret argues its own case rather than inheriting this one. **The generalisation was drafted and is refused:** an earlier version of this amendment rewrote the clause as "required unless the value's own absence is a designed operating mode", and loosening a rule nobody asked to loosen is unapproved scope exactly as tightening one is. *Amended by #24, and this amendment names its four keys too:* the composition root's own tuning joins the class as its fifth member — `LAB_GAME_PROCESS_MIGRATE_ON_START` (whether start-up applies pending migrations, default `true`), `LAB_GAME_PROCESS_SHUTDOWN_TIMEOUT` (the whole drain's bound, `30s`), `LAB_GAME_PROCESS_LIVENESS_INTERVAL` (the heartbeat cadence, `30s`) and `LAB_GAME_PROCESS_DOWNTIME_THRESHOLD` (the gap above which the restart shift runs, `5m`). Two notes rather than a widened clause: the first of them is this class's first **boolean**, so `internal/config` grew a `lookupBool` beside its existing lookup family; and a migration policy is operational tuning by the same test the other four scopes pass — an operator must be able to apply migrations out of band without a code change — while the required-with-no-default sentence is untouched, because none of these four is a credential, a base URL or a path. *Source:* the Bot API transport design D10, issue #19; the health-surface design D13, issue #23; the composition-root design, issue #24. *Decided:* 2026-09-04. *Amended:* 2026-09-10.

## Update ingestion (2026-09-06)

**KD-28 — Update ingestion is one package with one in-process poller, and the offset is a row holding `next_update_id`.** `internal/ingest` holds the loop, the router, the kind table, the offset, the give-up store, the observer and the gate — one cohesive unit with one contract surface, whose sub-packages would only ever import each other. **Only one poller may run against one bot token:** `getUpdates` confirms an update as soon as it is called with a higher offset, so two concurrent pollers would confirm each other's updates and lose them; what the shipped code enforces is narrower than a structural guarantee, and the distinction is worth keeping straight: one `Loop` polls sequentially and forks no goroutine of its own, so a single `Run` cannot overlap itself. Nothing stops a caller from building a second `Loop` over the same token or calling `Run` twice — no `sync.Once`, no atomic, no running flag — so single-pollership is a composition-root obligation, not an invariant this package can be relied on to hold. *The column's semantic is a decision, and the other reading is a live-lock:* `ingest_offset.next_update_id` stores `update_id + 1` and the loop transmits it **verbatim**, so the `+ 1` lives in exactly one statement — the advance — and nowhere on the poll path. Storing `n` and adding one at transmission, combined with the guarded-monotone advance (the write lands only when the new value exceeds the stored one), live-locks permanently: the same update is refetched every cycle, its handler returns `ErrAlreadyPosted`, the loop settles it as a duplicate and writes `n` again, the guard refuses `n > n`, and the offset never moves — with no symptom but an idempotency-hit count that nothing exposes until #23. *Consequences:* the advance for a handled update is written **inside that handler's own transaction**, so "handled" and "confirmed" commit together and the crash window between them is empty, while every other settled outcome (unrouted, duplicate after a rollback, given up) advances in a transaction of its own; one attempt is one transaction and a retry is a new one, with no savepoint machinery, because nothing here must survive a handler's failed subtransaction; the handler runs **inline under `recover`**, so there is no goroutine to leak and a recovered panic is a failure for the retry policy rather than a process exit; the offset row is a guarded singleton (`CHECK (id = 1)`) seeded at `0` by its own forward migration, and widening it to a per-bot key is a later migration rather than a speculative column today; and `allowed_updates` is transmitted on **every** poll — since `encoding/json` erases an *empty* slice under `omitempty` and an absent parameter silently inherits the server's previous setting, "send an empty list" is unreachable, so a loop with no route registered rides a one-element list holding the reserved `shipping_query` kind (an update this bot cannot receive, because it sends no invoices) instead of refusing to start. *Source:* the update-ingestion design D1/D3/D5/D6/D7/D14, issue #22. *Decided:* 2026-09-06.

**KD-29 — Inbound idempotency is the basis document's key, and the `operation_id` grammar `<space>:<id>` is `internal/ingest`'s, with an unexported builder.** There is no "seen updates" table: a replayed update is deduplicated by `player_operation`'s unique `(source, operation_id)`, which stays the only idempotency mechanism in the project ([`domain-invariants.md`](domain-invariants.md) § 3). The grammar belongs to this package because `internal/store` treats `operation_id` as opaque — `IDSpace` has one member for the `update_id` sequence and one for the `callback_query.id` sequence, and the builder joins the space token, `:` and the raw id, refusing an empty either. **The builder is unexported and `ingest.Update` carries the derived keys as fields**, so a handler cannot assemble an `operation_id` out of raw Telegram fields for want of a function to assemble one with — the structural form of the requirement rather than a rule in prose. A third id space costs one member and one field, never a migration of stored rows. *Classification is a sentinel test:* a handler error whose chain `errors.Is`-matches `store.ErrAlreadyPosted` settles as a duplicate — counted as an idempotency hit, no retry attempt consumed, offset advanced — and every other error, plus every recovered panic, takes the retry path; `errorlint` already forbids the `==` comparison that would not survive `%w`. *Consequence, and it is a trap the dependency sets:* `telego.Update` carries an unexported `context.Context` reachable through `Update.Context()` / `Update.WithContext()`, and the generated `getUpdates` attaches none — so the context riding in every update this package sees is a `context.Background()`, and a handler reading it would hold a context with no cancellation and no deadline, silently escaping both the loop's `ctx` and the attempt's transaction. Therefore the raw update is a **named** field of `ingest.Update` and never embedded (embedding would promote those two methods onto this project's own exported type), the handler's context is its first parameter, the riding one is never read, and `WithContext` is never called — it panics on a nil context, and a zero-panic package has no reason to invite that into a handler's call path. Structural tests walk for each of those. *Source:* the update-ingestion design D8/D9, issue #22. *Decided:* 2026-09-06.

**KD-30 — The outbound allowlist gains exactly one carve-out — a player — and the gate asks *who*, never what kind of chat.** `ingest.Gate` implements the consumer-declared `Gate` seam `internal/tg` exposes, so the allowlist lives in the package that already has the database and `internal/tg` gains neither a pool nor an import of `internal/store`. A `ChatKnown` destination is allowed when its `chat_id` token parses as an `int64` present in `AllowedChatIDs`, **or** when an `owner` row exists with `kind = 'player'` and that `telegram_id`; `ChatNone` is allowed, `ChatUnknown` refused, a token that parses as no integer refused, and a failed lookup refuses the call — the gate fails closed on every axis. *Why the kind is inside the predicate:* the schema's uniqueness is on the pair `(kind, telegram_id)` and a chat's own id lives in that same column, so a lookup keyed on the id alone would admit every chat the bot was ever added to — the allowlist bypassed by the bot's own knowledge. *Why a carve-out exists at all:* §1 puts every game command in DM, and a player's DM id is in no operator's list. *The cache holds positives only*, for the gate's lifetime, under one mutex, with the database call made **outside** the lock: nothing negative is remembered, so a player refused before their row existed is allowed on the next attempt with no restart and no invalidation path to get wrong, at the standing cost that revoking a player needs one. `sync.Map` was rejected — its wins are stable read-mostly keys under heavy core-count contention, which this seam does not have, and it would set a second concurrency vocabulary beside the shipped limiter's already-reviewed mutex. **And the rule the gate implies for every handler:** an outbound call whose permission rests on a row the handler's own *uncommitted* transaction created is refused, because the gate reads `owner` on a pool connection of its own — and the refusal is correct rather than a defect to work around, since a Telegram send cannot be rolled back and a message justified by a row that then rolls back has already reached a real person. Making the gate transaction-aware was rejected: it would smuggle a `pgx.Tx` through the outbound seam's context, make `internal/tg`'s gate contract database-aware, and buy a *worse* answer. The designed route is the outbound queue (#43) — enqueue in the transaction, send after the commit. *Two interfaces over one read, deliberately:* `store.Queryer` narrows what the read needs from its handle (one `QueryRow`, satisfied by both `pgx.Tx` and `*pgxpool.Pool`) and `ingest.PlayerLookup` narrows what the gate needs from the read (one boolean answer, and a place to count calls in a test) — each declared by its own consumer, per `AGENTS.md` § API Naming. *Source:* the update-ingestion design D10/D11/D17/D18, issue #22; the mechanics in [`domain-invariants.md`](domain-invariants.md) § 6. *Decided:* 2026-09-06.

**KD-31 — One exponential ramp for the whole module — `internal/backoff` — and both private copies are deleted, not left standing beside it.** `internal/tg`'s equal-jitter `backoffDelay` and `internal/scheduler`'s plain doubling `backoff` were the same `min(base·2^i, ceiling)` shape written twice, and the ingestion loop's retry policy needed a third. `internal/backoff` exports `Exponential(attempt, base, ceiling)` and `EqualJitter(attempt, base, ceiling, jitter)` over a **zero-based** attempt, and both shipped packages were re-pointed at it, the old functions removed rather than kept as delegating wrappers (`AGENTS.md` § API Stability) — the one-based→zero-based translation written at each call site, with every pre-existing assertion and expected value left byte-identical. **`Exponential` clamps at the ceiling *before* the doubling that would overflow, and that is exported contract rather than an implementation detail:** `time.Duration` is an `int64` of nanoseconds, the attempt argument is operator-reachable through the attempt-cap keys, and `base << attempt` — or a loop whose ceiling test comes after the doubling — wraps to a negative delay. *What the adoption cost, recorded because it is the reusable part:* the shipped scheduler suite is **invariant** to a missing translation at `settle.go`, because its expected `run_at` is computed through the very function the call site calls, so a byte-identical-assertion rule and a green `make verify` are both compatible with a wrong ramp. The instrument was built first — a literal one-based ramp table landed in the two persisted-`run_at` tests and confirmed green, then the wrong delay written at the call sites over a `cp` backup and required **RED**, and only then the re-point — per `AGENTS.md` § Patterns 2: a green gate is a claim about the gate until it has been seen to go red. *Consequence:* the ramp's call sites are now `internal/backoff`, `internal/tg`, `internal/scheduler` and `internal/ingest`, and #43's outbound queue is the next. *Amended by #22's round-6 amendment (design D20):* the ramp's growth factor is **configuration**, one key per adopter — `LAB_GAME_TG_RETRY_FACTOR`, `LAB_GAME_SCHEDULER_RETRY_FACTOR` and `LAB_GAME_INGEST_RETRY_FACTOR`, each defaulting to the named constant `backoff.DefaultFactor` (`= 2`) rather than to a re-typed literal, so every delay every adopter produces with none of the three set is the delay it produced before. The signatures are now `Exponential(attempt, base, ceiling, factor)` and `EqualJitter(attempt, base, ceiling, factor, jitter)` — the factor joins the ramp's other shape parameters, the jitter callback stays last, and every parameter is type-distinct, so a positional mix-up is a compile error rather than a wrong delay. **The clamp moved with it, and the no-wrap guarantee this entry states got stronger rather than weaker:** the doubling loop became `float64(base) * math.Pow(factor, attempt)`, and the clamp now sits immediately before the float→`time.Duration` conversion — anything not strictly below the ceiling (a finite value at or above it, `+Inf`, or a `NaN`) returns the ceiling itself, already a `time.Duration` and returned unconverted — so the only value ever converted lies in `[base, ceiling)`. The old loop could clamp only where the ceiling was reachable by doubling: at `base = 1ns` with `ceiling = MaxInt64` it returned a **negative** delay at attempt 63 and `0` past it, where the float form returns the ceiling. A factor that does not parse, is not finite, or is not strictly greater than `1` is a **start-up refusal**, and that boundary has exactly one definition — `backoff.ValidFactor` — called by `internal/config`'s reader (a `*KeyError` naming the variable) and by each adopter's constructor (its own option error naming its own field), each keeping its own error shape and sharing only the predicate; the finiteness half is not decoration, since `strconv.ParseFloat` accepts `"NaN"`, `"Inf"`, `"+inf"` and `"infinity"`, and `+Inf > 1` is true while `NaN > 1` is false. **The growth wording above is not strengthened by the amendment:** the contract still promises only that the delay *never decreases*, because the product is truncated to a whole nanosecond and two consecutive attempts can land on the same value. Behaviour preservation at the default is exact for a base below 2^53 nanoseconds (about 104 days); above that bound the float form and the deleted integer doubling diverge by a few nanoseconds at most, still positive and still clamped by the ceiling. *Source:* the update-ingestion design D2, issue #22. *Decided:* 2026-09-06.

## Composition root (2026-09-10)

**KD-32 — `cmd/bot` is the composition root itself, and its start-up is one written order that is all-fatal and unwinds through a single closer list.** No `internal/app` package: package `main` is split by phase across files (dispatch, assemble, readiness, serve/drain, migrate-only) with its tests beside them, the shape `cmd/commentrefs` already uses. Fourteen steps in a fixed order, each naming itself on stderr when it fails, each failure fatal — nothing is skipped, disabled or degraded on failure, the canaries included, which is the owner's explicit answer. *The one structure that carries it:* a `closer` list `assemble` appends to the moment a step takes something that must be given back, and only after the acquiring call returned nil. The start-up unwind and the drain's ordered shutdown are then the **same list walked backwards** rather than two hand-maintained parallel orders, which is why "what a failure at step N stops on the way out" is a property of the data structure instead of a claim beside it. *Rejected:* a shutdown call per failure site (drifts from the start-up order the first time a step moves); appending a closer *before* `Start` and swallowing the "not started" error an unstarted value returns (it would print a manufactured error beside the real bind error, and suppressing it would mean matching another package's error text). *Consequence:* the signal registration is step **1**, ahead of everything observable — before that call `SIGTERM` carries its default disposition and kills the process outright, so every later step would otherwise be a window in which a signal is a sudden death with nothing on stderr. Assembly itself is deliberately **not** interruptible: cancelling a half-applied migration buys nothing its transaction's rollback does not already give, and a start-up that hangs past the supervisor's grace period is the supervisor's `SIGKILL` to end. *Extended 2026-09-12 (#80):* the process's own HTTP client is built **inside** step 11 rather than as a fifteenth step — the step count is load-bearing prose in three live places — and joins the list as its own closer, appended before the Bot API client is constructed, so the backwards walk releases its idle connections after the canary legs that shared it have stopped. That closer is appended even when the caller supplied the client, which makes it the one entry giving back something the process did not itself take: the release then holds on every route rather than only the production one. *Source:* the composition-root design § *The shape* / § *Start-up*, issue #24. *Decided:* 2026-09-10.

**KD-33 — Shutdown is a stop seam beside the context, never a context cancel, and every runner carries the same one.** `Loop`, `Worker` and `Liveness` each grew `Stop()` — a `sync.Once`-guarded channel selected on beside `ctx.Done()`, with `Run` returning `nil` when stopped and `ctx.Err()` when cancelled. That `nil`-versus-`ctx.Err()` split is what lets the drain tell a completed shutdown from an abandoned one, so the exit code is read off the runner contract rather than from a per-runner exception. Cancelling the context would stop the cycle *and* abort the work inside it, which is exactly the in-flight work the drain exists to fund. *The one deliberate exception, scoped:* the ingest loop's `Stop` also cancels the `getUpdates` in flight — a poll parked in a 25s long-poll window holds the drain for nothing, and a discarded poll re-arrives because the offset is a guarded monotone row — but that cancel reaches the API call **only**; the offset read and every already-fetched update keep the parent context and settle, and the discarded poll is reported as discarded rather than as a poll error, so a graceful shutdown mints no error that never happened. *Rejected:* a composition-root wrapper cancelling a per-runner context for the liveness heartbeat (it would make a *stopped* runner return `context.Canceled`, a non-nil error that flips the exit code through the join path — the same branch a genuine failure takes — instead of returning `nil` like every other clean stop). *Also decided here:* a runner returning **before** any signal is itself a shutdown trigger — it begins the same drain, reports its name and error, and makes the exit non-zero, because a process that has lost a subsystem must not go on looking healthy; the runners are joined by a plain `errgroup.Group`, never `WithContext`, whose cancel-on-first-return would tear the siblings down at exactly the wrong moment. *Source:* the composition-root design § *Shutdown*, issue #24. *Decided:* 2026-09-10.

**KD-34 — Migrations apply at start-up by default, under goose's own advisory-lock id, with `bot migrate` as a second entry point rather than a second binary.** The default is apply-on-start (`LAB_GAME_PROCESS_MIGRATE_ON_START`, default `true`); with it off and anything pending the process **refuses to start**, naming the disabling variable, rather than serving against a schema it does not match. `store.Migrate` gained functional options so the lock stays **opt-in with a caller-supplied id** — an advisory lock is database-wide while the test suite's isolation is per-schema, so a lock in the default path would serialise every fixture in every binary behind one lock — and both production callers pass one exported constant, `store.ProcessLockID`, whose value **is** the library's own `lock.DefaultLockID`: taking the published id rather than minting a private number means any other goose-driven tooling pointed at the same database contends on the same lock instead of applying beside us. Two starters therefore never both apply; the one that arrives second waits out the lock and then proceeds to a normal start. The pending check is the provider's `HasPending`, which documents itself as ignoring a configured locker — exactly the semantics an auto-apply-off refusal needs. *`bot migrate`, not `cmd/migrate`:* one binary, one image, one place for the import gate to look, and the infrastructure pass gets an argv rather than a second artefact. It deliberately registers **no** signals — a registration with no reader does not delay a signal, it swallows it, and dying inside the lock wait costs nothing here because every migration runs in a transaction and the session lock dies with the connection. *Consequence:* readiness never re-asks whether migrations are pending — after the step the answer is established by construction, so the step latches it and readiness costs one pool round trip. *Source:* the composition-root design § *Migration policy* / § *The migrate-only entry point*, issue #24. *Decided:* 2026-09-10.

**KD-35 — Restart hygiene lives in `internal/scheduler`, and its whole decision is computed in SQL under a row lock.** The shift writes `scheduled_task.run_at`, and that table's package is its sole authority, so `Liveness` was added there rather than in `cmd/bot`: `AbsorbDowntime` is one transaction whose first statement is a `SELECT … FOR NO KEY UPDATE` on a NULL-seeded guarded singleton, `process_liveness`, returning both the stored instant and `now() - seen_at`; past the threshold it moves every overdue pending row by that same scanned interval, never a recomputed one. *Why SQL:* the package's standing rule is that every persisted instant comes from the database, and here it is also the acceptance condition — a process whose own clock disagrees with the database's must measure the same gap and move the same rows, which a `time.Now` anywhere on the path would break. The liveness source calls none of `time.Now`/`time.Since`/`time.Until`, held by a whole-file guard. *Why a row lock and not an advisory one:* atomicity is not mutual exclusion — under READ COMMITTED two concurrent starters would each see the pre-shift instant and each shift, doubling the move; `FOR NO KEY UPDATE` — the same mode the transaction's own non-key `UPDATE process_liveness SET seen_at = now()` already takes, and it conflicts with itself per PostgreSQL's locking table — makes the loser wait and then re-read what the winner wrote, a property `TestAbsorbDowntime_LockBlocksConcurrentSelect` proves directly (it drives two transactions by hand and asserts the second's locking `SELECT` has not returned while the first still holds the lock) rather than one asserted from the manual; `TestAbsorbDowntime_TwoConcurrentCallsShiftOnce`'s end-to-end goroutine pair does not overlap at the database and so cannot prove it, establishing only that the end-to-end path run twice leaves the row moved once. An advisory lock is database-wide while this table is per-schema, which would serialise unrelated schemas' fixtures on the shared test server. *Bounded tolerance rather than infinite:* a failing heartbeat is tolerated for `ceil(threshold / interval)` consecutive failures and then the runner returns, because a stale instant makes the *next* start shift rows for downtime that never happened — and a database this process cannot write to for that long could not have claimed a task or read an offset either. *Telemetry:* the measured gap and the shifted-row count are gauges; the shift moves no balance, so it declares no posting signature. *Source:* the composition-root design § *Restart hygiene*, issue #24. *Decided:* 2026-09-10.

## Test suite (2026-09-11)

**KD-36 — Every test binary ends with a goroutine-leak check, through one shared package, `internal/leaktest`, over `go.uber.org/goleak`, wrapping whatever owned the entry point.** Every package with tests declares `TestMain` as the single statement `os.Exit(leaktest.Main(m, run, ignore...))`, `run` being the runner that owned the entry point before — `testdb.Main` in a database-backed package, `(*testing.M).Run` everywhere else. `leaktest.Main` refuses a malformed ignore entry before any test runs, hands `m` to the runner, and, only when the runner returned zero, fails the binary on every goroutine still running outside the package's ignore set; on an unfiltered run it then evaluates each entry by leaving it out, failing one that excuses nothing or excuses this module's own code. A guard in `internal/leaktest`'s own tests fails the suite when a directory with tests lacks that `TestMain` under either build configuration the gates compile. *Why:* a leaked goroutine was a finding review had to make, and the owner asked for a checked condition instead — on every package with tests whether or not it starts a goroutine today, enforced rather than remembered, with every leak found at adoption fixed rather than excused. *Why one package over goleak:* every package with tests is a call site, far past the three-site threshold at which a shared `internal/` package is required over per-site copies; goleak was already a direct requirement, added by #24 for `cmd/bot`'s smoke test, and hand-rolling a goroutine-stack scan is refused by `AGENTS.md` § Dependency Versions. The package adds what goleak's public API cannot carry: its `Option` has only an unexported method, so no option written outside goleak can observe which entry matched which goroutine, and its `VerifyTestMain` exits the process itself — so the per-entry reason and the stale check are written once, here. *Why the detector wraps the runner and runs after it:* the runner is named at every site, so the composition is read where a reader meets it rather than discovered; and the check runs after the runner has returned — after `testdb.Main` has stopped the container it started on the fallback route — so it looks at the process once everything the entry point took has been given back. `testdb.Main`'s behaviour is unchanged. *Rejected:* a per-test `defer goleak.VerifyNone(t)` — goleak documents it as incompatible with `t.Parallel`, which is this suite's default shape (`cmd/bot`'s non-parallel smoke test keeps its own per-test check, taken against a snapshot); `goleak.VerifyTestMain` at every site — it exits the process itself, so it cannot wrap `testdb.Main` without an adapter per site, and it has no per-entry reason and no stale check; the check inside `testdb.Main` — it couples provisioning to leak detection, leaves every other package needing a second entry point, and gives the guard two entry points to vouch for; a check inside the runner, wrapping `m` before `testdb.Main` sees it — it would run before the provisioner's teardown, while what the entry point started is still running; a separate `make` target or a second pass over the suite — a run whose conditions are not the gate's, plus a CI step and a paths filter to keep it executed; a central ignore table keyed by import path — an entry naming a package later renamed or deleted is never evaluated, so it is never reported stale — dishonest by construction; scoping entries by provisioning route or by container runtime — no goroutine differed between the routes once the adoption leak was fixed, and if one ever does, its entry failing as not needed where the goroutine is absent is the signal to add that condition, by an owner decision; a patience window wider than goleak's own retry — it lets a goroutine that outlives its test by seconds pass as clean; the test's own `Context()` as the fake Bot API server's base context — it ends every in-flight request before the consumer's own cleanups have run; restating the go tool's file rules in the guard — `go/build` applies all of them, the legacy constraint form included, and reads in the test's own process. *Consequences:* the ignore set landed empty, because the one leak class found at adoption — a `tgtest.Delayed` handler still sleeping after its test ended — was fixed at its cause: `tgtest.New` gives its `http.Server` a base context its own cleanup cancels, and `Delayed` waits for its duration or for the request's context, whichever ends first, still on the virtual clock inside a `synctest` bubble (KD-26); a detection fails its package with no `--- FAIL:` line, so it is reproduced as the whole package with `-count=1` on the route it failed on, never with `-run`; the guard walks in-process and asks `go/build` which test files the default build and the race build each compile, so a package added later fails it even on a cached run, and a gate that ever sets a build tag of its own needs a third configuration there; KD-20's `Binaries` manifest now recognises the provisioner's `Main` by a parse rather than a substring, because the new form passes it as a value, and the count did not move; `Main` stays one delegating statement, because `testing` writes the coverage profile when `M.Run` returns, so nothing after the runner is counted by the package's own `TestMain` and every branch of the check is driven by its unit tests directly; there is no `Makefile` or workflow change, because the check rides in each package's `TestMain` and every invocation that runs a package's tests runs it; and a dependency goroutine that only CI's container runtime produces is a stop for an owner decision, never an entry added on CI's evidence alone. What an author follows day to day is [`go-test-conventions.md`](go-test-conventions.md) § *Goroutine-leak detection*. *Source:* the goroutine-leak-detection design D1–D10, issue #74. *Decided:* 2026-09-11.
