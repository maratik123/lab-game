# Key decisions

Decisions with the reasoning that produced them, so a later reader does not re-litigate a settled trade-off. Game-design decisions live in `~/lab-private/DESIGN.md` and are **not** duplicated here; this page carries the engineering and repository decisions, each pointing at its source.

Format: **KD-N — decision** · *why* · *consequence* · *source*.

## Stack

**KD-1 — Go.** Compilation and static types, a cheap instance (native binary), concurrency and networking in the standard library. Rust with `teloxide` was evaluated and rejected: incomplete Bot API surface plus framework opinionation. *Consequence:* the harness gates are `go build` / `go test -race` / `golangci-lint`. *Source:* `~/lab-private/DESIGN.md` §11.

**KD-2 — `telego` (mymmrac/telego), low-level layer only, pinned at `v1.11.2`.** Types and methods are generated one-to-one from the official documentation, so coverage is complete by construction. The helper layer is not used; a thin project-owned layer (`internal/tg`) adds retries with a never-retry-on-doubt classifier, rate limiting, an outbound gate, one typed error and one observation point. *Fallback if it disappoints:* `go-telegram/bot`. **Never** `go-telegram-bot-api` (frozen). *The pin, and what it is not:* `v1.11.2` declares `go 1.25.7`, while `v1.12.0` and `v1.12.1` declare `go 1.26.7` and the go command therefore refuses them *before* compiling — the installed toolchain is `go1.26.5` and `GOTOOLCHAIN` is `local`, here and in CI. **That is a configuration ceiling, not an incompatibility, and a later reader must not record `v1.12.x` as technically unusable:** its code builds clean under `go1.26.5` once its own directive is lowered, and `GOTOOLCHAIN=auto` dissolves the block outright by fetching a newer toolchain. Adopting `v1.12.x` also raises *this* module's `go` directive to `1.26.7`, which every local build and every CI runner would then have to satisfy — so raising the toolchain and moving to `v1.12.x` is **deferred to its own task** by the owner's decision rather than folded into the transport task. *The swap is half a runtime option and half a build tag, and only the runtime half is taken here.* §11's "replace `fasthttp`/`go-json` with `net/http` and `encoding/json`" resolves against `v1.11.2` into two different levers. **Taken:** `telego.WithAPICaller` installs this project's `net/http` caller, which also decodes the response envelope, and `telego.WithRequestConstructor` installs its `encoding/json` request marshaller — so every byte this project marshals or unmarshals itself goes through the standard library. **Not taken:** telego decodes the already-extracted `result` payload into its own generated types through a vendored reimplementation of `encoding/json`'s API, selected by the `stdjson` **build tag** rather than by an option. The tag works and removes `grbit/go-json` from the build graph, but adopting it changes what every `go` gate command *is*, and the Propagation Rule routes that to `AGENTS.md` § Build & Test, every skill's `allowed-tools` line and the `/task` gate checklist — a sweep found the bare gate commands spelled out across most of `.claude/**` and several `ai-docs/**` pages. **The owner's decision is a separate focused PR whose whole content is that propagation:** the residue is a recorded deferral, not an oversight, and half-threading the tag would leave a silently divergent second build configuration. `fasthttp` and `fastjson` remain in the module graph either way, tag or no tag; what a guard test asserts is that no file under `cmd/` or `internal/` imports them. *Consequences:* `internal/tg` is the only package that may name `telego.NewBot` or a `telego.With*` option, and a guard test enforces it — `telego.BotOption` is an exported function type, so any holder of the bot pointer could otherwise install its own caller and bypass the gate, the limiter and the observation; this module is the entire population of such code (no downstream importers, `AGENTS.md` § API Stability), which is what makes the guard a complete cover rather than a sample. Resolving the pin upgraded `github.com/stretchr/testify` to `v1.12.1`, indirect. *Source:* §11; the pin, the swap and the `stdjson` deferral from the Bot API transport design D1/D3, issue #19. *Decided:* 2026-09-04.

**KD-3 — Postgres + `pgx` + `goose` (`github.com/pressly/goose/v3`).** One database holds the ledger, the world, sessions, the event log and the scheduler queue — which is what makes a self-check like "opening + turnover == closing" meaningful at all. §11 named two migration tools (golang-migrate or goose); the owner chose goose: one SQL file per migration, embedded via `fs.FS`, applied by `store.Migrate` through `stdlib.OpenDBFromPool`. **Forward-only:** no `-- +goose Down` section anywhere — rolling a ledger table back is data loss, so a mistake is corrected by the next forward migration. *Source:* §11; goose and the no-`Down` policy decided 2026-09-02.

**KD-4 — A self-written scheduler on Postgres, not a job framework.** `scheduled_task` plus a worker on `SELECT … WHERE run_at <= now() FOR NO KEY UPDATE SKIP LOCKED`, each task executing in one transaction with its effects. ~100 lines, canonical pattern, horizontally scalable by adding a worker. `gocron` rejected (in-memory; one-shot tasks must survive restarts), Temporal rejected (overkill). *Escape hatch if it grows features:* River. *Source:* §11.

**KD-5 — Double-entry ledger with a global World account.** Append-only postings, zero-sum per kind enforced at write time, balances materialised only for controlled accounts, daily close for point-in-time balances. Pure event sourcing was rejected (a tax on every read); materialising a balance for *every* account was rejected (a hot row on World would be a global mutex on the economy). *Source:* §11, [`domain-invariants.md`](domain-invariants.md).

**KD-6 — A second machine for items with identity.** Instance-carrying items are never ledger kinds; ownership is a chain of movements. *Source:* §11.

**KD-7 — Lazy ticks instead of cron.** State is computed from timestamps at read time, so the bot is a stateless update handler over Postgres and restarts are trivial. The single true cron is the daily ledger close; the standing timer is the designed exception and rides the scheduler. *Amended by #24 — "restarts are trivial" is now true by construction on the scheduler side too, and it took one explicit step to keep it so:* lazy ticks make *state* restart-proof, but a persisted timer is not state computed at read time — every edge that came due during an outage is still sitting in `scheduled_task` when the process returns, and firing them all at once is the opposite of a trivial restart. The composition root's restart-hygiene step absorbs that: it measures the gap against a persisted liveness instant and, past a configured threshold, moves every overdue pending row forward by that gap. *Source:* §11. *Amended:* 2026-09-10.

**KD-8 — Raid session as an explicit FSM row.** No goroutines or in-memory timers; a restart is invisible to sessions; every transition is a basis document, so the transition log is a ready-made raid trace. *Amended by #24 — what "invisible" now means exactly:* a restart still costs a session nothing, because no edge is lost and no in-memory timer had to survive; what a *long* restart does move is the wall-clock instant an overdue edge arrives, since the restart-hygiene step shifts every overdue pending row forward by the measured downtime rather than firing the backlog in one salvo. A session is therefore invisible-to-restarts in the sense the row model buys — its transitions and its guard are untouched — and a mechanic must never assert that an edge fired at the instant it was scheduled for. *Source:* §3.5. *Amended:* 2026-09-10.

## Infrastructure

**KD-9 — Self-hosted `telegram-bot-api` from day one.** Motivation is a lived incident: the shared `api.telegram.org` frontend can wedge a specific bot for hours with no 429 and no error, and reissuing the token does not help because the state hangs on the bot id. A local instance talks MTProto to the DC directly and exposes `/stats`. It does **not** relax message rate limits — those are enforced by Telegram's core. *Source:* §12.2.

**KD-10 — Long polling, not webhooks.** Only outbound traffic is needed: no public IP, no domain, no TLS — so the whole thing can live on a home machine until a Mini App (radar) forces a public HTTPS endpoint. *Source:* §12.1.

**KD-11 — The test bot runs against cloud `api.telegram.org` while production runs on our instance.** Two independent paths to Telegram: "test bot works, production hangs" localises an incident instantly. Isolation is by configuration, never by code — same image, different env. *Source:* §12.5.

**KD-12 — A restore into testing is always sanitised.** Chat/user ids rewritten, outbound queue drained, updates offset reset — otherwise the test bot messages real people on the first tick. The same script doubles as the backup-restorability check, so that duty stops being a separate task. *Concrete as of #22:* the offset clause now names `ingest_offset`'s singleton row, the id clause reaches `ingest_dead_update.chat_id`, and there is a **fourth** obligation this three-clause summary does not cover — blank `ingest_dead_update.last_error`, whose free error prose can embed a real chat or user id that a column-targeted rewrite walks straight past ([`domain-invariants.md`](domain-invariants.md) § 6). *Source:* §12.3, §12.5.

## Repository and harness

**KD-13 — Module path `github.com/maratik123/lab-game`.** The repository is named for the project directory, not for the game's future name (which is an open question, §16.6), so finding the name later costs no import rewrite. *Decided:* 2026-08-29.

**KD-14 — Publish the repository, not its design corpus; server-side protection is whatever a ruleset requires.** The repository started private on the free plan, where GitHub refuses branch protection and rulesets (`403: Upgrade to GitHub Pro or make this repository public`), and the design document's economy and anti-abuse rules stayed unpublished because the repository was. The owner decided to publish the repository and to keep the design out of it: `DESIGN.md` and `IDEAS.md` moved to `~/lab-private/`, a git repository of its own (`AGENTS.md` § Project carries the AXIOM), and the world-topology redesign plan was deleted. History was **not** rewritten — every version of the design corpus up to the move stays readable in this repository's history, and the owner accepted that. *Consequence:* whether `main` is protected server-side is read from `gh api repos/maratik123/lab-game/rulesets`, never from this entry; without a ruleset it is protected only by the local commit hook and honour-system rules — see `AGENTS.md` § Permissions. *Decided:* 2026-08-29. *Amended:* 2026-09-14.

**KD-15 — The harness is ported from `graphite-gp` (itself evolved from `quartzite`), not reinvented.** What travels is the process — spec-driven `/task` flow, the learning loop, the propagation rule, the review agents. What is rewritten is every language-bound surface (gates, style, test and doc conventions, hooks) plus new domain rules for the ledger, telemetry and Telegram safety. Citations inherited from those projects are namespaced (`graphite-gp`'s log, `maratik123/quartzite#N`) rather than left as bare `#N`, which would resolve against *this* repository and lie. *Decided:* 2026-08-29.

**KD-16 — Strict `golangci-lint` from the first commit.** Enabled beyond the default set: `exhaustive` (an FSM switch must be total), `rowserrcheck` / `sqlclosecheck` (database correctness), `errorlint`, `nilerr`, `bodyclose`, `noctx`, `gosec`, `revive` with exported-doc rules; and, from the goroutine-ownership pass (#80), `containedctx` (a context stored in a struct field), `fatcontext` (a context nested in a loop or a function literal), `forbidigo` (`context.Background`, `context.TODO`, `time.Tick` and `time.After`, outside `main` packages and tests), `gocritic`'s `deferInLoop` and `govet`'s `nilness`. A finding is fixed, not silenced; `nolintlint` requires a specific linter and a stated reason on any exception. *The settings that keep the gate reporting are pinned with it:* `run.relative-path-mode: gomod`, without which an exclusion rule's `^cmd/` anchor stops meaning the module root; both issue-truncation caps at `0`, without which the gate stops reporting a class after its first few findings; and `issues.uniq-by-line: false`, without which it keeps only one finding per source line across linters — and "every site is handled" stops being a measurable claim under any of them. *Consequence:* an exclusion rule carries a `linters` list or it switches every linter off for its path, and a guard in `internal/gateguard` reads `.golangci.yml` and fails when the enabled set, the exclusion scoping or any pinned setting drifts; the enumeration with a reason per linter lives in [`code-style.md`](code-style.md) § *Linter posture*. *Decided:* 2026-08-29; extended 2026-09-12.

## Ledger core (2026-09-02)

**KD-17 — Account model: owner → scope → account, with two catalogs.** An `owner` has a kind from the open enum `owner_kind` (`world` — exactly one row; `player` and `chat` — identified by `telegram_id`, partial unique on `(kind, telegram_id)`); a `scope` belongs to an owner and points at a `scope_definition`; an `account` belongs to a scope and points at an `account_definition`, which carries the account's `ledger_kind` and its `controlled` flag. Kind therefore lives on the account definition, never on a posting. Scopes and accounts are singletons per `(owner, definition)`. *Why:* an open list of owner kinds and scopes (attributes, backpack, inventory, storage, constructions …) that grows by seeding a catalog row, without a per-kind column on `owner`. *Consequences:* singular table names and identity columns throughout; every referencing-side FK is covered by an index (a migration test enforces it); the transaction entity is `journal_entry`, 1:1 with its basis document (`player_operation` or `manual_correction`, exclusive arc) and the only holder of the timestamp; every controlled account gets its `account_balance` row at owner creation, so `Post` moves a balance with a plain `UPDATE` (an upsert would evaluate `CHECK (balance >= 0)` on the proposed row and refuse a covered debit) and a zero-row `UPDATE` is a broken invariant, never an overdraft; append-only is enforced in code only — the owner declined a database trigger. No composite FKs and no move-control: such moves are not planned by design, and the owner judged the declarative guard illusory. *Amended by #25 — «No composite FKs and no move-control» is scoped to the account model's own tables, not to the schema as a whole, and the owner ruled that scoping explicitly when the item machine's design raised it:* an account never moves, so a declarative guard against moving one guards nothing — but an item instance moves as its whole purpose, and there the guard is the mechanic. `item_movement` therefore carries a self-referential composite foreign key from `(prev_movement_id, item_id, from_holder_id)` to a predecessor's `(id, item_id, to_holder_id)`, alongside a `NULLS NOT DISTINCT` successor index, so "every movement's `from` equals its predecessor's `to`, and an instance sits at exactly one holder" is a database refusal rather than a convention. The same change gives `account_definition` a nullable `capacity_role` (`free` / `used`), which is what lets a capacity kind resolve to one account pair per holder without a branch on holder kind. *Amended:* 2026-09-12. *Source:* the ledger-core spec (`ai-docs/plans/2026-09-02-ledger-post-core.spec.md`), owner's redesign, 2026-09-02.

**KD-18 — Amounts are `numeric(30,5)`, and Go handles them as `shopspring/decimal`.** `posting.amount` and `account_balance.balance` are `numeric(30,5)`: balance tuning may produce fractions, and thirty digits is a reasonable ceiling. The Go side is `github.com/shopspring/decimal` with `github.com/jackc/pgx-shopspring-decimal` as the pgx codec — amounts will be operated on in game mechanics, so a decimal library beats integer minor units. *Consequence:* the codec is registered once per connection in `store.NewPool`'s `AfterConnect` (registering per call prepends to the type map every time); no `float32`/`float64` appears on the ledger path. *Decided:* 2026-09-02.

**KD-19 — Container images are pinned to the major tag.** `docker.io/library/postgres:18`, never `postgres:18.6` — the owner's standing preference for every container image, not only Postgres. *Why:* a patch tag pins what the image store already resolves to the same id, and it goes stale on every upstream release. *Decided:* 2026-09-02.

**KD-20 — Tests provision Postgres through testcontainers-go, and never skip.** `internal/testdb` starts a `postgres:18` container by default; `LAB_GAME_TEST_DSN` points the suite at an existing server instead (CI, or a developer with a server running). With neither, `testdb.Main` exits non-zero — "a job that did not run is not a passing job". Every test gets its own schema (`testdb.Schema`), so tests are order-independent and run in parallel against one server. The local development instance is not used by any committed file — the owner retired it for this purpose. *Consequence:* the container runtime never enters `cmd/bot`'s import graph — `go list -deps ./cmd/bot` must stay free of `testcontainers`, and since #24 that is a **gate**, not a documented hope: `make import-guard` (`cmd/importguard`) runs `go list -deps` over a rule table and fails on a forbidden module prefix, in `verify` and in CI's Build job. `depguard` was considered and rejected — it decides a file's own package imports, so a future `internal/` package that imported the runtime and was itself imported by the bot would pass it, which is a weaker proposition than the transitive one this invariant states. **That is the invariant, and it is not the same proposition as "only `_test.go` files import `internal/testdb`"**, which the amendment below stopped being true; a reader who carries the second one forward will read a legitimate importer as a violation. *Decided:* 2026-09-02. *Amended by #67 (design D2, D3, D3a):* **one server now serves the whole suite, and the per-binary path becomes the fallback rather than the default.** `cmd/testpg` wraps a gate command and exports the DSN into it, in a fixed decision order: a `LAB_GAME_TEST_DSN` already set by the caller is used exactly as it stands (a capacity shortfall is *reported* and the run proceeds — the contract is that the gates execute against the server the caller named); otherwise a long-lived server recorded by `make test-db-up` is used, but only if it answers *and* admits this run's computed need, falling through with a message when either check fails; otherwise the wrapper starts an **anonymous** container sized for the run and removes it on every exit path, an interrupt included — anonymous because only a server this invocation started may be removed, so two concurrent runs can never pull one out from under each other. `make test`, `make test-race` and the coverage ratchet all route through it, so a whole-module run starts **one** container instead of one per database-backed test binary; `make test-db-up` / `make test-db-down` keep a named long-lived server across runs, under a name derived from the checkout itself — the base name of the project directory the wrapper runs in plus `-test-postgres`, so a checkout at `~/lab-game` addresses `lab-game-test-postgres` and one at `~/lab-game2` addresses `lab-game2-test-postgres` — addressed by a DSN file under the ignored scratch directory; and `make test-fallback` — a bare whole-module run with the variable explicitly cleared, run as its own CI step — is what keeps the per-binary path executed now that no default gate reaches it. *The connection arithmetic of the shared configuration,* because one server must admit every client at once and a literal sized for one host is wrong on the next: `testdb.Ceiling(clients, parallel)` returns `clients × Binaries × parallel × (schemaMaxConns + 1) + ceilingSlack`, and that number is the `max_connections` the container is started with. `clients` is how many whole-module runs share the server **at the same time, all at the same `parallel`** — the product form is correct only under that condition — and defaults to 1, `make test-contention` being the one target that passes 2. `Binaries` is how many test binaries provision a database through `testdb.Main` — a count this entry deliberately does not state, because `TestBinaries_matchesTree` holds the constant equal to the number of `testdb.Main` callers in the tree — bounded above by `go test -p`'s own default, and that manifest test re-derives it from the tree so the next database-backed package fails by name instead of by exhaustion. `parallel` is how many tests run at once inside one binary, defaulting to `runtime.GOMAXPROCS(0)`; a target that pins its child's `-parallel` passes the same value to the wrapper, or the product funds neither client. `schemaMaxConns + 1` is the per-test pool cap `testdb.Schema` sets (**4**) plus one slot for the transient admin and dropper pools it opens around each schema. `ceilingSlack` is **32**: the server's own reserved slots (3 on this image) plus the one test that raises its pool cap above the per-test cap. The result is floored at the image's own default of **100** — computing less would only give back capacity the server already offers — while **the top is not a clamp**: above `ceilingMax`, **2000** and measured at capacity rather than guessed — a server started on the wrapper's own provisioning path, which sets no pids limit, was driven to hold every one of those connections at once, so what bounds the value is host memory at full use, not the server's start-up footprint — the wrapper refuses to provision at all, printing the computed value, the terms it came from and the flags that lower it, because silently granting less than the formula asks for is how a host quietly runs a population its server cannot admit. Two residues are stated rather than closed: `max_connections` is the server's *total*, not its free capacity, so a server that is large enough but already busy with another run passes the check and can still exhaust — the answer is to size it (`make test-db-up CLIENTS=2`), not a point-in-time free-slot count that would be racy and would make one gate's start depend on another gate's phase; and the fallback path keeps the image default, where one server serves one binary and the per-pool cap's own arithmetic still holds. *Amended by #24:* the composition root's own smoke condition made `cmd/bot` a database-backed test binary, so `Binaries` moved from 4 to 5 in the same commit that added the caller — the manifest test that re-derives it from the tree is what forces that pairing. *Amended by #91 (design D1, D3, D5, D6):* **the long-lived server's name is derived per checkout instead of being one fixed name for the host.** `cmd/testpg` takes the base name of its own working directory — the repository root every caller already invokes it from — and appends the fixed `-test-postgres` suffix, on `--up` and `--down` alike; `testdb.SharedContainerName` is deleted, so the wrapper is the only thing in this module that names a container. Two checkouts on one host therefore each own a server, and a `--down` in one leaves the other's running. The parent path contributes nothing, so two checkouts whose project directories carry the same name deliberately address one server — the owner's decision, not a residue. A base name the container runtime would refuse is never sanitised, because sanitising would map distinct checkouts onto one name and re-create the contention this removes; it fails instead before the reaper is touched or anything is provisioned, with a message naming the directory and the rule, which the runtime's own refusal does not carry. The anonymous fallback container stays anonymous: it is already per-invocation, so a name would buy no isolation and would cost the property that only a server this invocation started may be removed. *Amended by #110:* **the same `clients` input now sizes the PGDATA mount, not only the connection ceiling.** PGDATA and its WAL share one fixed-size tmpfs whose cap was a compile-time constant measured for a single client, while `Ceiling` scaled connections by `clients × parallel` — so the one target that passes `--clients 2` put two clients' schemas on a mount sized for one and exhausted it, and `make test-contention` had no working path at all: it died as an instrument failure (`No space left on device`, SQLSTATE 53100) before it could report anything about contention either way. `testdb.MountOptions(clients)` now returns the mount options the container is started with, granting `perClientMountMB` per client — **512**, the value a single client was always granted, kept byte-for-byte so the one-client default is unchanged — and a count below one sizes for one, so a zero `ServerOptions` stays usable. `walRetentionMB` is deliberately **unchanged at 64**: the mount grows per client while the retention target holds, which only widens the headroom the two numbers share, so they remain one decision rather than two. *What keeps the pair honest* is a budget assertion carrying a `clients` term, reading the literal counts out of the build file, and it carries **two** assertions because they catch different things. The budget half — WAL allowance plus per-client peak against the per-client grant — catches a broken *linkage*: remove the per-client term from the mount and it fails naming the shortfall. It cannot catch a merely larger client count, and saying otherwise was a claim this decision carried for several rounds before a review caught it: the count cancels, `128 + 320c ≤ 512c` reducing to `128 ≤ 192c`, true for every count — which is correct, since a bigger count buys proportionally more mount than it needs. What a bigger count really outruns is the figure's *basis*, so the second half asserts exactly that: `clusterPeakMB` was measured at **two** clients at `parallel=16`, nothing establishes that a per-client peak survives at four or nine where clients contend for shared buffers, autovacuum and checkpoint I/O, and provisioning more than the measured count fails by name telling the author to re-measure first. The figure itself is a measured **peak under sustained load**, not the cluster residue the first version of this assertion used, because the residue is 0.60 of the peak (193 MB against 320 MB per client) and would green-light a mount the run still overruns — a guard passing for the wrong reason. *And the reuse path is checked on BOTH axes, because a capacity probe cannot see a mount:* a container reused under its name keeps the ceiling **and** the mount it was created with, so resizing either needs a down-and-up. The connection cap is read back off the running server and compared with **this** run's computed need, which is correct for connections. That comparison cannot bound the *mount*, and not only because the mount is invisible to a SQL probe: `Ceiling` scales with `parallel` as well as `clients`, so a reusing run at a lower `parallel` computes a *smaller* need and passes the capacity check while requiring a *larger* mount — measured, a server created at `CLIENTS=1 parallel=16` (ceiling 432, mount 512 MB) admits a `--clients 2 --parallel 2` run (need 132) that requires 1024 MB, and `Ceiling`'s floor at `imageDefaultCeiling` opens the same hole a second way at small `parallel`. So the mount is bounded by its own recorded fact instead: the locator file records a client count the server is **known to satisfy** — emphatically not one that was merely asked for — and a run needing more than that is declined **before** any probe, naming both counts. The distinction is the whole mechanism, because recording an *asked-for* count is a defect that undoes the check by following this decision's own advice: `make test-db-up CLIENTS=2` against an already-running one-client server is correctly refused, and if that refusal had still recorded 2, every later two-client run would then reuse the one-client mount silently. So `--up` decides first and records second, and what it records is the largest count something actually **vouches** for — never the count asked. It starts at one client; it is raised to a prior locator's count when that locator names the very server just reattached to; and it is raised again to this invocation's own count only when this invocation **created** the container, which makes it correctly sized by construction. Whether it created the container is asked *before* provisioning, so the answer describes the state found rather than the state caused, and an error there reads as "already existed". Because every step only ever raises, a refusal never lowers a count and a smaller later `--up` never downgrades a larger vouched one — a plain `make test-db-up` after `make test-db-up CLIENTS=2` leaves the 2 standing. And a reattach nothing vouches for is refused outright once it asks for more than one client, which is precisely the case the capacity check cannot see: `Ceiling(1,1)` and `Ceiling(2,1)` are both the floored image default, so the ceilings coincide where the mounts do not. The DSN is recorded on every path regardless, so a refused `--up` never orphans a container `--down` would have to find. A locator carrying no count — one written before this was recorded — reads as one client for the same reason, failing closed, so a multi-client run declines it and provisions its own rather than trusting a mount that may be too small. Verified end to end in both directions: the two-client run at low `parallel` now falls through and provisions `rw,size=1024m`, while a one-client run still reuses the shared server, so the guard discriminates rather than disabling reuse. *And the mount scales with `clients` only, never with `parallel`*, though peak disk also depends on how many schemas exist at once; that is the chosen direction, not an oversight. *Amended by #26 (design D15, D16):* **two new `testdb.Main` callers raised `Binaries`, the raise pushed the two-client ceiling past the old `ceilingMax`, and `ceilingMax` was re-measured and raised from 1000 to 2000.** `internal/storetest` (the shared migrated-schema pool, KD-42) and `internal/contract` each carry a database-backed `TestMain`, so `Binaries` moved from 5 to 7, each raise landing in the commit that added its caller. On a 16-core host that made the two-client ceiling `2 × 7 × 16 × (4 + 1) + 32 = 1152`, above the old limit, and the wrapper refused before provisioning anything — so `make test-contention` and `make test-db-up CLIENTS=2`, the two targets that size a server for two clients at the host's parallelism, could not run there. Of the two routes the shared-test-server design left open for a host where the refusal fires — pin the parallelism, or re-measure what the container tolerates and raise the limit — this took the second. The re-measurement found three things: a container the wrapper starts has **no** pids limit, so the runtime's command-line default does not reach it, and the server held at capacity ran more processes than that default would admit; a 2000-connection server holding every slot at once served all of them; and the cost of that was host memory at full use, while the server's start-up allocation stayed small. `ceilingMax`'s own comment carries the recipe, and a larger value needs the same at-capacity measurement on the host meant to carry it — editing the number alone is not enough. *Rejected:* pinning parallelism below the core count in the two targets. For `make test-contention` it lowers the very load the probe exists to induce, and lowers it again with every database-backed package added later, so the instrument would weaken silently as the tree grows. ## Bot API transport (2026-09-04)

**KD-25 — The outbound rate limiter is project-owned: one schedule per key, holding every window.** A *schedule* is the whole state for one limiter key — its set of window constraints `(count, per)` plus the emission instants it has already granted — and its invariant is that no half-open interval of length `per` ever contains more than `count` grants. A pacing rate and a quota cap are the same kind of constraint under that model, which is what lets one mechanism hold both: `1/1s` is `(1, 1s)`, `20/1m` is `(20, 60s)`, and a pacing key contributes both `(1, ceil(per/count))`, which fixes the *shape* — one emission per interval instead of a burst — and `(count, per)`, which states the bound itself. The acquisition rule is **decide the emission instant against every constraint first, commit to every constraint at that same instant, never commit before the answer is final and never partially undo**; the two schedule kinds differ only in their answer to "earliest admissible instant", the per-`(chat, class)` key being **ordered** (the candidate is raised to that key's own newest grant, so its emission order is its arrival order) and the class-global key **unordered** (a class ceiling carries no ordering obligation, and imposing one held a quiet chat behind a busy chat's backlog). *Why:* an earlier design composed separate limiter legs and produced four defects of one shape across three review rounds — a leg committing at an instant another leg then moved, so a bound held on reservations rather than on emissions. The rule above removes the shape instead of patching its instances, and the mechanism is checked by a postcondition asserted after every insertion plus a brute-force oracle, not by an argument in a design document. *Why not a package* — `AGENTS.md` § Dependency Versions requires this comparison and KD-4 is the model: the requirement is to **shape** (answer *when*, never drop), to honour a context deadline and report refusal as this project's own typed error, and to hold **more than one window on one key**; every maintained candidate read fails the first clause, the third, or both. *Rejected:* `golang.org/x/time/rate` — a token bucket of size `b` refilled at rate `r` admits `b + r·W` in a window of length `W`, so no `burst` value makes it mean "at most `c` per `per`", and using it for one window while owning another is exactly the composition this decision forbids; `throttled/throttled/v2` — **policing**, not shaping: `RateLimitCtx` answers *allowed?*, not *when*, and its `RateQuota` carries the same burst parameter; `ulule/limiter/v3` — policing again, its whole `*Limiter` surface being `Get`/`Peek`/`Reset`/`Increment`, each returning a `Reached` verdict; `go.uber.org/ratelimit` — a genuine shaping leaky bucket, but `Take() time.Time` takes **no context**, so a call parked behind it cannot be cancelled; `github.com/sethvargo/go-limiter` — policing, `Take` returning an `ok` flag documented "If `ok` is false … the caller should NOT service the request". **No module is added for this**: `golang.org/x/time` is not a dependency of this project. *Escape hatch, in KD-4's spirit:* if a maintained package appears that shapes to a deadline with a context and expresses more than one window on a key, the schedule is one unexported type behind an internal call and is replaceable without touching the caller. *Two properties it deliberately does NOT provide, both reached the hard way.* **No grant reclamation:** a call cancelled after its instant is committed leaves that instant behind, because removing a grant for a call *outcome* is the shape that has already failed twice — once where the undo was not the inverse of the do, once where a refusal that removed its own instant shrank the window's memory. The only removal is ageing out, a function of the window set and the clock alone, which is what makes that defect structurally impossible rather than merely repaired; and the hole is safe in the one direction that matters, since a leftover grant can only push later grants *later*, so the limiter emits at or below its configured rate and never above it. It costs throughput under saturation, never flood safety, and it ages out after `per`. **No per-key locking:** one mutex covers the whole limiter, because per-key locks with a fixed acquisition order would restore the multi-component state commitment that produced every defect above; the critical section is a walk over a small window set and one insertion, which at MVP scale (one chat) and at fan-out scale (one bulk sender) is not a contention surface worth that risk. Contention is the thing to measure if it is ever revisited, and any replacement must keep decide-then-commit intact rather than merely shard the map. *Consequences:* retention is by **time**, never by count — a count bound is sound only on an append-only ordered schedule and would silently discard still-live grants on an unordered one — so the retained set is O(calls in flight); the registry holds one schedule per `(chat, class)` of a bounded class and does not evict, a known bound whose trigger to revisit is #43's fan-out, and whoever adds eviction must make it time-based, because dropping a key discards its grants and resets every window it was enforcing; an unbounded class (`off`) contributes no window, so it never blocks and allocates no history; and nothing persists — the state is in-process and touches no table, no disk and no migration, the durable queue staying #43's. *Source:* the Bot API transport design D9, after the owner's redirect away from composed legs; issue #19. *Decided:* 2026-09-04.

**KD-26 — Tests use `testing/synctest`; production code carries no clock abstraction.** The transport spec asked for an injectable clock *or an equivalent*, and the standard library ships the equivalent: inside a `synctest` bubble the whole `time` package is a fake clock, each bubble with its own. Production code therefore calls `time.Now` and `time.NewTimer` **directly** — no clock interface is threaded through the limiter or the caller — while the tests still get exact, instantaneous virtual time. *Why:* fewer moving parts in production *and* stronger assertions at once; and the limiter's whole contract is a statement about instants, so a test that cannot pin instants exactly cannot check it. Demonstrated on the exact stack the tests use rather than a nearby one — a real `*http.Transport` whose `DialContext` returns a `net.Pipe` connection with `DisableKeepAlives`, no listener and no socket — where a handler sleeping two virtual seconds completed in `0.00s` of wall time, clean under `-race`; the strategy turns on a pipe conn being durably blockable inside a bubble while a real listener is not, so a probe over a real socket would not have shown it. *Consequences:* the retry, `retry_after`, backoff, deadline and cancellation scenarios simulate hours and run in hundredths of a second; and three bubble rules bind the test code — `t.Run`, `t.Parallel` and `t.Deadline` must not be called inside a bubble, so a table-driven test puts `synctest.Test` **inside** each subtest and calls `t.Parallel()` outside it, which leaves this repo's table-test convention intact; a goroutine still blocked when the bubble's root returns is a hard failure, so the in-process fake Bot API server (`internal/tgtest`) disables keep-alives, closes its side of every pipe and registers its cleanup through `t.Cleanup`; and time advances only when every bubble goroutine is durably blocked, which is also the lever that makes arrival order deterministic, since releasing N concurrent callers one at a time with `synctest.Wait()` fixes the order in which they reach the limiter. *Source:* the Bot API transport design D14, issue #19. *Decided:* 2026-09-04.

The message-class defaults are the figures Telegram publishes, verified upstream together with their modality — `30/1s` globally and `20/1m` into one chat are stated as enforced, `1/1s` into one chat is stated as advice — and the edit and other classes default to `off` because the same page states no figure for them: throttling on an unciteable number would delay gameplay against a limit Telegram may not impose, while a 429 is honoured exactly and is safe to retry. `~/lab-private/DESIGN.md` §11 carries the global and per-minute figures but not the per-second one, and the owner declined to edit §11, so that incompleteness is known and accepted rather than unnoticed. *The boundary, stated exactly:* the relaxation reaches **only** operational tuning keys — these fourteen, the seven `LAB_GAME_SCHEDULER_*` keys the Postgres task scheduler later added as the second member of this same class (issue #20), the seven `LAB_GAME_INGEST_*` keys update ingestion added as the third (issue #22), the four `LAB_GAME_HEALTH_*` keys the health surface added as the fourth (issue #23), and the four `LAB_GAME_PROCESS_*` keys the composition root added as the fifth (issue #24). ## Update ingestion (2026-09-06)

**KD-28 — Update ingestion is one package with one in-process poller, and the offset is a row holding `next_update_id`.** `internal/ingest` holds the loop, the router, the kind table, the offset, the give-up store, the observer and the gate — one cohesive unit with one contract surface, whose sub-packages would only ever import each other. **Only one poller may run against one bot token:** `getUpdates` confirms an update as soon as it is called with a higher offset, so two concurrent pollers would confirm each other's updates and lose them; what the shipped code enforces is narrower than a structural guarantee, and the distinction is worth keeping straight: one `Loop` polls sequentially and forks no goroutine of its own, so a single `Run` cannot overlap itself. Nothing stops a caller from building a second `Loop` over the same token or calling `Run` twice — no `sync.Once`, no atomic, no running flag — so single-pollership is a composition-root obligation, not an invariant this package can be relied on to hold. *The column's semantic is a decision, and the other reading is a live-lock:* `ingest_offset.next_update_id` stores `update_id + 1` and the loop transmits it **verbatim**, so the `+ 1` lives in exactly one statement — the advance — and nowhere on the poll path. Storing `n` and adding one at transmission, combined with the guarded-monotone advance (the write lands only when the new value exceeds the stored one), live-locks permanently: the same update is refetched every cycle, its handler returns `ErrAlreadyPosted`, the loop settles it as a duplicate and writes `n` again, the guard refuses `n > n`, and the offset never moves — with no symptom but an idempotency-hit count that nothing exposes until #23. *Consequences:* the advance for a handled update is written **inside that handler's own transaction**, so "handled" and "confirmed" commit together and the crash window between them is empty, while every other settled outcome (unrouted, duplicate after a rollback, given up) advances in a transaction of its own; one attempt is one transaction and a retry is a new one, with no savepoint machinery, because nothing here must survive a handler's failed subtransaction; the handler runs **inline under `recover`**, so there is no goroutine to leak and a recovered panic is a failure for the retry policy rather than a process exit; the offset row is a guarded singleton (`CHECK (id = 1)`) seeded at `0` by its own forward migration, and widening it to a per-bot key is a later migration rather than a speculative column today; and `allowed_updates` is transmitted on **every** poll — since `encoding/json` erases an *empty* slice under `omitempty` and an absent parameter silently inherits the server's previous setting, "send an empty list" is unreachable, so a loop with no route registered rides a one-element list holding the reserved `shipping_query` kind (an update this bot cannot receive, because it sends no invoices) instead of refusing to start. *Source:* the update-ingestion design D1/D3/D5/D6/D7/D14, issue #22. *Decided:* 2026-09-06.

**KD-29 — Inbound idempotency is the basis document's key, and the `operation_id` grammar `<space>:<id>` is `internal/ingest`'s, with an unexported builder.** There is no "seen updates" table: a replayed update is deduplicated by `player_operation`'s unique `(source, operation_id)`, which stays the only idempotency mechanism in the project ([`domain-invariants.md`](domain-invariants.md) § 3). The grammar belongs to this package because `internal/store` treats `operation_id` as opaque — `IDSpace` has one member for the `update_id` sequence and one for the `callback_query.id` sequence, and the builder joins the space token, `:` and the raw id, refusing an empty either. **The builder is unexported and `ingest.Update` carries the derived keys as fields**, so a handler cannot assemble an `operation_id` out of raw Telegram fields for want of a function to assemble one with — the structural form of the requirement rather than a rule in prose. A third id space costs one member and one field, never a migration of stored rows. *Classification is a sentinel test:* a handler error whose chain `errors.Is`-matches `store.ErrAlreadyPosted` settles as a duplicate — counted as an idempotency hit, no retry attempt consumed, offset advanced — and every other error, plus every recovered panic, takes the retry path; `errorlint` already forbids the `==` comparison that would not survive `%w`. *Consequence, and it is a trap the dependency sets:* `telego.Update` carries an unexported `context.Context` reachable through `Update.Context()` / `Update.WithContext()`, and the generated `getUpdates` attaches none — so the context riding in every update this package sees is a `context.Background()`, and a handler reading it would hold a context with no cancellation and no deadline, silently escaping both the loop's `ctx` and the attempt's transaction. Therefore the raw update is a **named** field of `ingest.Update` and never embedded (embedding would promote those two methods onto this project's own exported type), the handler's context is its first parameter, the riding one is never read, and `WithContext` is never called — it panics on a nil context, and a zero-panic package has no reason to invite that into a handler's call path. Structural tests walk for each of those. *Source:* the update-ingestion design D8/D9, issue #22. *Decided:* 2026-09-06.

**KD-30 — The outbound allowlist gains exactly one carve-out — a player — and the gate asks *who*, never what kind of chat.** `ingest.Gate` implements the consumer-declared `Gate` seam `internal/tg` exposes, so the allowlist lives in the package that already has the database and `internal/tg` gains neither a pool nor an import of `internal/store`. A `ChatKnown` destination is allowed when its `chat_id` token parses as an `int64` present in `AllowedChatIDs`, **or** when an `owner` row exists with `kind = 'player'` and that `telegram_id`; `ChatNone` is allowed, `ChatUnknown` refused, a token that parses as no integer refused, and a failed lookup refuses the call — the gate fails closed on every axis. *Why the kind is inside the predicate:* the schema's uniqueness is on the pair `(kind, telegram_id)` and a chat's own id lives in that same column, so a lookup keyed on the id alone would admit every chat the bot was ever added to — the allowlist bypassed by the bot's own knowledge. *Why a carve-out exists at all:* §1 puts every game command in DM, and a player's DM id is in no operator's list. *The cache holds positives only*, for the gate's lifetime, under one mutex, with the database call made **outside** the lock: nothing negative is remembered, so a player refused before their row existed is allowed on the next attempt with no restart and no invalidation path to get wrong, at the standing cost that revoking a player needs one. `sync.Map` was rejected — its wins are stable read-mostly keys under heavy core-count contention, which this seam does not have, and it would set a second concurrency vocabulary beside the shipped limiter's already-reviewed mutex. **And the rule the gate implies for every handler:** an outbound call whose permission rests on a row the handler's own *uncommitted* transaction created is refused, because the gate reads `owner` on a pool connection of its own — and the refusal is correct rather than a defect to work around, since a Telegram send cannot be rolled back and a message justified by a row that then rolls back has already reached a real person. Making the gate transaction-aware was rejected: it would smuggle a `pgx.Tx` through the outbound seam's context, make `internal/tg`'s gate contract database-aware, and buy a *worse* answer. The designed route is the outbound queue (#43) — enqueue in the transaction, send after the commit. *Two interfaces over one read, deliberately:* `store.Queryer` narrows what the read needs from its handle (one `QueryRow`, satisfied by both `pgx.Tx` and `*pgxpool.Pool`) and `ingest.PlayerLookup` narrows what the gate needs from the read (one boolean answer, and a place to count calls in a test) — each declared by its own consumer, per `AGENTS.md` § API Naming. *Source:* the update-ingestion design D10/D11/D17/D18, issue #22; the mechanics in [`domain-invariants.md`](domain-invariants.md) § 6. *Decided:* 2026-09-06.

**KD-31 — One exponential ramp for the whole module — `internal/backoff` — and both private copies are deleted, not left standing beside it.** `internal/tg`'s equal-jitter `backoffDelay` and `internal/scheduler`'s plain doubling `backoff` were the same `min(base·2^i, ceiling)` shape written twice, and the ingestion loop's retry policy needed a third. `internal/backoff` exports `Exponential(attempt, base, ceiling)` and `EqualJitter(attempt, base, ceiling, jitter)` over a **zero-based** attempt, and both shipped packages were re-pointed at it, the old functions removed rather than kept as delegating wrappers (`AGENTS.md` § API Stability) — the one-based→zero-based translation written at each call site, with every pre-existing assertion and expected value left byte-identical. **`Exponential` clamps at the ceiling *before* the doubling that would overflow, and that is exported contract rather than an implementation detail:** `time.Duration` is an `int64` of nanoseconds, the attempt argument is operator-reachable through the attempt-cap keys, and `base << attempt` — or a loop whose ceiling test comes after the doubling — wraps to a negative delay. *What the adoption cost, recorded because it is the reusable part:* the shipped scheduler suite is **invariant** to a missing translation at `settle.go`, because its expected `run_at` is computed through the very function the call site calls, so a byte-identical-assertion rule and a green `make verify` are both compatible with a wrong ramp. The instrument was built first — a literal one-based ramp table landed in the two persisted-`run_at` tests and confirmed green, then the wrong delay written at the call sites over a `cp` backup and required **RED**, and only then the re-point — per `AGENTS.md` § Patterns 2: a green gate is a claim about the gate until it has been seen to go red. *Consequence:* the ramp's call sites are now `internal/backoff`, `internal/tg`, `internal/scheduler` and `internal/ingest`, and #43's outbound queue is the next. *Amended by #22's round-6 amendment (design D20):* the ramp's growth factor is **configuration**, one key per adopter — `LAB_GAME_TG_RETRY_FACTOR`, `LAB_GAME_SCHEDULER_RETRY_FACTOR` and `LAB_GAME_INGEST_RETRY_FACTOR`, each defaulting to the named constant `backoff.DefaultFactor` (`= 2`) rather than to a re-typed literal, so every delay every adopter produces with none of the three set is the delay it produced before. The signatures are now `Exponential(attempt, base, ceiling, factor)` and `EqualJitter(attempt, base, ceiling, factor, jitter)` — the factor joins the ramp's other shape parameters, the jitter callback stays last, and every parameter is type-distinct, so a positional mix-up is a compile error rather than a wrong delay. **The clamp moved with it, and the no-wrap guarantee this entry states got stronger rather than weaker:** the doubling loop became `float64(base) * math.Pow(factor, attempt)`, and the clamp now sits immediately before the float→`time.Duration` conversion — anything not strictly below the ceiling (a finite value at or above it, `+Inf`, or a `NaN`) returns the ceiling itself, already a `time.Duration` and returned unconverted — so the only value ever converted lies in `[base, ceiling)`. The old loop could clamp only where the ceiling was reachable by doubling: at `base = 1ns` with `ceiling = MaxInt64` it returned a **negative** delay at attempt 63 and `0` past it, where the float form returns the ceiling. A factor that does not parse, is not finite, or is not strictly greater than `1` is a **start-up refusal**, and that boundary has exactly one definition — `backoff.ValidFactor` — called by `internal/config`'s reader (a `*KeyError` naming the variable) and by each adopter's constructor (its own option error naming its own field), each keeping its own error shape and sharing only the predicate; the finiteness half is not decoration, since `strconv.ParseFloat` accepts `"NaN"`, `"Inf"`, `"+inf"` and `"infinity"`, and `+Inf > 1` is true while `NaN > 1` is false. **The growth wording above is not strengthened by the amendment:** the contract still promises only that the delay *never decreases*, because the product is truncated to a whole nanosecond and two consecutive attempts can land on the same value. Behaviour preservation at the default is exact for a base below 2^53 nanoseconds (about 104 days); above that bound the float form and the deleted integer doubling diverge by a few nanoseconds at most, still positive and still clamped by the ceiling. *Source:* the update-ingestion design D2, issue #22. *Decided:* 2026-09-06.

## Composition root (2026-09-10)

**KD-32 — `cmd/bot` is the composition root itself, and its start-up is one written order that is all-fatal and unwinds through a single closer list.** No `internal/app` package: package `main` is split by phase across files (dispatch, assemble, readiness, serve/drain, migrate-only) with its tests beside them, the shape `cmd/commentrefs` already uses. Fourteen steps in a fixed order, each naming itself on stderr when it fails, each failure fatal — nothing is skipped, disabled or degraded on failure, the canaries included, which is the owner's explicit answer. *The one structure that carries it:* a `closer` list `assemble` appends to the moment a step takes something that must be given back, and only after the acquiring call returned nil. The start-up unwind and the drain's ordered shutdown are then the **same list walked backwards** rather than two hand-maintained parallel orders, which is why "what a failure at step N stops on the way out" is a property of the data structure instead of a claim beside it. *Rejected:* a shutdown call per failure site (drifts from the start-up order the first time a step moves); appending a closer *before* `Start` and swallowing the "not started" error an unstarted value returns (it would print a manufactured error beside the real bind error, and suppressing it would mean matching another package's error text). *Consequence:* the signal registration is step **1**, ahead of everything observable — before that call `SIGTERM` carries its default disposition and kills the process outright, so every later step would otherwise be a window in which a signal is a sudden death with nothing on stderr. Assembly itself is deliberately **not** interruptible: cancelling a half-applied migration buys nothing its transaction's rollback does not already give, and a start-up that hangs past the supervisor's grace period is the supervisor's `SIGKILL` to end. *Extended 2026-09-12 (#80):* the process's own HTTP client is built **inside** step 11 rather than as a fifteenth step — the step count is load-bearing prose in three live places — and joins the list as its own closer, appended before the Bot API client is constructed, so the backwards walk releases its idle connections after the canary legs that shared it have stopped. That closer is appended even when the caller supplied the client, which makes it the one entry giving back something the process did not itself take: the release then holds on every route rather than only the production one. *Source:* the composition-root design § *The shape* / § *Start-up*, issue #24. *Decided:* 2026-09-10.

**KD-33 — Shutdown is a stop seam beside the context, never a context cancel, and every runner carries the same one.** `Loop`, `Worker` and `Liveness` each grew `Stop()` — a `sync.Once`-guarded channel selected on beside `ctx.Done()`, with `Run` returning `nil` when stopped and `ctx.Err()` when cancelled. That `nil`-versus-`ctx.Err()` split is what lets the drain tell a completed shutdown from an abandoned one, so the exit code is read off the runner contract rather than from a per-runner exception. Cancelling the context would stop the cycle *and* abort the work inside it, which is exactly the in-flight work the drain exists to fund. *The one deliberate exception, scoped:* the ingest loop's `Stop` also cancels the `getUpdates` in flight — a poll parked in a 25s long-poll window holds the drain for nothing, and a discarded poll re-arrives because the offset is a guarded monotone row — but that cancel reaches the API call **only**; the offset read and every already-fetched update keep the parent context and settle, and the discarded poll is reported as discarded rather than as a poll error, so a graceful shutdown mints no error that never happened. *Rejected:* a composition-root wrapper cancelling a per-runner context for the liveness heartbeat (it would make a *stopped* runner return `context.Canceled`, a non-nil error that flips the exit code through the join path — the same branch a genuine failure takes — instead of returning `nil` like every other clean stop). *Also decided here:* a runner returning **before** any signal is itself a shutdown trigger — it begins the same drain, reports its name and error, and makes the exit non-zero, because a process that has lost a subsystem must not go on looking healthy; the runners are joined by a plain `errgroup.Group`, never `WithContext`, whose cancel-on-first-return would tear the siblings down at exactly the wrong moment. *Source:* the composition-root design § *Shutdown*, issue #24. *Decided:* 2026-09-10.

**KD-34 — Migrations apply at start-up by default, under goose's own advisory-lock id, with `bot migrate` as a second entry point rather than a second binary.** The default is apply-on-start (`LAB_GAME_PROCESS_MIGRATE_ON_START`, default `true`); with it off and anything pending the process **refuses to start**, naming the disabling variable, rather than serving against a schema it does not match. `store.Migrate` gained functional options so the lock stays **opt-in with a caller-supplied id** — an advisory lock is database-wide while the test suite's isolation is per-schema, so a lock in the default path would serialise every fixture in every binary behind one lock — and both production callers pass one exported constant, `store.ProcessLockID`, whose value **is** the library's own `lock.DefaultLockID`: taking the published id rather than minting a private number means any other goose-driven tooling pointed at the same database contends on the same lock instead of applying beside us. Two starters therefore never both apply; the one that arrives second waits out the lock and then proceeds to a normal start. The pending check is the provider's `HasPending`, which documents itself as ignoring a configured locker — exactly the semantics an auto-apply-off refusal needs. *`bot migrate`, not `cmd/migrate`:* one binary, one image, one place for the import gate to look, and the infrastructure pass gets an argv rather than a second artefact. It deliberately registers **no** signals — a registration with no reader does not delay a signal, it swallows it, and dying inside the lock wait costs nothing here because every migration runs in a transaction and the session lock dies with the connection. *Consequence:* readiness never re-asks whether migrations are pending — after the step the answer is established by construction, so the step latches it and readiness costs one pool round trip. *Source:* the composition-root design § *Migration policy* / § *The migrate-only entry point*, issue #24. *Decided:* 2026-09-10.

**KD-35 — Restart hygiene lives in `internal/scheduler`, and its whole decision is computed in SQL under a row lock.** The shift writes `scheduled_task.run_at`, and that table's package is its sole authority, so `Liveness` was added there rather than in `cmd/bot`: `AbsorbDowntime` is one transaction whose first statement is a `SELECT … FOR NO KEY UPDATE` on a NULL-seeded guarded singleton, `process_liveness`, returning both the stored instant and `now() - seen_at`; past the threshold it moves every overdue pending row by that same scanned interval, never a recomputed one. *Why SQL:* the package's standing rule is that every persisted instant comes from the database, and here it is also the acceptance condition — a process whose own clock disagrees with the database's must measure the same gap and move the same rows, which a `time.Now` anywhere on the path would break. The liveness source calls none of `time.Now`/`time.Since`/`time.Until`, held by a whole-file guard. *Why a row lock and not an advisory one:* atomicity is not mutual exclusion — under READ COMMITTED two concurrent starters would each see the pre-shift instant and each shift, doubling the move; `FOR NO KEY UPDATE` — the same mode the transaction's own non-key `UPDATE process_liveness SET seen_at = now()` already takes, and it conflicts with itself per PostgreSQL's locking table — makes the loser wait and then re-read what the winner wrote, a property `TestAbsorbDowntime_LockBlocksConcurrentSelect` proves directly (it drives two transactions by hand and asserts the second's locking `SELECT` has not returned while the first still holds the lock) rather than one asserted from the manual; `TestAbsorbDowntime_TwoConcurrentCallsShiftOnce`'s end-to-end goroutine pair does not overlap at the database and so cannot prove it, establishing only that the end-to-end path run twice leaves the row moved once. An advisory lock is database-wide while this table is per-schema, which would serialise unrelated schemas' fixtures on the shared test server. *Bounded tolerance rather than infinite:* a failing heartbeat is tolerated for `ceil(threshold / interval)` consecutive failures and then the runner returns, because a stale instant makes the *next* start shift rows for downtime that never happened — and a database this process cannot write to for that long could not have claimed a task or read an offset either. *Telemetry:* the measured gap and the shifted-row count are gauges; the shift moves no balance, so it declares no posting signature. *Source:* the composition-root design § *Restart hygiene*, issue #24. *Decided:* 2026-09-10.

## World generation (2026-09-13)

**KD-37 — The world's content is a keyed hash chain under one domain tag, every generation pass reads a stream of its own, and a chunk map carries a generation version that is not that tag.** `worldKey = SHA-256(domainTag ‖ seed)` with `domainTag = "lab-game/maze/v1"` and the seed written as a fixed-width big-endian `int64`; every later digest folds that root with a one-byte **purpose** — cell, island, algorithm draw, spanning structure, extra passages, border — and then the fixed-width big-endian `int32` coordinates the purpose is about. A cell's own seed is the first eight bytes of its digest read big-endian; a border's digest folds the two chunk coordinates in canonical `(Q, R)` order, so both sides of a border compute the same key from their own call site without consulting each other. Each digest keys a ChaCha8 stream from `math/rand/v2`, reached through an unexported one-method interface whose sole constructor is this package's only reference to that module — so a struct field typed with the concrete type would be a second reference and the guard would say so. *Why the purpose byte:* a pass whose own draw count changes must never shift another pass's values; without domain separation, adding one draw to island selection would silently re-mint every chunk's corridors. *Why big-endian fixed-width and no floating point anywhere:* the encoding is **specified rather than inherited from the host**, which is what makes the derived bytes a function of the inputs alone and therefore what lets a golden pin them at all; for the same reason the reductions are integer-only (the bounded draw rejects above the limit instead of taking a modulo, and is **total** — a bound of one or zero returns zero and consumes nothing) and every share is `decimal.Decimal`. That the bytes then come out identical on a 32-bit build and a 64-bit one is an incidental consequence of that, not the reason for it — the owner ruled that the game targets linux amd64 for now and that the architecture half of this task's criterion goes entirely, so these mechanisms stay while nothing gates that axis: the amendment removed a gate, not a property. *One fact about the primitive, checked rather than assumed:* its stability **is** gated upstream — `math/rand/v2`'s own test suite carries a golden commented to make sure the algorithm never changes, which `go doc` cannot see and which an early draft of this design wrongly recorded as absent. *Why the generation version is not the tag:* the tag versions the key encoding, and the per-cell seed hangs off it. The generation version is `maze.Version`, an exported `int32` that starts at 1, and every `Map` that `Generate` returns carries it. If the tag moved with every generation change, each bump would also re-roll the per-cell seed, and with it the content of every chunk already stored for whatever layer samples its content from that seed. The per-cell seed depends on the world seed and the coordinate alone, never on `Version`. *Consequences:* any change to what a chunk generates is a `Version` bump. That covers the key chain, a stream, a reduction, the canonical local order, the border enumeration order, the island rule or the gate exclusion, an algorithm's traversal order, the cycle pass, the portal count or placement, and stored-border precedence. A bump does not re-mint a world. A map keeps the version it was built under, and `NewMap` rebuilds a stored map under whatever version it names. `Generate` takes a shared border from a supplied neighbour map whatever version that map names. So a chunk generated after a bump still meets its older neighbours at their stored borders; storing the maps is `internal/world`'s, and it stores each one with the version it was built under (KD-46). Changing the key chain the per-cell seed hangs off (the tag, the byte encoding or the digest) goes further, because it also moves that seed and re-rolls content sampled from it on every chunk already stored. That is a **season rotation, never a refactor**. The two goldens make both kinds of change visible in a diff. `chunks.golden` names `Version` in its header, and its mismatch message names `Version` as the thing to bump. `derive.golden` pins the key chain itself. *Amended by #119:* the generation version is new. The shipped core had none, so this entry said that any generation change re-mints every world under a seed. With a chunk's map stored beside the version that built it, only a change to the key chain behind the per-cell seed still does that. *Source:* the world-generation design § *Determinism* / § *Test Design*, issue #27; the generation version from the hexagonal-chunk design D10, issue #119. *Decided:* 2026-09-13. *Amended:* 2026-09-14.

**KD-39 — Connectivity is built, never repaired: guarded islands inside a chunk, and a bounded count of non-touching portals on every border.** Inside a chunk the drawn algorithm builds a spanning structure over the **non-island induced subgraph**, so every non-island cell is reachable from every other by construction. Island candidates are the chunk's **non-border** cells only, the cells within `R−1` of its centre. In a gate chunk the centre is not a candidate either, so the gate cell is reachable by construction. The candidates are shuffled from the island stream. Each is taken tentatively and kept only if the remaining non-island cells are still connected over the **chunk-induced** subgraph: interior adjacency alone, so no neighbouring chunk may reconnect a pocket this chunk enclosed. Between two chunks the border is the `2R+1` faces `hexgrid` enumerates in path order. Its guaranteed passages are drawn from the key of the canonically ordered chunk pair. The count falls within `[⌈lower × (2R+1)⌉, ⌈upper × (2R+1)⌉]`. The shuffle-and-rank bijection places the portals at pairwise non-consecutive positions along the path, exactly and uniformly, with no rejection loop. So no two portals of one border share a vertex, and that includes two faces of one cell. The candidate list is enumerated from the lesser chunk's side, so both sides derive the identical faces. The rule stops at a three-chunk corner. A border therefore depends on the world seed, the generation inputs and its two chunks alone, and on neither chunk's type nor any third chunk. When `Generate` is given a neighbour's map, the border with that neighbour is taken from the map face by face instead. That map may be a stored one rebuilt through `NewMap`, and its faces are taken even where they differ from what the seed would derive. The extra-passage pass draws only from still-closed **interior** faces whose endpoints are both non-island, so it structurally cannot open a border face. *Why no repair stage:* `~/lab-private/DESIGN.md` §2.2.2 rejects post-materialisation repair outright — a repair depends on the order in which the world was explored, and the world stops being a pure function of the seed. *Consequences:* the induction is chunk-connected plus neighbour-connected, hence world-connected. Locality is preserved: one chunk's own keys and type, plus, for each border, a supplied neighbour map or the pair's border key. `New` refuses a lower portal share that rounds to no portal, because a border with none breaks the induction. It also refuses an upper share that rounds past `R+1`, the most non-touching positions a border path holds. A border taken from a stored map carries whatever the version that built it guaranteed. `NewMap` re-checks no portal count and no connectivity, so across a stored border the induction holds only as far as that version's own rule does. A guard test asserts the lattice-connectivity helper is reached from island selection and from nowhere else in the package's non-test files, so no second connectivity check exists downstream of the structure build for a repair to hide in; and the achieved island count may fall **short** of its target where the guard keeps rejecting candidates, which is why the tolerance is asserted against the achieved share and the failure message reports the achieved value. *Amended by #119:* on the rhombic chunks this replaced, every border carried one or two portals. The bounded count, the non-touching rule, the gate-centre exclusion and the border taken from a neighbour's map all arrived with the hexagonal rework. *Source:* the world-generation design § *The per-chunk construction* / § *Test Design*, issue #27; the corpus rule in `~/lab-private/DESIGN.md` §2.2.2; the hexagonal-chunk design D5–D7 and D9, issue #119. *Decided:* 2026-09-13. *Amended:* 2026-09-14.

**KD-40 — Four shares over three denominators, a bias that is no share, and two rounding rules, written down because they look like one number.** The **island share** multiplies the chunk's **total** cell count, `3R² + 3R + 1`. Its *capacity* is a different number: the count of candidate cells. `New` checks the rounded target against the **gate** chunk's capacity, `3R² − 3R` (the non-border cells less the centre). That is the smaller of the two types' capacities, so an input valid once is valid for every chunk type instead of failing per call at generation time. At the lowest radius `New` accepts, that capacity is already 90 cells. So the core carries no separate refusal of a positive share at a shape with no candidate cell: the rhombic core needed one, and #119 removed it, because no radius `New` accepts has such a shape. The **extra-passage share** multiplies `nonIslandCells − 1`, the spanning structure's own edge count — "10–20% additional passages" is a share of the tree's edges, not of the chunk's faces. The two **portal shares**, lower and upper, multiply the border's length, `2R + 1` faces, and bound the count range a border draws from. `New` refuses a lower share above the upper one, a lower share that rounds to no portal, and an upper share that rounds past `R + 1`. The **growing-tree bias** is not a share at all: it is a threshold in `[0,1]` between the algorithm's two extremes. The **radius** has a lower bound, `maze.MinRadius` (6), which `New` and the balance loader both read. It has no upper bound. The radius is the owner's configuration value, and at a radius near the limits of the types a chunk exhausts memory long before any coordinate arithmetic overflows, so the core neither refuses such a radius nor adds code for it. *Why it is a decision and not an implementation detail:* each share is an operator-facing balance number that configuration supplies, and a reader who assumes one denominator for all of them mis-tunes most of them. *Consequences:* every share and the bias are `decimal.Decimal` and never a float. Two rounding rules are pinned, each in a single helper. The island and extra-passage targets use `floor(x + ½)`. Both portal bounds use the ceiling, because the design corpus rounds a portal count up. A float-valued `decimal` accessor is one of the three bans the determinism guard carries, precisely because a float arriving as a *method result* walks past a guard that can only see the type names. Every share and the bias is validated to `[0,1]` by name, so a rejection says which input was wrong. *Amended by #119:* the island share's denominator was the rhombic chunk's columns × rows. Neither portal share nor the radius bound was an input. The rounding stopped being a single helper when the portal bounds arrived. *Amended by #28 — who supplies these numbers moved, and not one of them changed.* The radius, the four shares and the growing-tree bias stopped being balance numbers and became a world's own authored generation inputs, so the sentence "which `New` and the balance loader both read" is **falsified**: the bound is read by `New` and by the **world** loader. Each share and the bias is still validated to `[0,1]` by name, now in the world schema, before `New` folds the cross-field rules over them; the radius binds through an `int32` destination there, so the decoder itself refuses a value the type cannot hold. Every denominator, both rounding rules, each refusal and the no-upper-bound ruling above are untouched — a reader who takes this entry for the arithmetic still gets the right answer, and only the phrase naming the reader was wrong. *Source:* the world-generation design § *The per-chunk construction* / § *API sketch*, issue #27; the hexagonal-chunk design D6, D7 and D12, issue #119. *Decided:* 2026-09-13. *Amended:* 2026-09-16.

## Gate placement (2026-09-14)

**KD-41 — Gate placement and the nearest-gate depth are one package, `internal/gate`, over `hexgrid` alone. The spiral's orientation is world identity, and depth is an exact ring search whose stop rule bounds its work.** `internal/gate` holds three pure functions over the chunk super-lattice: the spiral order (`Spiral`, `SpiralIndex`), the next gate (`Next`), and the nearest-gate depth (`NewSet` builds a `Set`, and `Set.Depth` answers it). Its non-test imports are `internal/hexgrid` and the standard library, and it applies `detguard` from its own `guards_test.go`. No import-allowlist guard holds that set, unlike `maze`'s. *Why a package of its own:* not `hexgrid`, which KD-38 keeps the topology vocabulary, while the spiral's start and turn are a placement decision. Not `maze`, because a depth consumer such as the monster budget would then pull the generator into its graph for a distance.

*The spiral, in lattice terms, because the lattice statement is the binding one.* Index 0 is the centre chunk `(0, 0)`. Ring `n ≥ 1` holds the chunks at `ChunkDistance` `n` from the centre and follows ring `n−1` whole. **Starting direction: `hexgrid.DirE`.** Ring `n`'s reference corner is `(n, 0)`, `n` steps in `DirE`. **Turn: the canonical `Direction` order.** The corners are reached `DirE → DirNE → DirNW → DirW → DirSW → DirSE`, and the side from the corner in `d` to the corner in `d+1` is walked in direction `d+2 (mod 6)`. Under the compass sense the names carry, that is counter-clockwise. **Start: mid-side, rounding down.** Ring `n`'s first chunk is `⌊n/2⌋` steps from `(n, 0)` in `DirNW`, which is `(n, −⌊n/2⌋)`. That start is the owner's decision, not a consequence of how densely gates pack. Ring `n` begins at index `1 + 3n(n−1)`. `SpiralIndex` recovers a chunk's side and step from its coordinates in integers alone, a derivation independent of the walk, and `TestSpiralIndex_AgreesWithSpiral` holds the two equal. There is no index-to-chunk inverse: the ring of an index needs a square root, and `detguard` bans `math` on this path. One unexported ring walk serves `Spiral`, `Next` and `Depth`.

*Why the orientation is a data contract.* #29 stores gate chunks and their spiral indices, and its chunk-created event carries the index, so the orientation is live data (`AGENTS.md` § API Stability carve-out) — a standing fact now rather than the condition this sentence once stated. A change to the start direction, the turn or the ring start re-places every later gate and renumbers every stored index. That is a data migration, never a refactor. `TestSpiral_RingWalkTable` lists rings 1 to 3 in full, so any such change shows in a diff.

*The next gate.* `k` is the minimum gate spacing, the gate chunks themselves not counted: any two gate chunks lie at `ChunkDistance` of at least `k+1`. A negative `k` returns `ErrNegativeK` with the zero chunk, which is not an answer. The zero chunk is also the centre, so the error alone carries the refusal. Otherwise let `M` be the largest ring of any chunk in `created` or `gates`. `Next` scans rings `0` to `M+k` in spiral order for the first chunk that is not created and keeps `k+1` from every gate. If none qualifies, it returns ring `M+k+1`'s first chunk. That fallback is valid by construction: it lies beyond every created chunk, and by the triangle inequality it is at least `k+1` from every gate. So `Next` is total with no unbounded loop, and `TestNext_MatchesSpiralScan` holds the bounded scan equal to an unbounded scan of `Spiral()`. The inputs are slices, not sets, because `M` needs every chunk and `detguard` refuses a range over a map. The gate check is therefore linear in the gate count, which placement at once per chat per world affords. `Next` does not bound `k`, and its ring arithmetic makes no promise near the `int32` seam: bounding `k` is the world configuration's call.

*The depth.* `NewSet(lattice, gates)` copies the gate chunks into a hash set once per gate snapshot. Building it is not part of a query, and a caller that rebuilds it per cell pays the gate count per cell. `Set.Depth(cell)` returns the hex-formula cell distance from `cell` to the centre cell of the nearest gate chunk, never a path length through passages. It walks rings `s = 0, 1, 2, …` around the cell's chunk and looks each ring's chunks up in the set. It stops once a gate has been found and the best distance is at most `L(s) = ⌈s·C/(2R+1)⌉ − R`, with `C = 3R²+3R+1`. **Why `L` is a lower bound:** the map from super-lattice vectors to cell vectors commutes with rotation, so the hex norm's minimum over the super-lattice's unit hexagon is `C/(2R+1)` on every edge. Two chunk centres at super distance `s` are therefore at least `⌈s·C/(2R+1)⌉` cells apart, and a cell lies within `R` of its own chunk's centre. The bound is attained, not loose: the chunk `(2R+1, −(R+1))` has its centre exactly `C` cells from the origin chunk's. `TestLowerBound_HoldsAndIsAttained` checks both halves against brute force. `L` never decreases, so the stop is exact however sparse the gates are, and a nearer gate in a later ring than the first hit is still found. **The search bound:** the search never looks past super distance `S(cell) = ⌊(depth + R)(2R+1)/C⌋` from the cell's chunk, so gates beyond `S` add no work whatever their number. **That bound rests on the stop-rule proof and on `TestSearch_StaysWithinBound` and `TestSearch_FarGatesAddNoWork`, never on `detguard`.** The guard's map-range check recognises only a composite literal, a `make` call and a bare identifier, so a range over a field such as the `Set`'s own map passes it unreported. The same guard decides map-ness by identifier name per file, which is why that field is named `members` and not after the ranged parameter slice. **Termination:** `Depth` returns `(0, false)` at once when the set holds no gate. That covers a `Set` built from an empty slice and the zero `Set`, whose map is nil, and it matters because the ring search reaches its stop only after a hit. `NewSet` refuses a negative radius with `ErrNegativeRadius`, because `L` then decreases and the search would never stop.

*Consequences:* consumers of depth (the PvP tier, the monster budget, the wave multiplier, newcomer XP) depend on `gate` and `hexgrid` and pull in no generator (KD-38). Where the gate snapshot lives, and whether depth is stored or computed on read, is #29's, along with persisting gates and the chunk-created event. *Amended by #29 — both questions this entry handed on are answered, and neither changes a word of the mechanics above.* The gate snapshot has **no home of its own**: `internal/world`'s `Depth` reads the maze's gate rows and builds a `Set` on every call, so depth is computed on read with no stored column and no invalidation (KD-48). Gates persist as `chunk` rows carrying the chat and the spiral index (KD-46), and the chunk-created event carries the index and the ring (KD-49). So the per-query cost this entry names is the cost the persisted world pays, and the escape hatch it names — hold a `Set` across many cells — is the one that stays open. *Source:* the spiral-gate-placement design D1, D2, D4 and D5, with D6's snapshot note, issue #120; the ring start from the owner's answer recorded in that task's spec; the two answers from the maze-persistence design D7 and D9, issue #29. *Decided:* 2026-09-14. *Amended:* 2026-09-17.

## Posting-signature contract (2026-09-15)

**KD-42 — Posting signatures are declared and checked by `internal/contract`, a package only tests import, and its tests stand on `internal/storetest`, the shared migrated-schema pool the scheduler, ingest and bot suites now take theirs from.** `contract` holds three things: the vocabulary a signature is declared in, the declared set as one Go literal, and the check that reads a real transaction back and compares it. Only tests import it, so `cmd/bot`'s dependency graph carries neither the read-back path nor the pool fixture. *Why its own package:* not `internal/store`, because every mechanic's pull request would then edit the ledger package to declare its signature, and the binary would carry what is test support; not a `_test.go` helper in each package, because every balance-moving mechanic calls the check from its own package, which is past the three-site threshold for a shared package. The name is the design corpus's own word for the check, and `contract.Signature` does not stutter where `signature.Signature` would.

*What a type is.* A `DocumentType` is opaque and comparable, and only its constructors make one: `ManualCorrection()`, a whole-table type; `Event(store.EventType)`; `DeferredTask(code)` and `RecurrentTask(code)`. The two task tables stay separate keys, read from the table the entry references with no merge rule, and task codes are strings because the store's task bases carry them as strings, so `contract` does not import `scheduler`. The zero `DocumentType` is refused. **The player operation has no constructor.** Its table has no type column, and a whole-table signature for it was put out of scope by the owner, so `NewRegistry` refuses a declaration under that basis and `Check` fails every player-operation entry with `ErrNoSignature`. The first mechanic that writes under a player operation introduces a type within that table and adds the constructor in its own pull request.

*What a signature is.* Exactly one of two forms, and the zero `Signature` is neither. `Expect(legs...)` admits exactly its legs, and `NewRegistry` refuses it with none. A posting leg is a scope-definition code, an account-definition code, a kind, a sign and a cardinality; a movement leg is the from and to scope-definition codes and a cardinality; a cardinality is `Exactly(n)` or `AtLeast(n)` with `n ≥ 1`, and a leg that may be absent is simply not declared. Amounts are not in a leg, because they are balance numbers and the comparison is structural; owner identity is not either, so two players' postings to the same account definition match one leg and its cardinality counts them. Kind is declared although the account definition determines it, and `contract` reads no catalog: a leg whose codes or kind disagree with the migrated catalog never matches, so the mechanic's own test fails on it, and the check is its own drift detector. The capacity postings `store.Move` derives for a movement are declared as ordinary postings, because a checker that re-derived them would pass a defect in the derivation by construction. `AnyBalanced()` admits any postings that sum to zero per kind and any movements, and `NewRegistry` accepts it for `ManualCorrection()` alone — so the manual correction's permission loosens no other type, structurally, when the registry is built, with no second guard inside the check. `Registry` has unexported fields and `NewRegistry` as its only constructor, so no caller can loosen a type after it is built. **There is no empty form:** every write path leaves at least one posting, so an empty signature could only ever fail, and its one use — a type no mechanic writes under — left the task with the completeness gate the owner struck. A type therefore has an `Expect` row, an `AnyBalanced` row, or no row, and a forgotten row cannot pass for a declared one.

*What "the transaction" is: every journal entry past a mark.* `NewMark` reads the greatest `journal_entry.id` visible to its handle, and gives the zero mark when none is visible. That case is reachable — neither the migrations nor player creation write a journal entry — and pgx refuses to scan NULL into an integer, so without the fallback an empty journal would fail loudly rather than admit every entry. `(*Registry).Check(ctx, q, mark, want)` refuses a `want` with no row before reading anything; otherwise it runs every read before judging any entry, and judges each entry past the mark by the signature of **its own** type, read from the document, so a mechanic's test is also a check on everything else its operation wrote. It returns one joined error carrying a wrap per class present: `ErrNoDocument` when no entry of type `want` exists, so a mechanic that wrote nothing cannot pass vacuously; `ErrNoSignature` for an entry whose type has no row, including an entry that references none of the basis tables `contract` knows — what a later migration's new arc column produces — so a new basis is refused rather than skipped; and `ErrNonconforming` for any mismatch, including a set that does not sum to zero per kind, which only a write bypassing the write path can produce. The error is joined rather than first-found so a test can assert that a class did *not* fire. **The precondition**, stated in `Check`'s doc comment: no other writer adds journal entries to the schema between `NewMark` and `Check`. One schema per test (KD-20) meets it by construction, and a concurrency test must not reach for `Check`, because a conforming entry another writer commits past the mark can pass a mechanic that wrote nothing. Gaps in identity values are harmless, because the mark is the greatest *visible* id, not a sequence position. *Rejected:* returning the journal-entry id from the write paths — neither returns one, changing both for a test's benefit would still leave a scheduler-run handler's entry out of its test's reach; filtering on `xmin` equal to the current transaction id — a handler runs under a savepoint, and a subtransaction that writes is assigned an id of its own, so which id a row's `xmin` carries is row-header behaviour this decision would have had to prove before any task mechanic could rely on it; judging every entry in the schema — a test's own fixture funding would be judged as the code under test.

*Where signatures live: one slice literal, `declarations` in `internal/contract/declared.go`, built into a registry by `Declared()`.* One element per type; every leg spelled with catalog codes, a named sign and a named cardinality; **each leg on its own line**; no loop, helper or computed leg; and a fixed order — the manual correction, then event types in the event-log migration's declaration order, then deferred-task and recurrent-task types by code. That is what makes a signature change a changed line of its own naming the account, kind, sign or cardinality that moved; a signature written on one line would show the whole signature changed when one sign moved. One registry rather than one per mechanic package, because `Check` judges every entry past the mark by its own type, so the registry a test passes must hold every type the operation writes under, and the manual correction's row then exists once. *Rejected:* a YAML or JSON file — a loader and parser this project would own, values type-checked only at load, and a diff no more readable than a formatted literal; a SQL table seeded by migration — a signature is a test contract, not live data, and a forward-only migration would turn every signature edit into an INSERT/DELETE delta and put a test-only fact in the production schema. The merged set holds the manual correction's `AnyBalanced()` row alone: no production code writes under any type yet, and each mechanic's row ships with that mechanic.

*The pool fixture.* `storetest.Pool(tb)` is the migrated-schema pool helper — a fresh schema from `testdb.Schema`, a pool from `store.NewPool` closed on the test's cleanup, `store.Migrate` with a discarding logger — as an ordinary package imported only by tests, with its own database-backed test. Before this decision the helper already existed as a copy in four packages, so `contract` holding a fifth was refused as the per-site duplication the three-site rule forbids. **On the owner's word, the scheduler, ingest and bot suites were moved onto it**, every call site included and no delegating name kept: `newScheduler`, `newIngestPool` and `newBotPool` are deleted. **The store package's own copies stay, and that split is forced, not chosen:** the store's tests are in `package store`, and a test in that package cannot import a package that imports `store`; `Pool` could not live in `internal/testdb` for the same reason, since `testdb` would then import `store`. A change to how a test pool is built therefore lands in both `storetest` and the store package's own helpers.

*Consequences:* a balance-moving mechanic follows [`domain-invariants.md`](domain-invariants.md) § 5 — its row in `declared.go`, its contract test calling `Check`, each in its own pull request; nothing requires every type to have a row or every mechanic to call `Check`, by the owner's narrowing of the task, so the review checklists rate a balance-moving mechanic without a signature or a contract test `major`; and the two new database-backed test binaries raised `testdb.Binaries`, which is KD-20's #26 amendment. *Source:* the posting-signature contract-test design D1–D3, D6, D8, D13 and D14, issue #26; the pool move from the owner's answers recorded as rounds 5 and 6 of that task's interview state. *Decided:* 2026-09-15.

The Go mirror grows in the same change, and `TestEnums_mirror_database` is the gate holding the two equal in both directions. *Why enum members* rather than world-configuration content or items of the item machine: the owner's decision, and it carries a standing cost worth naming rather than discovering — an enum member is **permanent after merge**, so a world authored later introduces a resource only with a migration of its own, and a kind named wrongly is corrected by a new member plus a dead one, never by an edit. *Why these three tokens:* they are the promoted sketch's own materials — spun sugar from the cotton-candy clouds, fleece from its fluffy fauna, glitter from its dangerous encounters — so the biome's specialisation reads as this world's, which is what makes a biome recognisable and what motivates walking into another one. *Why a test and not a start-up check:* the world set is **tracked in this repository**, so the agreement is a repository fact a gate holds, exactly as the tracked balance file's own agreement is; `internal/store` exports its ledger-kind member list through `Kinds()`, and a test beside the world loader holds every resource kind the tracked set names inside that list, importing `internal/store` from a `_test.go` file only so the production package keeps its storage-free dependency graph (KD-43). *Rejected:* a composition-root start-up check — it would police an operator input that does not exist in the shipped operating model; *trigger to revisit:* an operator-authored world set. *Rejected:* re-listing the members in the test — that is precisely the drift the mirror test exists to prevent. *Consequences:* the addition cannot break the lint gate, because every `switch` over a ledger kind in the tree carries a `default` and `exhaustive` is configured with `default-signifies-exhaustive`, and a new switch written later carries one too; and the design corpus records the three kinds beside the world they belong to, so a later author meets them where the world is described rather than inside a migration. *Source:* the world-and-biome-config design D8 and D9, issue #28; the token triple approved by the owner in that task's round 3. *Decided:* 2026-09-16.

## Maze persistence (2026-09-17)

**KD-46 — The persisted world is its own package over one forward migration, and a stored chunk map is one byte per cell whose layout is live data.** `internal/world` holds the persistence: it imports `internal/hexgrid`, `internal/maze`, `internal/gate`, `internal/store`, pgx and the standard library, and nothing in the module imports it yet — `cmd/bot` wires it when a mechanic calls it. Not `internal/maze`, which is the generator and whose graph a persistence consumer must not inherit (KD-38's reason for splitting topology from generation applies again); not `internal/store`, whose package comment scopes it to the ledger, the item machine and the event log. The migration takes the next free number in `internal/store/migrations`, the only directory `Migrate` embeds.

*The schema.* `maze` carries a biome, a world seed and a season under `UNIQUE (biome, season)`, which makes "the maze of this biome this season" a lookup and a rotation an insert. `chunk` is keyed on `(maze_id, q, r)`, the super-lattice coordinate, and carries the chunk type, the creation cause, the gate's chat, the spiral index, the encoded faces and the generation version. Both enum columns are `NOT NULL`, and that is load-bearing rather than tidy: the `CHECK` tying the gate fields together compares the chunk type against `'gate'`, and a NULL there would make the comparison NULL and the whole constraint pass. A chat's gate is unique per maze through a partial unique index; the gate chat's foreign key is covered by a **separate** standalone partial index, because the migration test compares a foreign key's columns against an index's **leading** columns and the unique one leads with the maze. `node_discovery` is keyed on the **cell** coordinate plus the player and carries no chat column at all — a discovery is never a chat's. Coordinates are `integer` because the topology package's own coordinate fields are `int32`, and the spiral index is wider because the placement package returns an `int64`. Singular names, identity columns and an index over every referencing-side foreign key follow the ledger core (KD-17). **A cell table was never on the table:** cells are not stored row by row (`~/lab-private/DESIGN.md` §2.2.4), and every kind of per-cell state is deferred to the mechanic that writes it.

*The blob.* A stored map is `bytea`: one byte per cell in the lattice's own local-cell order, bit *d* set iff face *d* is a passage, with both remaining bits zero and a set one refused by name. The blob's length must equal the maze's own lattice cell count, and a disagreement is `ErrRadiusMismatch` naming both — which is what catches a world file whose generation radius was edited after chunks were stored. Decode hands the faces to `maze.NewMap`, so the interior-agreement and face-state refusals stay the generator's. **The byte layout is live data from the first merged chunk** (`AGENTS.md` § API Stability carve-out): a change to the cell order, the bit order or the high-bit rule misreads every stored map in every database, so it is a forward migration that rewrites every blob, never an edit. The golden that pins it is specified in the design rather than only in the test, so it is reproducible, and a diff in it is what such a change looks like. *Rejected:* JSONB and `smallint[]` — both cost several times the bytes, and neither makes a byte-for-byte golden meaningful.

*The generation version travels with the map, never with the maze.* A read rebuilds the map under the **stored** version, not the current constant; nothing regenerates and nothing back-fills, so a maze holding chunks of several versions is the designed state. A new chunk beside an old one still agrees on their shared border, because generation reads the neighbour's stored faces rather than re-deriving them and that path is version-blind (KD-37). The migration is forward-only, so rolling the binary back leaves the tables in place and unread, and rolling forward again finds them. *Rejected by the corpus rather than by this decision:* regenerating on read — the chunk map is stored together with its generation version and is not generated again (`~/lab-private/DESIGN.md` §2.2.2). *Rejected:* storing the chunk radius on the maze row as a stronger form of the length check — it adds a column no acceptance criterion asks for, and the length check catches the same drift at the first read.

*The enum vocabulary is this package's own.* `world.ChunkType` and `world.CreationCause` mirror the two database enums as string types, with a total mapping to and from the generator's own chunk type that refuses a value it does not know. The mapping exists rather than reusing that type's `String`, because `String` renders for logging and test failure messages and a stored value must not move when a rendering does. The mirror test is this package's own, following `scheduled_task_state`'s precedent of an enum with no mirror in the ledger package — with the mirror added, which that enum never had. The `exhaustive` linter treats a `default` branch as exhaustive, so it would not force the mapping to be total; a table driving every exported member is what holds it.

*Two inputs the handle refuses rather than guesses.* `Open` inserts the maze row on conflict-do-nothing, reads it back, and returns `ErrSeedMismatch` naming both seeds when the stored one disagrees with the requested one: every stored chunk was generated under the row's seed, so silently adopting a new one would leave a world whose stored maps and whose freshly generated ones belong to different worlds. `Spec.Season` is a plain parameter with no default and no configuration key, on the owner's ruling — whoever creates the maze supplies it, and a season key lands with whatever task ships rotation, which is outside the MVP.

*And the discovery's guard is structural where the gate's is not, which is KD-17's scoping rather than an oversight.* `RecordDiscovery` runs on the **caller's own** transaction, so a discovery rolls back with the move edge that produced it — the opposite of a chunk creation, and for the opposite reason. Its insert selects from `owner` filtered on the player kind and takes conflict-do-nothing, so a non-player row is unwritable and a repeat keeps its first discovery instant. Zero rows affected is ambiguous between "no such player" and "already discovered", so **that branch alone** reads the owner's kind and returns `ErrNotAPlayer` from that read's own result rather than guessing from rows affected; a first discovery and an ordinary repeat both stay one statement. *Rejected:* a composite kind-pinned foreign key, the item machine's construction — KD-17's amendment scopes that to where the guard **is** the mechanic, and a gate's chat and a discovery's player never move. *Rejected:* one statement for both answers — an upsert-and-return would distinguish them in one round trip at the price of writing a row version on every repeat, turning the common re-enter-a-known-cell case from a no-write into a write on a raid's hot path to save a read on the branch that writes nothing; a single-round-trip CTE keeps both properties and is the shape to reach for if that second read ever shows up in a profile. *No foreign key from `node_discovery` to `chunk`:* "you can only discover a cell you reached" is the raid edge's invariant, and a derived chunk coordinate would need the lattice radius, which is configuration and unavailable to a generated column.

*Source:* the maze-persistence design D1, D2, D3, D4, D10, D11 and D12, issue #29; the season settled by the owner in that task's round 1. *Decided:* 2026-09-17.

**KD-47 — Chunk creation is a short transaction of its own at explicitly pinned READ COMMITTED whose one explicit lock is the maze row's; a read takes no lock at all; and the whole call carries a budget.** The statement order is the corpus's own: lock the maze row `FOR NO KEY UPDATE`, re-read the chunk row, read the existing neighbours' stored maps, generate, insert the chunk, append the event, commit.

**The lock-ordering rule, which #36 must obey: a chunk-creation transaction takes no explicit row lock other than the maze row's, and a raid-session transaction never takes the maze row lock — so the maze row is the only lock #36 has to order against.** The word *explicit* is load-bearing: the transaction still takes the implicit key-share locks its foreign keys imply on the `owner` rows its event and its gate column reference, and the rule stays true the day someone locks an owner row deliberately. With one explicit lock on one side and none on the other there is no cycle to order, so a chunk created during a raid cannot deadlock against the session row lock whichever order the two are taken in — which is why the rule lives in [`domain-invariants.md`](domain-invariants.md) and not only in a doc comment: #36 is a different pull request. Today the "none on the other" half is a fact about the whole module rather than about #36's plan alone: the explicit row locks in non-test Go source are `internal/scheduler`'s, on `scheduled_task` and `process_liveness`, together with `internal/world`'s on `maze` — and none of them is on `owner`, which is the row both kind checks below read.

*Why the isolation level is passed explicitly* through the transaction options rather than inherited from a server setting: two properties rest on it. In READ COMMITTED each command starts with a new snapshot including everything committed up to that instant, so the loser of a lock race re-reads the chunk row **after** the winner commits, finds it present and writes nothing. Under REPEATABLE READ the same wait ends in a serialization failure instead.

*A read is unlocked, and only a genuine miss pays the lock.* That rests on one invariant the package **owes** rather than one the tree enforces: a `chunk` row is never updated after insert, so a row reads the same locked or unlocked. **No gate holds it**, deliberately — the package's own suite updates a stored blob on purpose, precisely to prove that a read does not regenerate, so an invariant stated over the whole package would contradict its own test plan. It is review-judged, exactly like the premise the gate allocation's pre-lock kind check rests on: nothing in this module ever updates an owner's kind, and the day a mechanic does, that guard must move into the insert — the shape the discovery insert already uses — or into a composite key. Without the fast path every step of a raid would queue behind the maze row lock, which is the hot path of the whole game; with it, a miss happens once per chunk in a world's lifetime.

*Rejected: running the creation on the caller's own transaction.* A chunk created while serving a caller must survive that caller's own rollback, and the corpus asks for a short separate transaction. **The cost of that rejection is a stall rather than an error, so it is designed against rather than noted.** A caller that creates a chunk from inside its own transaction holds two pool connections at once, and enough such callers can reach the state where every holder waits for a connection nobody will release. Three things absorb it, and all three are written down rather than left to be found in production: the designed call order creates a missing chunk *before* the raid transition, so nothing nests on the hot path; the composition root sizes the pool at **at least two connections per concurrent nesting caller**; and `Spec.CreateBudget` — no default, refused when non-positive, this module's standing no-silent-default posture — bounds **the whole call, the unlocked fast-path read included**, so an exhausted pool or a long-held maze row lock surfaces as `ErrCreateBudget` wrapping the deadline error wherever it bites instead of as a hang. **The scope has to be the call and not the transaction**, and that was measured rather than assumed: the fast-path read acquires a connection of its own, so a caller already holding one can be blocked *before* the creation transaction is ever reached, and a budget scoped to the transaction alone would let exactly the stall this decision exists to prevent happen with a bare context error and no named one to read. *The bound is this task's, not #36's:* a package that can hang its caller is not something to hand over with a note.

*Source:* the maze-persistence design D5, D6 and D8, issue #29. *Decided:* 2026-09-17.

**KD-48 — Depth is computed on read, from the maze's gate rows alone, and the gate snapshot has no home of its own.** This answers both questions KD-41 handed here. One statement reads every gate chunk's coordinate in the maze, those coordinates build the placement package's gate set, and that set answers the query. No stored column, no invalidation, and no sentinel of its own: the answer is not-found when the maze holds no gate, matching that package's own contract. The predicate selects on the gate's chat being present rather than on the chunk type, for two reasons that coincide — the `CHECK` makes them the same row set, and the partial unique index on the maze and the gate chat already serves **this query**, so the read needs no index beyond the ones the schema already carries. That is a statement about the depth query alone and never about foreign-key cover, which the standalone index provides (KD-46).

*Why "a crafted door can never be an input" is a property of the input type rather than of a filter.* The metric's input is a set of chunk coordinates read from gate rows, and a crafted door is bound to a **cell** and will live in a table of its own — it is not a chunk row and cannot become one, so there is no filter for a later author to forget. `Depth` takes no parameter carrying a position other than the cell being measured.

*The read interface is this package's own*, a single multi-row query method declared by its consumer, because the ledger's own read-sharing interface carries a single-row query alone. Both a transaction and a pool satisfy it, so a raid transition can read depth inside its own transaction. *Consequence:* the per-query cost KD-41 names is the cost the persisted world pays — the gate set is built fresh on every call — and the escape hatch KD-41 names stays open: export the snapshot read beside the query and let a consumer that answers many cells hold a set of its own. At MVP scale a maze holds one chat's gate and a raid edge asks about one cell, which is what makes the cost affordable rather than tolerated.

*Source:* the maze-persistence design D7, issue #29. *Decided:* 2026-09-17.

**KD-49 — `chunk_created` is one `low_volume` event per created chunk, whatever the cause, appended inside the creation transaction — and it is the first event type any production code in this module emits.** It is registered by the migration in `event_type_definition` and mirrored in the ledger package's catalog, which is the only way an event type can be registered at all. Dimensions: the maze always; the chat from the activating chat or the caller's session chat; the player from the caller's player; depth null, because a chunk is not a cell and the one shipped view that reads an event's depth filters on the death type. Payload: the chunk type and the creation cause as **separate** keys — §13.4 made them separate fields so a later type or a later cause varies independently — the generation version, the chunk coordinate, and, for a gate chunk only, the spiral index and the ring.

**The ring is carried for the event's *reader*, not because the writer could not compute it.** The writer already holds the chunk the placement rule returned and takes the ring straight from it at no cost, while a reader holding only the spiral index has no way back: there is no index-to-chunk inverse (KD-41). A payload key is the only place that asymmetry can be repaired. **The coordinate went beyond the owner's enumerated list, was put to them, and is now theirs**; the reason it was worth asking stands — an event that names no chunk cannot be joined to the row it is about, which is what "one event per created chunk" is for. **The gate-spacing parameter is deliberately not carried**, although the placement issue's body anticipated it: it is a property of the world configuration for the season and is recoverable there. Sharing one transaction with the chunk insert makes "one event for every created chunk" and "the chunk outlives its caller's rollback" the same fact.

**Chunk creation moves no balance**, so it declares no posting signature and adds no row to the declared set `internal/contract` holds (KD-42). That is `AppendEvent`'s own documented no-posting path, and until this event nothing outside a test had taken it — no production code in this module writes a posting yet either, so a mechanic author reading KD-42's "each mechanic ships its own row" meets the first mechanic that correctly ships none.

*Source:* the maze-persistence design D9, issue #29; the payload's coordinate settled by the owner in that task's round 1. *Decided:* 2026-09-17.
