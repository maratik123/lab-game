# Project context — lab-game

## Purpose

A **Telegram bot game** (working title «Лабиринты»): adding the bot to a group chat gives that chat a *home* in a shared, infinite, procedurally generated hex maze. Players issue commands in DM with the bot; the group chat receives only rare, status-worthy notifications. The chat is a collective entity — shared buildings, shared reputation, shared map knowledge.

The canonical, finalized specification is **[`docs/DESIGN.md`](../docs/DESIGN.md)** (Russian) — read it for anything non-obvious about the world, raids, combat, economy, PvP, seasons, or infrastructure. Its idea backlog is **[`docs/IDEAS.md`](../docs/IDEAS.md)**, which is *not* a source of implementable behaviour (`AGENTS.md` § Project carries the AXIOM). This file is the short orientation; the design document is the source of truth.

## The positioning that decides ties

> **The unit of acquisition is a chat, not a player.** When two designs compete, the one that strengthens *chat-as-an-entity* wins (shared map, doors as infrastructure, walking newcomers in, chat legends in notifications) over the one that strengthens an individual.

The mechanics are deliberately conventional (stamina, auto-combat, seasons, an extraction loop) so players understand the rules immediately. What is novel is the combination, not the bricks.

## Load-bearing invariants worth knowing before touching a block

- **The world is generated lazily, a whole chunk at a time.** A hexagonal chunk of radius R is generated when first needed — an explorer crosses into it or looks into one of its cells — and its map is stored with its generation version; its fabric is a pure function of `(world_seed, chunk coordinate, chunk type)`, and every chunk creation runs under a per-world lock in a short transaction of its own. Connectivity is guaranteed *by construction* (per-chunk spanning structure + guaranteed portals on each of a chunk's six borders), never repaired after the fact. Rotation of a season = a new `world_seed` (`docs/DESIGN.md` §2.2.2).
- **Cells are not stored row by row.** Passages and walls live in the stored chunk map, and a new chunk takes its shared border from an existing neighbour's map, so both sides agree; only cell state — a door, a corpse, a respawn timer — gets a row of its own (§2.2.2, §2.2.4).
- **Danger is a property of space, not of the observer.** Depth = the distance in cells, by the hex formula, to the nearest *chat gate* (crafted doors do not count); a chat's gate is placed on a spiral from the world's centre when the chat first raids that world. PvP tier, monster budget, wave multiplier and newcomer XP all hang off that one axis (§2.2).
- **A raid session is a row, not a process.** An explicit FSM in Postgres: player actions and timers are edges of the same kind, every transition is a guarded transaction plus a basis document, and timer edges are one-shot scheduler tasks that die on a stale guard. Bot restarts are invisible to sessions (§3.5).
- **Combat is a pure function** `combat(seed, party, monsters) → outcome + log`. Nothing outside sees its internals; the combat-system version is part of every stored log and PvP-trail snapshot, which is what buys the freedom to rewrite it wholesale (§4).
- **Every balance change is a ledger posting.** Double-entry with a global "World" account, zero-sum per kind inside each transaction, checked at write time in `store.Post` and in `store.Move`, which composes it; instance-carrying items live in a second machine (`item` + append-only `item_movement`) whose holders are addresses in the ledger's own `scope` space. All game logistics — death, looting, contributions, corpse evaporation — are one "move under a document" operation over those machines (§11, and [`domain-invariants.md`](domain-invariants.md)).
- **Lazy ticks, no cron.** Stamina, corpse evaporation and respawn are computed from timestamps at read time; the single exception is the Postgres-backed scheduler that drives raid-session timer edges, notifications and day-close (§11).

## Architecture

The design document defines the blocks; the Go package layout lands one implementation spec at a time, never by assumption. **Layout so far:** `internal/store` — the ledger's write path (owner/scope/account catalog, forward migrations under `internal/store/migrations`, `store.Post`), the item machine that shares its holder address space (`item`, append-only `item_movement` whose chain the database itself keeps continuous, the `slots` / `weight` capacity kinds carried by a `free` / `used` account pair, `store.Move` writing both machines under one basis document, and the reconciliation views over each) and the product event log (the `event` table, its §13.4 type registry, the write API, and the `metric_*` SQL views a product dashboard reads); `internal/testdb` — PostgreSQL provisioning for the whole suite (a `postgres:18` container or `LAB_GAME_TEST_DSN`, one schema per test), exported as an API that `cmd/testpg` imports as well as the `_test.go` files that call `Main` and `Schema`: `make test`, `make test-race` and the coverage ratchet each run their test invocation through that wrapper, so one run shares **one** server instead of starting a container per database-backed test binary, and the per-binary path survives as the fallback a bare `go test ./...` still takes; the long-lived server the wrapper keeps across runs is named for the checkout it runs in, so two checkouts on one host each own one and neither can take the other's down; `internal/repotest` — the module's one repository-root resolver for tests (`Root`, `RootPath`), into which every per-package copy was folded and then deleted; `internal/config` — the start-up configuration layer (the `LAB_GAME_` environment set, the tracked balance YAML, the world-set path), which `cmd/bot` loads and validates before any other work; `internal/tg` — the Bot API transport over `telego`'s low-level layer (the caller with retries and exact `retry_after`, the window-schedule rate limiter, the `Gate` seam `internal/ingest` installs its allowlist into (#22), the observation point `internal/health` reads), with `internal/tgtest` as its in-process fake Bot API server; `internal/scheduler` — the Postgres-backed task scheduler over the `scheduled_task` table (the handler registry with its one-shot and recurrent declarations, the worker's claim/execute/settle cycle and its per-task deadline, the start-up reconciler that seeds and corrects recurrences, the `process_liveness` singleton whose start-up shift absorbs an outage and whose heartbeat keeps the instant fresh, the `Stop` seam that ends a cycle without aborting the work inside it, the handler-boundary recovery that makes a panicking handler one counted attempt under the same failure policy instead of a crashed process, the deadline reclaim that terminates a breached task's own backend so its row is claimable without waiting for the handler to return, and the observation seam `internal/health` reads), which ships no production handler; `internal/backoff` — the one exponential ramp (`Exponential`, `EqualJitter`) that `internal/tg`, `internal/scheduler` and `internal/ingest` all call, both private copies deleted rather than left standing beside it, its growth factor read from each adopter's own configuration over the shared `DefaultFactor` / `ValidFactor` pair rather than compiled into the arithmetic; `internal/panicguard` — the one recovered-panic primitive both handler boundaries call (the type carrying the recovered value together with the stack captured at the recovery point, its constructor from a `recover()` result the caller's own deferred function still has to make, and its `error` rendering, so the caller's usual `%w` wrap carries the stack into whatever it already persists while a log record can carry it as its own attribute), standard library only; `internal/ingest` — update ingestion over the transport (the long-polling loop with its always-transmitted `allowed_updates`, the 26-row update-kind table and the router, the `ingest_offset` row whose guarded advance rides the handler's own transaction, one transaction per attempt with retries and the `ingest_dead_update` give-up row, the unexported `operation_id` grammar a handler cannot forge, the `ALLOWED_CHAT_IDS`-plus-player outbound gate, and the observation seam `internal/health` reads), which registers no route — a production handler and a route alike arrive with their own mechanic; `internal/health` — the health surface (an explicitly-constructed Prometheus registry with no global default registerer, one adapter per consumer-declared observation seam, the pgx pool collector read at scrape time rather than from a cached snapshot, the `/metrics` server with the `/readyz` path beside it, the process-identity collector carrying the build version, the start instant, readiness and the restart gauges, and the two-leg `getMe` canary whose legs each carry their own client and limiter so a probe draws on no production budget), whose alert shapes are fixed in [`alert-contract.md`](alert-contract.md) and whose numbers are not; `internal/srcguard` — the shared source-walk support every structural guard in the module parses its own package's files through, taking the repository root as an argument rather than ascending to it; `internal/leaktest` — the goroutine-leak check every test binary ends with (`Main`, wrapping whatever owned the entry point, and the `Ignore` entry with its stated reason), over `go.uber.org/goleak`, together with the guard that fails the suite when a package with tests does not run it; `internal/gateguard` — the two structural guards over the module's own gates, one keying every bare `go` statement in the module's compiled non-test source by its package directory and enclosing function against a reviewed allow list that states how each launch stops, who waits for it, where its error goes and where its panic goes, the other parsing `.golangci.yml` and asserting its exclusion reach, its exclusion scoping, its enabled linter set and every setting pinned with it — the relative-path mode, both truncation caps and the line dedup. `internal/hexgrid` — the hex topology vocabulary (the axial coordinate and its six directions with `Opposite`, the canonical face a neighbouring pair shares with `FaceOf` computing the same key from either side, the chunk coordinate with its six neighbours on the hexagonal super-lattice, the `Lattice` that maps a cell to its chunk and local coordinate and back and enumerates a chunk's local cells and each border's `2R+1` faces in path order, the cell distance by the hex formula that gameplay formulas read, and the chunk distance on the super-lattice); `internal/maze` — the deterministic generation core (the domain-tagged keyed hash chain, the ChaCha8 stream behind an unexported one-method interface, the in-package draw reductions, the generation inputs with their enum-indexed algorithm weights, the chunk radius's lower bound `MinRadius` and the two portal shares, the chunk cell graph, the chunk type, connectivity-guarded island selection that never takes a gate chunk's centre, the five spanning-structure algorithms drawn per chunk, the extra-passage pass, the portal rule's bounded count of non-touching portals on every border, and the chunk-level entry point `Generate`, whose `Map` carries the generation `Version` and which takes a shared border from any neighbour map it is given, with `NewMap` rebuilding a stored map), which only the balance loader reaches, to check the chunk radius against `MinRadius` — configuration onto its inputs, persistence and node content each arrive with their own issue; `internal/gate` — gate placement and the nearest-gate depth, over `internal/hexgrid` and the standard library alone (`Spiral`, the infinite placement order that starts at the centre chunk and enters each ring mid-side, with `SpiralIndex` its closed-form index; `Next`, the first chunk in that order that is not created and keeps at least `k+1` chunks from every gate, refusing a negative `k`; and `Set.Depth`, the hex-formula cell distance from a cell to the nearest gate chunk's centre, found by a ring search whose lower-bound stop rule keeps gates beyond its bound from adding work), which nothing calls yet — persisting gates, the activation that places them and every depth consumer arrive with their own issues; `internal/detguard` — the determinism predicates a generation-path package applies to its own directory (no clock, no unpinned randomness, no floating-point type, no `math` import, no float-valued decimal member, and no map range it can name — the scan decides map-ness from an identifier's declarations, so its reach is what a name-based pass can see and the goldens are what actually prove the property), composing `internal/srcguard`'s walker and adding no walk of its own. Under `cmd/`: `cmd/bot` is the composition root — it assembles every block above in one written, all-fatal, unwinding order, serves `/metrics` and `/readyz`, applies the migration policy, and drains on a signal ([`process-lifecycle.md`](process-lifecycle.md)) — beside `cmd/testpg`, `cmd/commentrefs` and `cmd/importguard`, the gate that keeps the bot's non-test dependency graph free of the container runtime. The blocks the layout has to house:

| Block | Responsibility | Design ref |
|---|---|---|
| Transport | Bot API client over a self-hosted `telegram-bot-api`, retries, 429/`retry_after`, rate limits, idempotency of updates | §11, §12.2 |
| World | Deterministic chunked generation, stored chunk maps, spiral gate placement, discovery/knowledge | §2.2 |
| Raid | Session FSM, leader screen (one edited message), stamina, standing-timer escalation | §3, §5 |
| Combat | Pure simulator + narrative rendering from the world's vocabulary | §4 |
| Economy | Double-entry ledger (`internal/store`), item machine, logistics addresses, shop/craft | §6, §11 |
| Scheduler | `scheduled_task` worker (`FOR NO KEY UPDATE SKIP LOCKED`), one transaction per task with its effects | §11 |
| Notifications | Outbound queue with a rate limiter; the notification budget is a design obligation | §1, §13.3 |
| Observability | `event` log (product) + Prometheus metrics and canaries (health) | §13 |

- **Gates:** one entry point — `make verify` runs the whole gate list, and CI invokes the same sub-targets, so hook, CI and a local run cannot disagree. Format gate is `golangci-lint fmt -d` (gofumpt included); file size is gated at 1000 / 1500 lines; `make comment-refs` refuses a comment that points outside itself, over `*.go`, `*.sh`, `*.sql`, `*.yml`, `*.yaml`, `.gitignore`, `.env.example`, `Makefile` and `.githooks/**`. `make import-guard` refuses a forbidden module in the non-test dependency graph of a package the rule table names — today, the container runtime in the bot's. Every test binary ends with a goroutine-leak check (`internal/leaktest` over goleak), wired into each package's `TestMain`, and a guard fails the suite when a package with tests does not run it — so every route that runs the tests runs the check. The lint gate also carries the goroutine-ownership shapes a linter can decide — a context stored in a struct or nested in a loop or a function literal, a `defer` inside a loop, a provable nil dereference or impossible nil comparison, and a fresh root context or an unstoppable timer or ticker outside `main` packages and tests — and `internal/gateguard`'s two guards hold the halves it cannot see: every bare `go` statement in compiled non-test source carries a reviewed allow-list row, and the lint configuration's own reach, scoping, enabled set and pinned settings are asserted from the parsed file. The pre-commit hook is a symbolic link to a dispatcher that runs the reference gate over the staged set and then the coverage ratchet. In CI each test gate — the suite, the race gate, the coverage ratchet, the fallback path — runs as its own job rather than as a step of one shared job, so a run costs the slowest of them instead of their sum, and a red gate no longer stops the others from reporting.
