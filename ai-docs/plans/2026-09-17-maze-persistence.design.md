# Design: Maze persistence: mazes, lazy chunk creation, gates, discoveries, depth

**Issue:** #29
**Date:** 2026-09-17

## Approach

Everything this task computes with already exists and is already pure. `internal/maze` builds a chunk whole and hands back a `Map` carrying its chunk, its `ChunkType` and the generation `Version` it was built under, and it takes a shared border from any neighbour `Map` it is given: `Generate(ch hexgrid.Chunk, typ ChunkType, neighbors ...Map) (Map, error)` `[measured 65b17dd:internal/maze/generate.go:45 · Read → that signature; lines 92-103 → "if nm, ok := neighborMaps[neighborChunk]; ok { … passage = nFaces[d.Opposite()] == FacePassage }"]`, with `NewMap(ch, typ, version, faces [][6]FaceState) (Map, error)` rebuilding a stored one and refusing an unknown type, a version below one, a face count that is no hexagon, a face state outside wall and passage, and an interior face whose two cells disagree `[measured 65b17dd:internal/maze/map.go:98-139 · Read → that refusal list]`. `internal/gate` places and measures: `Next(created, gates []hexgrid.Chunk, k int) (hexgrid.Chunk, error)` `[measured 65b17dd:internal/gate/next.go:16 · Read → that signature]`, `SpiralIndex(ch) int64` `[measured 65b17dd:internal/gate/spiral.go:70 · Read → that signature]`, and `NewSet(lattice, gates)` / `Set.Depth(cell) (int64, bool)` `[measured 65b17dd:internal/gate/depth.go:20,37 · Read → those signatures]`. `internal/hexgrid` maps between a cell and its chunk — `Lattice.Locate`, `Lattice.At`, `Lattice.Center`, `Lattice.LocalCells`, `Lattice.CellCount` `[measured 65b17dd:internal/hexgrid/lattice.go:15,21,39,70,82 · Read → those signatures]`. `internal/store` owns the module's only embedded migration directory and the event log's write path — `AppendEvent(ctx, tx, e Event) (EventID, error)`, which writes one event row and no journal entry `[measured 65b17dd:internal/store/event.go:79-94 · Read → "Unlike Post, it creates no journal_entry and moves no balances"]`, over an `Event` whose player, chat, maze and depth dimensions are nullable columns and whose everything-else is `Payload` JSONB `[measured 65b17dd:internal/store/event.go:42-49 · Read → that struct]`.

What is missing is the database between them. This task adds one forward migration and one package, `internal/world` — the block name the architecture table already gives this responsibility `[measured 65b17dd:ai-docs/context.md · grep -n "Deterministic chunked generation" ai-docs/context.md → "| World | Deterministic chunked generation, stored chunk maps, spiral gate placement, discovery/knowledge | §2.2 |"]`. The migration lands in `internal/store/migrations` because that is the directory `store.Migrate` embeds, and a table a non-`store` package owns has migrated there before — `scheduled_task` and its enum are in that directory while every statement reading them is in `internal/scheduler` `[measured 65b17dd:internal/store/migrations/00002_scheduler.sql:2 · grep -n "CREATE TYPE" internal/store/migrations/*.sql → "CREATE TYPE scheduled_task_state AS ENUM ('pending', 'dead');"]` `[measured 65b17dd:internal/scheduler/claim.go:20 · Read → "WHERE state = 'pending' AND run_at <= now()"]`. That precedent decides the Go vocabulary too: `scheduled_task_state` has no mirror in `store/enums.go`, so this task's two new enums are `internal/world`'s own vocabulary and `store/enums.go` does not grow `[measured 65b17dd · grep -rn "'pending'" --include=*.go internal/store/ → only internal/store/migrate_test.go, a test file; the same pattern against internal/scheduler/ matches claim.go, settle.go, liveness.go, reconcile.go and schedule.go, so the empty non-test result is the pattern working]`. The event **type** is the exception in the other direction: the registry and its element-for-element Go mirror belong to the event log, which is `store`'s, so the new row lands in `store/catalog.go` beside the rest `[measured 65b17dd:internal/store/catalog.go:53-58 · Read → "A new type is registered by a forward migration inserting a row — never by adding a constant here alone — and TestCatalog_mirrors_database's element-for-element comparison fails on either side doing so without the other"]`.

**The three questions the spec left to this design are answered as D7, D5 and D9 below**, and each is answered from something already in the tree rather than from taste.

*Depth is computed on read, never stored (D7).* The metric is a cell distance by the hex formula to the nearest gate of any chat `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.4 · `git -C ~/lab-private show 4200ebc:DESIGN.md | grep -o 'Дистанция опасности = до ближайших ворот любого чата; крафтовые двери в ней не участвуют'` → that sentence]`, so there is no per-chunk or per-cell quantity to hold: the answer is a function of the gate set alone, and a maze's gate set is a handful of rows. Storing it would buy nothing and would owe an invalidation sweep over every stored cell on every activation — and AC13 is precisely the statement that a later gate must lower an earlier depth, which a computed read satisfies by construction and a stored column satisfies only if that sweep is correct. `gate.Set` is already built for this shape: KD-41 records that the stop rule bounds the ring search by the distance and the lattice radius rather than by the gate count, and its closing sentence hands this question here — "Where the gate snapshot lives, and whether depth is stored or computed on read, is #29's" `[measured 65b17dd:ai-docs/key-decisions.md · `awk '/KD-41 —/,/KD-42 —/' ai-docs/key-decisions.md` → both sentences]`.

*The per-world lock is a `FOR NO KEY UPDATE` row lock on the maze row, in a short transaction of its own, at an explicitly pinned READ COMMITTED (D5).* The corpus fixes the shape — "любое создание чанка — исследователем и при активации — идет под блокировкой мира в короткой отдельной транзакции: проверка отсутствия, чтение границ уже созданных соседей, генерация, вставка" `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.2 · `git -C ~/lab-private show 4200ebc:DESIGN.md | grep -o 'любое создание чанка[^.]*\.'` → that sentence]` — and leaves the form open. A row lock is chosen over an advisory lock for three reasons that are in the tree. The module already takes exactly this lock mode for exactly this purpose, with the reason written down: `FOR NO KEY UPDATE` is what the transaction's own later write already takes and it conflicts with itself, which is all the mutual exclusion needed `[measured 65b17dd:internal/scheduler/liveness.go:87-91 · Read → "The lock is FOR NO KEY UPDATE, not the stronger FOR UPDATE … PostgreSQL's conflicting-locks table has FOR NO KEY UPDATE conflict with itself, which is all the mutual exclusion this transaction needs"]`, and PostgreSQL's own conflict table agrees `[measured postgresql@18 · https://www.postgresql.org/docs/18/explicit-locking.html → Table 13.3 marks FOR NO KEY UPDATE as conflicting with FOR NO KEY UPDATE]`. An advisory lock is identified by a bare application-defined integer with no relation or schema qualification `[measured postgresql@18 · https://www.postgresql.org/docs/18/functions-admin.html → "All these functions are intended to be used to lock application-defined resources, which can be identified either by a single 64-bit key value or two 32-bit key values"]`, so it would need a module-wide id registry beside the one id already allocated, and this module has already recorded why that is the awkward direction here — the migration lock is opt-in with a caller-supplied id precisely because "the lock is database-wide while this package's own test isolation is schema-wide" `[measured 65b17dd:internal/store/migrate.go:43-54 · Read → that sentence]`. And the row lock doubles as the maze-row existence check, so a chunk creation naming a maze that is not there fails on the lock statement rather than on an insert.

*The event is `chunk_created`, low volume (D9).* The dictionary's own convention is subject-then-past-participle — `bot_added_to_chat`, `player_started`, `raid_started`, `node_entered`, `combat_resolved`, `raid_finished`, `backpack_dropped`, `backpack_looted`, `backpack_expired`, `notification_sent`, `button_clicked`, `bot_kicked` `[measured 65b17dd:internal/store/migrations/00003_event_log.sql:20-36 · Read → that seeded row set]`. Its volume class is `low_volume`: the high-volume pair is the per-message and per-press traffic, and a chunk is created once and never again, so the traffic is bounded by exploration rather than by interaction.

**Nothing is wired into `cmd/bot`.** This task ships the package and its migration; the composition root gains the world handle with its first caller, which is #36's session creation, `move(face)` and look `[measured 65b17dd · `gh issue view 36 --json body` → "the neighbouring chunk created through #29 (its own short transaction) when it does not exist yet"]`. That is the posture `internal/gate` shipped under, and the architecture page already describes it that way `[measured 65b17dd:ai-docs/context.md · grep -n "which nothing calls yet" ai-docs/context.md → "which nothing calls yet — persisting gates, the activation that places them and every depth consumer arrive with their own issues"]`. #36 also owns the `node_entered` event; what this task owes it is the depth value that event carries, which D7 delivers.

| D3 | **A stored map is `bytea`: one byte per cell in the lattice's `LocalCells` order, bit *d* set iff face *d* is a passage; the two high bits are zero and a set one is refused.** The blob's length must equal the maze's own `Lattice.CellCount()`; a disagreement is `ErrRadiusMismatch` naming both. Decode hands the faces to `maze.NewMap`, so the interior-agreement and face-state refusals stay the generator's. **This byte layout is a data contract** (`AGENTS.md` § API Stability carve-out): changing it is a forward migration that rewrites every stored blob, never an edit. **The golden that pins the layout is specified here rather than only in the test, so it is reproducible from the design:** radius `maze.MinRadius`, and a face set built by the rule *a face is a passage iff the sum of `hexgrid.FaceOf(localCell, d).Cell.Q`, its `.Cell.R` and its `.Dir`'s ordinal is even*. | The bit order is `hexgrid`'s canonical `Direction` order, which that package pins as the order every enum-indexed value relies on `[measured 65b17dd:internal/hexgrid/coord.go:10-24 · Read → "the six values are in the canonical order this package fixes"]`; the cell order is `LocalCells`'s documented one `[measured 65b17dd:internal/hexgrid/lattice.go:79-81 · Read → "in canonical order: rows r = −R..R, q ascending within each row"]`. The high-bit rule turns a truncated or foreign blob into a named refusal instead of a plausible map. The length check is what catches a world file whose `generation.radius` was edited after chunks were stored. **JSONB and `smallint[]` rejected:** both cost several times the bytes and neither makes a byte-for-byte golden meaningful. **The golden's rule is stated over the *canonical* face for a reason**: `hexgrid.FaceOf` returns one identical value from either side of a neighbouring pair `[measured 0eb6105:internal/hexgrid/face.go:13-16 · Read → "so FaceOf called from either side of a neighbouring pair returns one identical value"]`, which is exactly what makes the fixture satisfy `maze.NewMap`'s interior-agreement check by construction — an arbitrary per-cell rule would not, and an all-passage fixture would pin neither the cell order nor the bit order, every byte being the same. The radius is `MinRadius` so the golden stays small and matches the § Test Design fixture helper. **Regenerating on read rejected by the corpus, not by this design** — "Карта чанка хранится вместе с версией генерации и заново не генерируется" `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.2 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o 'Карта чанка хранится[^;]*;'` → that phrase]`. |
| D4 | **The generation version is stored per chunk and read back with the map; a maze holding chunks of several versions is the designed state.** A read returns `maze.NewMap(ch, storedType, storedVersion, decodedFaces)` — the stored version, not the current constant. Nothing regenerates and nothing back-fills. **Deploy window and rollback:** the migration is forward-only, so rolling the binary back leaves the tables in place and unread, and rolling forward again finds them. | `maze.Version` is the constant a generation change bumps, and a stored map's own version "travels with it and never changes on its own" `[measured 65b17dd:internal/maze/map.go:9-14 · Read → that sentence and `const Version int32 = 1`]`. A new chunk beside an old one still agrees on their shared border, because `Generate` reads the neighbour's stored faces rather than re-deriving them, and that branch is version-blind (the `neighborMaps` branch cited in § Approach). **Why that read is load-bearing at all, since agreement holds without it today:** the generator derives a border from the two chunk coordinates in canonical order, so both sides compute the identical portal set from their own call site `[measured c4b9416:internal/maze/seed.go:112-119 · Read → "It is a function of the world key and the two chunk coordinates in canonical order alone — computing it from either chunk's own call site yields the identical key"]` `[measured c4b9416:internal/maze/portal.go:12-20 · Read → "Computing it from either chunk's own call site yields the identical list, since the lesser/greater choice does not depend on which one calls"]`. Symmetry therefore delivers agreement for exactly as long as a stored map is still what today's generator would derive — and the read is what holds it **on the day those two differ**, which is the mixed-version maze this row calls the designed state and which the per-chunk version column exists for. No case that compares a stored map against a fresh derivation can reach that property; § Test Design's neighbour-read case is what does. Forward-only is this package's stated posture — "forward-only (no -- +goose Down section exists in this package)" `[measured 65b17dd:internal/store/migrate.go:62-64 · Read → that phrase]`. |
| D5 | **Chunk creation is its own short transaction, at explicitly pinned READ COMMITTED, whose first statement locks the maze row `FOR NO KEY UPDATE` and which takes no other lock.** Statement order, the corpus's own: lock the maze row, re-read the chunk row, read the existing neighbours' stored maps, generate, insert the chunk, append the event, commit. **The lock-ordering rule, which #36 must obey: a chunk-creation transaction takes no explicit row lock other than the maze row's, and a raid-session transaction never takes the maze row lock — so the maze row is the only lock #36 has to order against.** The word *explicit* is load-bearing: the transaction still takes the implicit key-share locks its foreign keys imply on the `owner` rows its event and its gate column reference, and the rule stays true the day someone locks an owner row deliberately. | With one explicit lock on one side and none on the other there is no cycle to order, so a chunk created during a raid cannot deadlock against the session row lock whichever order the two are taken in — which is why the rule goes into `ai-docs/domain-invariants.md` and not only into a doc comment: #36 is a different pull request. Today the "none on the other" half is a fact about the whole module, not only about #36's plan: the explicit row locks in non-test Go source are `internal/scheduler`'s, on `scheduled_task` and `process_liveness`, **together with this design's own `lockMazeSQL` on `maze`** — and none is on `owner`, which is the row both D8's and D10's kind checks read `[measured fe89960 · `grep -rn "FOR UPDATE\|FOR NO KEY UPDATE\|FOR SHARE\|FOR KEY SHARE" --include=*.go internal/ cmd/ \| grep -v _test.go` → `internal/scheduler`'s claim.go, settle.go, liveness.go, reconcile.go and doc.go, plus `internal/world/chunk.go:31`; the pattern's own hits are the control that it matches, and no hit names `owner`]`. The inventory names this design's lock rather than quietly excluding it, because a clause that silently omits its own subject invites a reader to wonder what else it omits. The isolation level is passed explicitly through `pgx.TxOptions` rather than inherited from a server setting, because two properties rest on it: in READ COMMITTED "each command starts with a new snapshot that includes all transactions committed up to that instant", so the loser of a lock race re-reads the chunk row **after** the winner commits and finds it present `[measured postgresql@18 · https://www.postgresql.org/docs/18/transaction-iso.html → "Because Read Committed mode starts each command with a new snapshot that includes all transactions committed up to that instant, subsequent commands in the same transaction will see the effects of the committed concurrent transaction in any case"]`, whereas under REPEATABLE READ the same wait ends in `could not serialize access due to concurrent update` `[measured postgresql@18 · https://www.postgresql.org/docs/18/transaction-iso.html → that error and "a repeatable read transaction cannot modify or lock rows changed by other transactions after the repeatable read transaction began"]`. **Running on the caller's transaction rejected** by AC7 and by "короткой отдельной транзакции". **The consequence is a stall, not an error, so it is designed against rather than noted.** The designed call order already avoids the nesting on the hot path: §3.5's own transition pseudocode has the missing chunk created *before* the transition `[measured ~/lab-private@4200ebc:DESIGN.md § 3.5 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o 'недостающий чанк создается до перехода — своей короткой транзакцией'` → that fragment]`, which holds one connection at a time. The nested shape is supported all the same, because AC7 is stated over a caller whose own work fails and is rolled back, and it costs two connections at once — so N nesting callers can exhaust a pool with every holder waiting on a connection nobody will release. Two things are therefore written down rather than discovered in production: the composition root sizes the pool at **at least two connections per concurrent nesting caller**, and `Spec` carries an acquisition-and-work budget, `CreateBudget time.Duration`, with no default and refused when non-positive — the module's standing no-silent-default posture — which `EnsureChunkAt` and `ActivateChat` apply to **the whole call — D6's unlocked fast-path read included, not only the locked transaction**. The scope has to be the call, and the reason is the hazard itself: the fast-path read acquires a connection of its own, so a caller already holding one can be blocked *before* the creation transaction is ever reached, and a budget scoped to the transaction alone would let exactly the stall this decision exists to prevent happen with a bare context error and no `ErrCreateBudget` to read. With the call as the scope, an exhausted pool and a long-held maze row lock alike surface as `ErrCreateBudget` instead of as a hang, wherever in the call they bite. **The sentinel means *this call's context ended*, not those two causes specifically**, and the design says so because the narrower reading is the tempting one: the wrap fires on any non-nil `ctx.Err()`, so it carries `context.DeadlineExceeded` when the budget elapses and `context.Canceled` when the **caller** cancels the context it passed in. A caller's own cancellation surfaces identically, by design, and a reader who took `ErrCreateBudget` for proof of contention would be reading more into it than it says. **The bound is this task's, not #36's:** a package that can hang its caller is not something to hand over with a note. |
| D6 | **A read is unlocked; only an absent chunk pays the lock.** `func (m *Maze) EnsureChunkAt(ctx context.Context, cell hexgrid.Coord, by Actor) (maze.Map, error)`, with `type Actor struct { PlayerID, ChatID *store.OwnerID }` carrying the event's player and chat dimensions (D9). **The creation cause is not a parameter**: this entry point's cause is always `explorer` and D8's is always `chat_activation`, so there is no cause a caller can get wrong. Named error returns: `ErrMazeMissing` from the lock statement, `ErrRadiusMismatch` from the decode; everything else is wrapped. It reads the chunk row first with no lock and returns it when present; only a miss opens D5's transaction, which re-checks under the lock. **The unlocked read is inside D5's budget**, not outside it — it takes a pool connection of its own, so it is one of the two places the call can stall. This rests on one invariant the package owes: **a `chunk` row is never updated after insert** — there is no `UPDATE chunk` statement in the package's **non-test** source `[measured fe89960 · `grep -rn "UPDATE chunk" --include=*.go internal/` → exactly one hit, `internal/world/chunk_test.go:145`, which is § Test Design's own read-does-not-regenerate case mutating a stored blob on purpose; that hit is this negative's control — the pattern matches a real occurrence, and every occurrence it matches is in test source]`. **No gate holds it**, which is why it is written as an invariant the package *owes* rather than one the tree enforces: like D8's `owner.kind` premise it is review-judged, and D8 leans on it a second time for its own unlocked gate read. | A row that is never updated reads the same locked or unlocked, so the fast path gives up nothing. The invariant is scoped to non-test source deliberately: subtask 4's discriminating case updates a stored blob from `package world`'s own test file, precisely to prove that a read does not regenerate, so an invariant stated over the whole package would contradict this design's own test plan. Without the fast path, every `move(face)` would queue behind the maze row lock, which is the hot path of the whole game; with it, only a genuine miss pays, and a miss happens once per chunk in a world's lifetime. |
| D7 | **Depth is computed on read, from the maze's gate rows alone.** `func (m *Maze) Depth(ctx context.Context, q Queryer, cell hexgrid.Coord) (depth int64, found bool, err error)`, over a consumer-declared `type Queryer interface { Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error) }` — this package's own, because `store.Queryer` carries `QueryRow` alone and this read is multi-row `[measured 0eb6105:internal/store/owner.go:10-18 · Read → "Queryer is the single QueryRow method a read shared between a transaction and a pool-backed caller needs", declared "per this project's interfaces-declared-by-the-consumer rule"]`. Both `pgx.Tx` and `*pgxpool.Pool` satisfy it, so a raid transition can read depth inside its own transaction. One statement — `SELECT q, r FROM chunk WHERE maze_id = $1 AND gate_chat_id IS NOT NULL` — feeds `gate.NewSet` and `Set.Depth`. `found` is false when the maze holds no gate, matching `Set.Depth`'s own contract; there is no sentinel of its own. ## Risks

- **A caller that creates a chunk while holding its own transaction holds two pool connections at once, and the failure mode is a hang rather than an error.** D5 puts the creation on a connection of its own, which is what AC7 asks for; a pool that cannot hand out the second connection blocks the first, and N such callers can reach the state where every holder waits for a connection nobody will release. The test pool is capped per schema, so the suite is where this shows first `[measured 65b17dd:internal/testdb/testdb.go:71-74 · Read → "schemaMaxConns caps each per-test pool so 16 parallel subtests stay well under the server's connection limit"; `const schemaMaxConns = 4`]`. Mitigation, in three parts, all of them D5's: the designed call order creates a missing chunk **before** the transition and so nests nothing on the hot path; `Spec.CreateBudget` bounds **the whole call**, D6's unlocked read included and not the locked transaction alone, so exhaustion surfaces as `ErrCreateBudget` wherever it bites rather than as a stall — a sentinel that names a context that ended, the caller's own cancellation included, never contention specifically (D5); and the sizing rule the composition root inherits — at least two connections per concurrent nesting caller — is written down here rather than left to be found. The two-connection requirement is also stated on `EnsureChunkAt`'s own doc comment, and § Test Design drives the nested case, the budget refusal and the bound itself — `[derived → the AC7 rollback case, and the budget refusal and bound cases, in § Test Design]`.
- **The maze row lock serialises every chunk creation in a world, explorers and activations alike.** That is the corpus's design, not a defect, but it is the shape that would show first under load. Mitigation: D6's unlocked fast path means only a genuine miss pays it, and a miss happens once per chunk in a world's lifetime — `[derived → the repeated-request case in § Test Design, which asserts the existing-chunk path writes nothing]`.
- **`Depth` builds its gate set per call, which is the cost KD-41 names.** It reads the maze's gate rows on every query, so a consumer answering many cells pays the gate count each time `[measured 65b17dd:internal/gate/depth.go:6-8 · Read → "Build it once per gate snapshot with NewSet; a caller that rebuilds it per query pays the gate count every time"]`. Mitigation: at MVP scale a maze holds one chat's gate and a raid edge asks about one cell; the escape hatch, if a consumer ever needs many, is to export the snapshot read beside `Depth` and let that consumer hold a `gate.Set`. Nothing in this design blocks it.
- **Activation reads every created chunk of the maze.** `gate.Next` takes slices and needs the largest ring of any created chunk, so the read cannot be bounded without changing that function `[measured 65b17dd:internal/gate/next.go:22-33 · Read → the loops over `created` and `gates` computing `m`]`. Mitigation: activation happens once per chat per world, which KD-41 already records as what makes the linear check affordable; the observable is a maze's chunk count, and the escape hatch is a ring-bounded read, which is a change in `internal/gate` and therefore out of this task.
- **The stored byte layout is live data from the first merged chunk.** A change to the cell order, the bit order or the high-bit rule misreads every stored map in every database. Mitigation: the golden in § Test Design fails on any such change, and D3 records what a diff in it means — `[derived → the codec golden in § Test Design]`.
- **A world file's `generation.radius` edited after chunks exist would silently generate at a second radius.** Mitigation: D3's length check refuses the first stored chunk read at the new radius, naming both — `[derived → the radius-mismatch case in § Test Design]`.
- **Panic surface.** None is designed: every refusal is a returned error, and the panic index is empty and stays so `[measured 65b17dd:ai-docs/panic-index.md:9 · Read → "| — | — | — |"]`. `maze.Generate` and `maze.NewMap` return errors rather than panicking, including for an unknown chunk type `[measured 65b17dd:internal/maze/generate.go:9-13 · Read → "Generate can still refuse an unknown ChunkType or an invalid neighbour map, but never panics"]`, so the decode path has no unreachable branch to assert away.
- **`rowserrcheck` and `sqlclosecheck` are enabled, and this package's reads are the module's first multi-row gameplay queries.** Both the gate-chunk read and the created-chunk read iterate `pgx.Rows` `[measured 65b17dd:.golangci.yml:26-27 · Read → "- rowserrcheck" and "- sqlclosecheck"]`. ## Test Design

Subtask 1's tests are `internal/store`'s own and are described in their own entry below. Every other test here is in `package world`, so the codec and the locked creation body are reachable directly, and every database-backed test takes its pool from `storetest.Pool(t)` — the shared migrated-schema pool the scheduler, ingest, bot and contract suites already stand on `[measured 65b17dd:internal/storetest/storetest.go:16-18 · Read → "Pool builds a fresh, migrated schema-scoped pool for tb and closes it on tb's cleanup"]`. The package's `TestMain` is the single statement `os.Exit(leaktest.Main(m, testdb.Main))`, the database-backed form, which a guard fails the suite for omitting `[measured 65b17dd:ai-docs/go-test-conventions.md · `grep -n "leaktest.Main(m, testdb.Main)" ai-docs/go-test-conventions.md` → that form, and "the guard below counts them together"]`. Table-driven subtests with `t.Parallel()` are the default shape; every wall-clock value here is an instrument and is generous, never a subject — except where a case names one as its own discriminator, which the budget case below does. **This hazard has recurred in this package: an assertion whose expected value coincides with the value a broken implementation would produce.** It has appeared as an error identity a missing budget reproduced exactly; as a spiral index and ring that are zero at the centre chunk every fixture happened to use; and as a border agreement the generator's symmetry delivers with or without the neighbour read. None was visible from reading the assertion, and the list is kept without a tally on purpose — a count is what made this paragraph need correcting the last time it was amended. **The line worth drawing, because it says which claims still need running:** a discriminator the fixture *forces* — a mutated blob cannot equal a freshly generated one, a nearer chunk cannot leave a minimum unchanged — holds by construction and is argued; a discriminator that merely *happens* to differ, because two paths produced distinguishable observations in the case at hand, is a claim about those paths and is worth nothing until the defect has been put in and the case watched. Every instance above was of the second kind.
