# Design: Maze persistence: mazes, lazy chunk creation, gates, discoveries, depth

**Issue:** #29
**Date:** 2026-09-17

## Approach

Everything this task computes with already exists and is already pure. `internal/maze` builds a chunk whole and hands back a `Map` carrying its chunk, its `ChunkType` and the generation `Version` it was built under, and it takes a shared border from any neighbour `Map` it is given: `Generate(ch hexgrid.Chunk, typ ChunkType, neighbors ...Map) (Map, error)` `[measured 65b17dd:internal/maze/generate.go:45 · Read → that signature; lines 92-103 → "if nm, ok := neighborMaps[neighborChunk]; ok { … passage = nFaces[d.Opposite()] == FacePassage }"]`, with `NewMap(ch, typ, version, faces [][6]FaceState) (Map, error)` rebuilding a stored one and refusing an unknown type, a version below one, a face count that is no hexagon, a face state outside wall and passage, and an interior face whose two cells disagree `[measured 65b17dd:internal/maze/map.go:98-139 · Read → that refusal list]`. `internal/gate` places and measures: `Next(created, gates []hexgrid.Chunk, k int) (hexgrid.Chunk, error)` `[measured 65b17dd:internal/gate/next.go:16 · Read → that signature]`, `SpiralIndex(ch) int64` `[measured 65b17dd:internal/gate/spiral.go:70 · Read → that signature]`, and `NewSet(lattice, gates)` / `Set.Depth(cell) (int64, bool)` `[measured 65b17dd:internal/gate/depth.go:20,37 · Read → those signatures]`. `internal/hexgrid` maps between a cell and its chunk — `Lattice.Locate`, `Lattice.At`, `Lattice.Center`, `Lattice.LocalCells`, `Lattice.CellCount` `[measured 65b17dd:internal/hexgrid/lattice.go:15,21,39,70,82 · Read → those signatures]`. `internal/store` owns the module's only embedded migration directory and the event log's write path — `AppendEvent(ctx, tx, e Event) (EventID, error)`, which writes one event row and no journal entry `[measured 65b17dd:internal/store/event.go:79-94 · Read → "Unlike Post, it creates no journal_entry and moves no balances"]`, over an `Event` whose player, chat, maze and depth dimensions are nullable columns and whose everything-else is `Payload` JSONB `[measured 65b17dd:internal/store/event.go:42-49 · Read → that struct]`.

What is missing is the database between them. This task adds one forward migration and one package, `internal/world` — the block name the architecture table already gives this responsibility `[measured 65b17dd:ai-docs/context.md · grep -n "Deterministic chunked generation" ai-docs/context.md → "| World | Deterministic chunked generation, stored chunk maps, spiral gate placement, discovery/knowledge | §2.2 |"]`. The migration lands in `internal/store/migrations` because that is the directory `store.Migrate` embeds, and a table a non-`store` package owns has migrated there before — `scheduled_task` and its enum are in that directory while every statement reading them is in `internal/scheduler` `[measured 65b17dd:internal/store/migrations/00002_scheduler.sql:2 · grep -n "CREATE TYPE" internal/store/migrations/*.sql → "CREATE TYPE scheduled_task_state AS ENUM ('pending', 'dead');"]` `[measured 65b17dd:internal/scheduler/claim.go:20 · Read → "WHERE state = 'pending' AND run_at <= now()"]`. That precedent decides the Go vocabulary too: `scheduled_task_state` has no mirror in `store/enums.go`, so this task's two new enums are `internal/world`'s own vocabulary and `store/enums.go` does not grow `[measured 65b17dd · grep -rn "'pending'" --include=*.go internal/store/ → only internal/store/migrate_test.go, a test file; the same pattern against internal/scheduler/ matches claim.go, settle.go, liveness.go, reconcile.go and schedule.go, so the empty non-test result is the pattern working]`. The event **type** is the exception in the other direction: the registry and its element-for-element Go mirror belong to the event log, which is `store`'s, so the new row lands in `store/catalog.go` beside the rest `[measured 65b17dd:internal/store/catalog.go:53-58 · Read → "A new type is registered by a forward migration inserting a row — never by adding a constant here alone — and TestCatalog_mirrors_database's element-for-element comparison fails on either side doing so without the other"]`.

**The three questions the spec left to this design are answered as D7, D5 and D9 below**, and each is answered from something already in the tree rather than from taste.

*Depth is computed on read, never stored (D7).* The metric is a cell distance by the hex formula to the nearest gate of any chat `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.4 · `git -C ~/lab-private show 4200ebc:DESIGN.md | grep -o 'Дистанция опасности = до ближайших ворот любого чата; крафтовые двери в ней не участвуют'` → that sentence]`, so there is no per-chunk or per-cell quantity to hold: the answer is a function of the gate set alone, and a maze's gate set is a handful of rows. Storing it would buy nothing and would owe an invalidation sweep over every stored cell on every activation — and AC13 is precisely the statement that a later gate must lower an earlier depth, which a computed read satisfies by construction and a stored column satisfies only if that sweep is correct. `gate.Set` is already built for this shape: KD-41 records that the stop rule bounds the ring search by the distance and the lattice radius rather than by the gate count, and its closing sentence hands this question here — "Where the gate snapshot lives, and whether depth is stored or computed on read, is #29's" `[measured 65b17dd:ai-docs/key-decisions.md · `awk '/KD-41 —/,/KD-42 —/' ai-docs/key-decisions.md` → both sentences]`.

*The per-world lock is a `FOR NO KEY UPDATE` row lock on the maze row, in a short transaction of its own, at an explicitly pinned READ COMMITTED (D5).* The corpus fixes the shape — "любое создание чанка — исследователем и при активации — идет под блокировкой мира в короткой отдельной транзакции: проверка отсутствия, чтение границ уже созданных соседей, генерация, вставка" `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.2 · `git -C ~/lab-private show 4200ebc:DESIGN.md | grep -o 'любое создание чанка[^.]*\.'` → that sentence]` — and leaves the form open. A row lock is chosen over an advisory lock for three reasons that are in the tree. The module already takes exactly this lock mode for exactly this purpose, with the reason written down: `FOR NO KEY UPDATE` is what the transaction's own later write already takes and it conflicts with itself, which is all the mutual exclusion needed `[measured 65b17dd:internal/scheduler/liveness.go:87-91 · Read → "The lock is FOR NO KEY UPDATE, not the stronger FOR UPDATE … PostgreSQL's conflicting-locks table has FOR NO KEY UPDATE conflict with itself, which is all the mutual exclusion this transaction needs"]`, and PostgreSQL's own conflict table agrees `[measured postgresql@18 · https://www.postgresql.org/docs/18/explicit-locking.html → Table 13.3 marks FOR NO KEY UPDATE as conflicting with FOR NO KEY UPDATE]`. An advisory lock is identified by a bare application-defined integer with no relation or schema qualification `[measured postgresql@18 · https://www.postgresql.org/docs/18/functions-admin.html → "All these functions are intended to be used to lock application-defined resources, which can be identified either by a single 64-bit key value or two 32-bit key values"]`, so it would need a module-wide id registry beside the one id already allocated, and this module has already recorded why that is the awkward direction here — the migration lock is opt-in with a caller-supplied id precisely because "the lock is database-wide while this package's own test isolation is schema-wide" `[measured 65b17dd:internal/store/migrate.go:43-54 · Read → that sentence]`. And the row lock doubles as the maze-row existence check, so a chunk creation naming a maze that is not there fails on the lock statement rather than on an insert.

*The event is `chunk_created`, low volume (D9).* The dictionary's own convention is subject-then-past-participle — `bot_added_to_chat`, `player_started`, `raid_started`, `node_entered`, `combat_resolved`, `raid_finished`, `backpack_dropped`, `backpack_looted`, `backpack_expired`, `notification_sent`, `button_clicked`, `bot_kicked` `[measured 65b17dd:internal/store/migrations/00003_event_log.sql:20-36 · Read → that seeded row set]`. Its volume class is `low_volume`: the high-volume pair is the per-message and per-press traffic, and a chunk is created once and never again, so the traffic is bounded by exploration rather than by interaction.

**Nothing is wired into `cmd/bot`.** This task ships the package and its migration; the composition root gains the world handle with its first caller, which is #36's session creation, `move(face)` and look `[measured 65b17dd · `gh issue view 36 --json body` → "the neighbouring chunk created through #29 (its own short transaction) when it does not exist yet"]`. That is the posture `internal/gate` shipped under, and the architecture page already describes it that way `[measured 65b17dd:ai-docs/context.md · grep -n "which nothing calls yet" ai-docs/context.md → "which nothing calls yet — persisting gates, the activation that places them and every depth consumer arrive with their own issues"]`. #36 also owns the `node_entered` event; what this task owes it is the depth value that event carries, which D7 delivers.

### Key decisions

| # | Decision | Why / rejected alternatives |
|---|---|---|
| D1 | **One new package, `internal/world`, and one forward migration in `internal/store/migrations`.** `internal/world` imports `internal/hexgrid`, `internal/maze`, `internal/gate`, `internal/store`, `pgx`/`pgxpool` and the standard library; no existing package imports it, so nothing else moves. The migration file is next in that directory's sequence, `00009_world_persistence.sql` `[measured 65b17dd:internal/store/migrations/ · `ls internal/store/migrations/` → the sequence ends at 00008_biome_resource_kinds.sql]`. | `internal/world` is the architecture table's own name for this block. Not `internal/maze`, which is the generator and whose graph a persistence consumer must not inherit (KD-38's reason for splitting topology from generation applies again here); not `internal/store`, whose package comment scopes it to the ledger, the item machine and the event log `[measured 65b17dd:internal/store/store.go:1-9 · Read → that comment]`. The migration goes to `store/migrations` because that is the only directory `Migrate` embeds `[measured 65b17dd:internal/store/migrate.go:17-18 · Read → `//go:embed migrations/*.sql`]`. |
| D2 | **The schema: `maze`, `chunk`, `node_discovery`, and two enums of `internal/world`'s own.** `maze` — an `ALWAYS` identity id, `biome text NOT NULL`, `world_seed bigint NOT NULL`, `season integer NOT NULL`, `created_at`, and `UNIQUE (biome, season)`. `chunk` — `PRIMARY KEY (maze_id, q, r)` on the super-lattice coordinate, `chunk_type` and `creation_cause` enum columns, `gate_chat_id bigint REFERENCES owner (id)`, `spiral_index bigint`, `faces bytea NOT NULL` (D3), `generation_version integer NOT NULL` (D4), `created_at`, a `CHECK ((chunk_type = 'gate') = (gate_chat_id IS NOT NULL) AND (chunk_type = 'gate') = (spiral_index IS NOT NULL))`, and a partial `UNIQUE (maze_id, gate_chat_id) WHERE gate_chat_id IS NOT NULL`. `node_discovery` — `PRIMARY KEY (maze_id, q, r, player_id)` on the **cell** coordinate plus `discovered_at`, and no chat column at all. `CREATE TYPE chunk_type AS ENUM ('fabric', 'gate')` and `CREATE TYPE chunk_creation_cause AS ENUM ('explorer', 'chat_activation')`, both growing later by `ALTER TYPE … ADD VALUE`. | Singular names and identity columns follow the ledger core `[measured 65b17dd:ai-docs/key-decisions.md · `grep -n "singular table names" ai-docs/key-decisions.md` → KD-17 "singular table names and identity columns throughout; every referencing-side FK is covered by an index (a migration test enforces it)"]`. `biome` carries the authored world's own id, which the tracked world file already calls "the identity a maze row and every telemetry event carry" `[measured 65b17dd:config/world/cotton_candy.yaml · Read → that comment above `id: cotton_candy`]`, and the triple is the corpus's own field list `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.4 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o '\`mazes\`: id, биом, world_seed, сезон\.'` → that line]`. `UNIQUE (biome, season)` makes "the maze of this biome this season" a lookup and a rotation an insert. The gate `UNIQUE` is AC9's second line, never the mechanism, which is D5's lock. **Type and cause are deliberately tied to nothing**: §13.4 made them separate fields so a later type or cause varies independently `[measured ~/lab-private@4200ebc:DESIGN.md § 13.4 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o 'событие создания чанка\*\* — одно на любую причину; тип чанка и причина создания (активация чата / исследователь) — раздельные поля\.'` → that sentence]`. Every referencing-side FK gets a covering index, because a migration test enforces it with a planted positive control `[measured 65b17dd:internal/store/fkcover_ac17_test.go:8-40 · Read → the clean assertion and the planted `planted_owner_fk` control]`: the two `maze_id` columns ride their primary keys, `chunk.gate_chat_id` takes a partial index whose `IS NOT NULL` predicate that test accepts `[measured 65b17dd:internal/store/fkcover_test.go:25-28 · Read → "whose predicate is either absent or an \"IS NOT NULL\" partial predicate"]`, and `node_discovery.player_id` takes a plain one. A **cell table** was never on the table: cells are not stored row by row `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.4 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o 'Клетки построчно не хранятся'` → that phrase]`, and the spec's own key-decision row defers every kind of cell state to the mechanic that writes it. |
| D3 | **A stored map is `bytea`: one byte per cell in the lattice's `LocalCells` order, bit *d* set iff face *d* is a passage; the two high bits are zero and a set one is refused.** The blob's length must equal the maze's own `Lattice.CellCount()`; a disagreement is `ErrRadiusMismatch` naming both. Decode hands the faces to `maze.NewMap`, so the interior-agreement and face-state refusals stay the generator's. **This byte layout is a data contract** (`AGENTS.md` § API Stability carve-out): changing it is a forward migration that rewrites every stored blob, never an edit. | The bit order is `hexgrid`'s canonical `Direction` order, which that package pins as the order every enum-indexed value relies on `[measured 65b17dd:internal/hexgrid/coord.go:10-24 · Read → "the six values are in the canonical order this package fixes"]`; the cell order is `LocalCells`'s documented one `[measured 65b17dd:internal/hexgrid/lattice.go:79-81 · Read → "in canonical order: rows r = −R..R, q ascending within each row"]`. The high-bit rule turns a truncated or foreign blob into a named refusal instead of a plausible map. The length check is what catches a world file whose `generation.radius` was edited after chunks were stored. **JSONB and `smallint[]` rejected:** both cost several times the bytes and neither makes a byte-for-byte golden meaningful. **Regenerating on read rejected by the corpus, not by this design** — "Карта чанка хранится вместе с версией генерации и заново не генерируется" `[measured ~/lab-private@4200ebc:DESIGN.md § 2.2.2 · `git -C ~/lab-private show 4200ebc:DESIGN.md \| grep -o 'Карта чанка хранится[^;]*;'` → that phrase]`. |
| D4 | **The generation version is stored per chunk and read back with the map; a maze holding chunks of several versions is the designed state.** A read returns `maze.NewMap(ch, storedType, storedVersion, decodedFaces)` — the stored version, not the current constant. Nothing regenerates and nothing back-fills. **Deploy window and rollback:** the migration is forward-only, so rolling the binary back leaves the tables in place and unread, and rolling forward again finds them. | `maze.Version` is the constant a generation change bumps, and a stored map's own version "travels with it and never changes on its own" `[measured 65b17dd:internal/maze/map.go:9-14 · Read → that sentence and `const Version int32 = 1`]`. A new chunk beside an old one still agrees on their shared border, because `Generate` reads the neighbour's stored faces rather than re-deriving them, and that branch is version-blind (the `neighborMaps` branch cited in § Approach). Forward-only is this package's stated posture — "forward-only (no -- +goose Down section exists in this package)" `[measured 65b17dd:internal/store/migrate.go:62-64 · Read → that phrase]`. |
| D5 | **Chunk creation is its own short transaction, at explicitly pinned READ COMMITTED, whose first statement locks the maze row `FOR NO KEY UPDATE` and which takes no other lock.** Statement order, the corpus's own: lock the maze row, re-read the chunk row, read the existing neighbours' stored maps, generate, insert the chunk, append the event, commit. **The lock-ordering rule, which #36 must obey: a chunk-creation transaction takes the maze row lock and nothing else, and a raid-session transaction never takes the maze row lock.** | With one lock on one side and none on the other there is no cycle to order, so a chunk created during a raid cannot deadlock against the session row lock whichever order the two are taken in — which is why the rule goes into `ai-docs/domain-invariants.md` and not only into a doc comment: #36 is a different pull request. The isolation level is passed explicitly through `pgx.TxOptions` rather than inherited from a server setting, because two properties rest on it: in READ COMMITTED "each command starts with a new snapshot that includes all transactions committed up to that instant", so the loser of a lock race re-reads the chunk row **after** the winner commits and finds it present `[measured postgresql@18 · https://www.postgresql.org/docs/18/transaction-iso.html → "Because Read Committed mode starts each command with a new snapshot that includes all transactions committed up to that instant, subsequent commands in the same transaction will see the effects of the committed concurrent transaction in any case"]`, whereas under REPEATABLE READ the same wait ends in `could not serialize access due to concurrent update` `[measured postgresql@18 · https://www.postgresql.org/docs/18/transaction-iso.html → that error and "a repeatable read transaction cannot modify or lock rows changed by other transactions after the repeatable read transaction began"]`. **Running on the caller's transaction rejected** by AC7 and by "короткой отдельной транзакции"; the consequence the caller owns is that creation runs on a second pool connection (§ Risks). |
| D6 | **A read is unlocked; only an absent chunk pays the lock.** `EnsureChunkAt` reads the chunk row first with no lock and returns it when present; only a miss opens D5's transaction, which re-checks under the lock. This rests on one invariant the package owes: **a `chunk` row is never updated after insert** — there is no `UPDATE chunk` statement in the package. | A row that is never updated reads the same locked or unlocked, so the fast path gives up nothing. Without it every `move(face)` would queue behind the maze row lock, which is the hot path of the whole game; with it, only a genuine miss pays, and a miss happens once per chunk in a world's lifetime. |
| D7 | **Depth is computed on read, from the maze's gate rows alone.** One statement — `SELECT q, r FROM chunk WHERE maze_id = $1 AND gate_chat_id IS NOT NULL` — feeds `gate.NewSet` and `Set.Depth`. No stored column, no invalidation. | The predicate is `gate_chat_id IS NOT NULL` rather than `chunk_type = 'gate'` for two reasons that coincide: D2's `CHECK` makes them the same row set, and the partial unique index on `(maze_id, gate_chat_id)` serves this predicate without a second index. **AC12's "by construction" is a property of the input type**: the metric's input is a set of `hexgrid.Chunk` values read from the gate rows of the chunk table, and a crafted door is bound to a **cell** and will live in its own table — it is not a chunk row and cannot become one, so there is no filter to forget. `Depth` takes no parameter carrying a position other than the cell being measured. |
| D8 | **Gate allocation runs under D5's lock and D5's transaction, and delegates the rule to `gate.Next`.** Under the lock: return the chat's existing gate when the `(maze, chat)` row is there (AC9); otherwise read the maze's created chunks and its gate chunks, call `Next(created, gates, k)`, and create that chunk whole with type `gate`, cause `chat_activation`, the chat, and `gate.SpiralIndex` of the chosen chunk. | `Next` never returns a created chunk — it filters the created set over the scanned prefix and its fallback lies on a ring beyond every created chunk `[measured 65b17dd:internal/gate/next.go:40-57 · Read → the bounded scan with `createdSet` and the `fallbackRing` return]` — so activation never collides with an explorer's chunk, which is the corpus's "explorers push gates outward" observed rather than fixed. `k` comes from the world configuration's `k` key, which the loader already validates non-negative `[measured 65b17dd:internal/config/world_schema.go:150 · Read → `entry("k", bindInt(&w.GateSpacing, nonNegativeInt, "non-negative"))`]`, so `Next`'s `ErrNegativeK` is unreachable through a loaded world — and is propagated rather than swallowed, because "unreachable" is a property of today's only caller. |
| D9 | **`chunk_created`, `low_volume`, one row per created chunk, appended inside D5's transaction.** Registered by the migration in `event_type_definition` and mirrored in `store/catalog.go`. Dimensions: `maze_id` always; `chat_id` from the activating chat or the caller's session chat; `player_id` from the caller's player; `depth` null. Payload: `chunk_type` and `creation_cause` as separate keys, `generation_version`, the chunk coordinate, and — for a gate chunk only — `spiral_index` and `ring`. **Chunk creation moves no balance, so it declares no posting signature and adds no `internal/contract` row.** | Registering through the migration plus the mirror is the only way one can be registered `[measured 65b17dd:internal/store/catalog.go:53-58 · Read → that rule and the mirror test it names]`. `depth` is null because a chunk is not a cell, and no shipped view reads `depth` from any type but `death` `[measured 65b17dd:ai-docs/domain-invariants.md · `grep -n "No shipped view reads" ai-docs/domain-invariants.md` → "No shipped view reads `chat_id` from `raid_started` or from `death`; none reads `maze_id`; none reads any payload key"]`. **The coordinate is this design's own addition beyond the owner's enumerated list**, flagged as such: the issue left the remaining payload fields to be settled downstream, and an event that names no chunk cannot be joined to the row it is about, which is what "one event per created chunk" is for. **`k` is deliberately not carried**, although #120's body anticipated it — the owner's answer enumerates the spiral index, the ring and the generation version, and `k` is a property of the world configuration for the season, recoverable there. Sharing one transaction with the insert makes AC15's "one for every created chunk" and AC7's survival the same fact. The no-posting claim is `AppendEvent`'s own documented behaviour `[measured 65b17dd:internal/store/event.go:79-84 · Read → "Unlike Post, it creates no journal_entry and moves no balances"]`, held by `[derived → the contract-silence case in § Test Design]`. |
| D10 | **A discovery rides the caller's transaction, is idempotent, and checks the owner's kind inside its own INSERT.** `RecordDiscovery(ctx, tx pgx.Tx, cell, playerID)` writes on the caller's `pgx.Tx`. `INSERT … SELECT … FROM owner WHERE id = $n AND kind = 'player'` plus `ON CONFLICT DO NOTHING` gives both properties in one statement: a non-player inserts nothing and the package returns `ErrNotAPlayer`, and a repeat keeps the first `discovered_at`. The same statement shape checks `kind = 'chat'` for a gate's chat in D8. | A discovery is an effect of the move edge and must roll back with it — the opposite of D5's chunk, and for the opposite reason. **A composite kind-pinned FK rejected**, in the item machine's style: KD-17's amendment scopes that construction to where the guard **is** the mechanic — an item instance moves, so a declarative guard on its chain guards the mechanic, whereas the account model's own tables were left without one `[measured 65b17dd:ai-docs/key-decisions.md · `grep -n "No composite FKs" ai-docs/key-decisions.md` → "«No composite FKs and no move-control» is scoped to the account model's own tables … an account never moves, so a declarative guard against moving one guards nothing"]`. A gate's chat and a discovery's player never move either, and each table has exactly one writer, which is where the check lives. **No FK from `node_discovery` to `chunk`:** "you can only discover a cell you reached" is the raid edge's invariant, and a derived chunk coordinate would need the lattice radius, which is configuration and unavailable to a SQL generated column. |
| D11 | **`Open` resolves the maze row, creating it when absent, and refuses a seed that disagrees with a stored one.** `Open(ctx, pool, Spec{Biome, Season, Seed, Generation maze.Params, GateSpacing}) (*Maze, error)` inserts `ON CONFLICT (biome, season) DO NOTHING`, reads the row back, and returns `ErrSeedMismatch` naming both seeds when the stored `world_seed` is not `Spec.Seed`. The handle holds the pool, the maze id, a `*maze.Generator`, the lattice and `k`; `Lattice()` is exported so a caller can locate a cell and take a gate chunk's centre. | The refusal is the point of storing the seed at all: every stored chunk was generated under the row's seed, so silently adopting a new one would leave a world whose stored maps and whose freshly generated ones belong to different worlds. The generator is built by `maze.New(spec.Seed, spec.Generation)`, the single source of every cross-field refusal on those inputs `[measured 65b17dd:internal/maze/generate.go:19-26 · Read → "New builds a Generator over seed and params. It rejects an invalid params, naming the offending input"]`. **Storing the chunk radius on the maze row rejected** as the stronger form of D3's length check: it adds a column no acceptance criterion asks for, and the length check catches the same drift at the first read. |
| D12 | **The world package's own enum vocabulary, mirrored against the database by its own test.** `world.ChunkType` and `world.CreationCause` are string types whose members are the two database enums' members, with a total mapping to and from `maze.ChunkType` that refuses a value it does not know. | The mapping exists rather than reusing `maze.ChunkType.String()` because `String` is for logging and test failure messages `[measured 65b17dd:internal/maze/chunktype.go:17-27 · Read → "String renders t for logging and test failure messages"]`, and a stored value must not move when a rendering does. The mirror test is this package's own because the enums are, following `scheduled_task_state`'s precedent — with the mirror added, which the scheduler's enum never had. |

## Risks

- **A caller that creates a chunk while holding its own transaction holds two pool connections at once.** D5 puts the creation on a connection of its own, which is what AC7 asks for; a pool that cannot hand out the second connection blocks the first. The test pool is capped per schema, so the suite is where this shows first `[measured 65b17dd:internal/testdb/testdb.go:71-74 · Read → "schemaMaxConns caps each per-test pool so 16 parallel subtests stay well under the server's connection limit"; `const schemaMaxConns = 4`]`. Mitigation: the two-connection requirement is stated on `EnsureChunkAt`'s own doc comment, and § Test Design drives the nested case explicitly rather than leaving a caller to discover it — `[derived → the AC7 rollback case in § Test Design, which calls from inside an open caller transaction]`.
- **The maze row lock serialises every chunk creation in a world, explorers and activations alike.** That is the corpus's design, not a defect, but it is the shape that would show first under load. Mitigation: D6's unlocked fast path means only a genuine miss pays it, and a miss happens once per chunk in a world's lifetime — `[derived → the repeated-request case in § Test Design, which asserts the existing-chunk path writes nothing]`.
- **`Depth` builds its gate set per call, which is the cost KD-41 names.** It reads the maze's gate rows on every query, so a consumer answering many cells pays the gate count each time `[measured 65b17dd:internal/gate/depth.go:6-8 · Read → "Build it once per gate snapshot with NewSet; a caller that rebuilds it per query pays the gate count every time"]`. Mitigation: at MVP scale a maze holds one chat's gate and a raid edge asks about one cell; the escape hatch, if a consumer ever needs many, is to export the snapshot read beside `Depth` and let that consumer hold a `gate.Set`. Nothing in this design blocks it.
- **Activation reads every created chunk of the maze.** `gate.Next` takes slices and needs the largest ring of any created chunk, so the read cannot be bounded without changing that function `[measured 65b17dd:internal/gate/next.go:22-33 · Read → the loops over `created` and `gates` computing `m`]`. Mitigation: activation happens once per chat per world, which KD-41 already records as what makes the linear check affordable; the observable is a maze's chunk count, and the escape hatch is a ring-bounded read, which is a change in `internal/gate` and therefore out of this task.
- **The stored byte layout is live data from the first merged chunk.** A change to the cell order, the bit order or the high-bit rule misreads every stored map in every database. Mitigation: the golden in § Test Design fails on any such change, and D3 records what a diff in it means — `[derived → the codec golden in § Test Design]`.
- **A world file's `generation.radius` edited after chunks exist would silently generate at a second radius.** Mitigation: D3's length check refuses the first stored chunk read at the new radius, naming both — `[derived → the radius-mismatch case in § Test Design]`.
- **Panic surface.** None is designed: every refusal is a returned error, and the panic index is empty and stays so `[measured 65b17dd:ai-docs/panic-index.md:9 · Read → "| — | — | — |"]`. `maze.Generate` and `maze.NewMap` return errors rather than panicking, including for an unknown chunk type `[measured 65b17dd:internal/maze/generate.go:9-13 · Read → "Generate can still refuse an unknown ChunkType or an invalid neighbour map, but never panics"]`, so the decode path has no unreachable branch to assert away.
- **`rowserrcheck` and `sqlclosecheck` are enabled, and this package's reads are the module's first multi-row gameplay queries.** Both the gate-chunk read and the created-chunk read iterate `pgx.Rows` `[measured 65b17dd:.golangci.yml:26-27 · Read → "- rowserrcheck" and "- sqlclosecheck"]`. Mitigation: both follow the scheduler's shipped discipline — deferred `Close`, `rows.Err()` checked after the loop `[measured 65b17dd:internal/scheduler/claim.go:28-46 · Read → `defer rows.Close()` and the `rows.Err()` check]`.
- **Coverage.** The package is mostly refusal and concurrency paths, and the ratchet only ever rises. Mitigation: every refusal D3, D8, D10, D11 and D12 name gets its own case in § Test Design.
- **The `exhaustive` linter treats a `default` as exhaustive, so it will not force the `maze.ChunkType` mapping to be total** `[measured 65b17dd:.golangci.yml:44-45 · Read → "exhaustive:" with "default-signifies-exhaustive: true"]`. Mitigation: D12's mapping refuses an unknown value in its `default` branch, and § Test Design holds the mapping total over the exported members by driving it from a table rather than by trusting the linter.
- **A goroutine in a test is not covered by the module's bare-`go` allow list, but a leaked one still fails the package.** The concurrency suite launches goroutines; production code in this package launches none. Mitigation: subtask 7 fans out through `golang.org/x/sync/errgroup`, which is already a direct dependency `[measured 65b17dd:go.mod · `grep -n "golang.org/x/sync" go.mod` → "golang.org/x/sync v0.23.0" in the direct require block]`, so every goroutine is waited for and its error reaches the test; the package's `TestMain` leak check is what holds that claim.

## Test Design

All tests are in `package world`, so the codec and the locked creation body are reachable directly, and every database-backed test takes its pool from `storetest.Pool(t)` — the shared migrated-schema pool the scheduler, ingest, bot and contract suites already stand on `[measured 65b17dd:internal/storetest/storetest.go:16-18 · Read → "Pool builds a fresh, migrated schema-scoped pool for tb and closes it on tb's cleanup"]`. The package's `TestMain` is the single statement `os.Exit(leaktest.Main(m, testdb.Main))`, the database-backed form, which a guard fails the suite for omitting `[measured 65b17dd:ai-docs/go-test-conventions.md · `grep -n "leaktest.Main(m, testdb.Main)" ai-docs/go-test-conventions.md` → that form, and "the guard below counts them together"]`. Table-driven subtests with `t.Parallel()` are the default shape; every wall-clock value here is an instrument and is generous, never a subject.

**Fixtures.** One helper opens a maze over a small authored `Spec` — `maze.MinRadius` for the radius `[measured 65b17dd:internal/maze/params.go:12-16 · Read → `const MinRadius = 6` and "the MVP's own lower bound"]`, a seed constant of the test's own, and shares `maze.New` accepts — so a chunk is small enough to compare cell by cell. A second creates a player owner and a chat owner through `store.CreateOwner`, the only route that also creates their scopes and accounts. A third compares two `maze.Map` values face for face over `Lattice.LocalCells`. A fourth compares the shared border of two adjacent chunks by walking each border cell of one, stepping to its global neighbour, locating it in the other, and comparing the two face states in opposite directions. `[derived → subtask 2]`

**Subtask 2 — the codec (D3, D12).** Location `internal/world/chunkmap_test.go` and `internal/world/enums_test.go`; entry points the unexported encode and decode and the `maze.ChunkType` mapping.

- Round trip: for several chunk coordinates, generate a map through `maze.Generate` and assert `decode(encode(m))` agrees face for face and carries the same chunk, type and version. `[derived → AC3]`
- **The golden, `internal/world/testdata/chunkmap.golden`.** *What it is:* the encoding of a map built by `maze.NewMap` from a fixture whose face set the test constructs by an explicit stated rule, with **no generator and no seed involved** — this golden pins the *encoding*, not the generation, which `internal/maze`'s own goldens already pin `[measured 65b17dd:internal/maze/testdata/ · `ls internal/maze/testdata/` → chunks.golden, derive.golden]`. *What the comparison covers:* every byte, therefore every cell's every face bit, in `LocalCells` order. *What a diff means:* the stored byte layout has changed, so every stored chunk in every database is now misread — a forward migration that rewrites the blobs, never a refactor. The generation version travelling with a stored map is pinned beside it by a separate case asserting the version column round-trips unchanged, since the version is a column and not part of the blob. `[derived → AC3, and D3's data-contract status]`
- Refusals, one case each, by name: a blob shorter and a blob longer than the lattice's cell count (`ErrRadiusMismatch`, naming both lengths); a byte with either high bit set; and a blob whose interior faces disagree, which must surface as `maze.NewMap`'s own refusal rather than as a new one. `[derived → D3]`
- The enum mapping: a table over the exported `maze` chunk types asserting a round trip through `world.ChunkType`, and a case asserting an unrecognised value is refused rather than defaulted. A mirror case reads `enum_range(NULL::chunk_type)` and `enum_range(NULL::chunk_creation_cause)` and compares each with the package's member slice, in the shape `internal/store`'s own enum mirror uses `[measured 65b17dd:internal/store/enums_test.go:9-38 · Read → `SELECT enum_range(NULL::`+tc.enum+`)::text[]` and the sorted comparison]`. `[derived → D12]`

**Subtask 3 — `Open` (D11).** Location `internal/world/maze_test.go`; entry point `Open`.

- Happy path: on a fresh schema, `Open` twice with the same `Spec` yields the same maze id and leaves one row in `maze`. `[derived → AC1]`
- The stored row carries the spec's biome, seed and season, read back by a direct query — AC1's whole content. `[derived → AC1]`
- `ErrSeedMismatch`: `Open`, then `Open` again with a different seed and the same biome and season; the error names both seeds and no row changes. `[derived → D11]`
- A `Spec` whose generation inputs `maze.New` refuses is refused by `Open`, naming the offending input rather than wrapping it away. `[derived → D11]`

**Subtask 4 — `EnsureChunkAt` (D5, D6, D9).** Location `internal/world/chunk_test.go`; entry point `EnsureChunkAt`. The public entry point is driven throughout, never the unexported creation body, so the wiring is under test and not only the algorithm.

- Creation: a cell in an absent chunk yields a map whose chunk is the one `Lattice.Locate` names, with type fabric and cause explorer stored, and exactly one row in `chunk`. `[derived → AC2]`
- **Equality with generation at the stored version:** read the stored row back and compare its decoded map with `Generate(ch, fabric)` from a generator built on the same seed and inputs, face for face. `[derived → AC3]`
- **The read does not regenerate — the discriminating case.** Create a chunk; then, in the test, decode its stored blob, flip one interior face on both of the cells that share it, re-encode and `UPDATE` the row; call `EnsureChunkAt` again and assert the **mutated** map comes back. A read that regenerated would return the pristine one, so this case fails on the defect it is written for. `[derived → Scope 2, AC6]`
- **Border agreement with an existing neighbour:** create one chunk, then a cell in an adjacent chunk; walk the shared border with the fixture helper and assert every face pair agrees. Repeat with the creation order reversed, and over several directions so the case does not rest on one. `[derived → AC4]`
- Idempotence: calling with two different cells of one chunk yields the same map and leaves the row's blob, type and cause byte-identical, asserted by reading the row before and after. `[derived → AC6]`
- The event: after a creation, exactly one `event` row of type `chunk_created` exists, with `maze_id` set, `depth` null, the caller's player and chat in their columns, and a payload carrying the chunk type, the creation cause, the generation version and the chunk coordinate — and **no** `spiral_index` or `ring` key, a fabric chunk having neither. `[derived → AC15, AC16]`
- **Contract silence:** take `contract.NewMark` on a transaction, run a creation, and assert no journal entry exists past the mark. This is the case that would catch a later edit routing the event through `store.Post` instead of `AppendEvent`. `[derived → D9]`
- Refusal: a cell in a maze whose row has been deleted underneath the handle fails on the lock statement, not on the insert. `[derived → D5]`

**Subtask 5 — `ActivateChat` (D8, D9, D10).** Location `internal/world/activate_test.go`; entry point `ActivateChat`.

- The first activation of a world takes the centre chunk, and the stored row carries type gate, cause `chat_activation`, the chat, and `gate.SpiralIndex` of that chunk. `[derived → AC8]`
- The chunk the spiral yields **for the world as it stands**: create some chunks through `EnsureChunkAt` first, then activate, and assert the gate lands where `gate.Next` called with the same created and gate sets says it does — asserted against `Next`'s answer rather than a hard-coded coordinate, so a change to the spiral's orientation fails `internal/gate`'s own tests instead of failing twice. `[derived → AC8]`
- Re-activation: activating the same chat again yields the same gate chunk and writes no second row and no second event. `[derived → AC9]`
- Two chats in one maze, activated in sequence, take distinct chunks at least `k+1` apart, over a table of `k` values including zero. `[derived → AC9, AC10]`
- The chat-kind check: activating with a player owner's id returns `ErrNotAChat` and writes nothing. `[derived → D10]`
- The event: a gate chunk's `chunk_created` carries the spiral index and the ring beside the keys a fabric chunk's carries, and the chat in its column. `[derived → AC16]`

**Subtask 6 — `Depth` and `RecordDiscovery` (D7, D10).** Location `internal/world/depth_test.go` and `internal/world/discovery_test.go`.

- `Depth` of a gate's own centre cell is zero; of a cell at a known offset, the hex-formula distance to that centre — asserted against `hexgrid.Distance`, never against a literal. `[derived → AC11]`
- No gate in the maze: `Depth` reports not-found rather than zero, matching `Set.Depth`'s own contract. `[derived → AC11]`
- **Fabric chunks do not reach the metric:** create fabric chunks nearer to the probe cell than the gate is, and assert the answer is unchanged — the case that fails if the query ever drops its gate predicate. `[derived → AC12]`
- **A later gate lowers an earlier depth:** read a cell's depth with one gate placed; activate a second chat whose gate the spiral puts nearer that cell; read again and assert the value is strictly lower. The second gate is placed through `ActivateChat`, not inserted by hand, so the case covers the wiring. `[derived → AC13]`
- `RecordDiscovery`: a row naming the cell, the player and a time; a second call for the same triple leaves `discovered_at` unchanged; two players discovering one cell make two rows; a chat owner's id returns `ErrNotAPlayer` and writes nothing; and a discovery written on a transaction that is then rolled back leaves no row — the property that distinguishes it from D5's chunk. `[derived → AC14, D10]`

**Subtask 7 — the concurrency suite (AC5, AC6, AC7, AC10).** Location `internal/world/race_test.go`, run under `-race`, each case with its own maze on a shared schema pool, fanning out through `errgroup` so a goroutine's error reaches the test.

- **AC5:** two goroutines create two adjacent chunks at the same moment; when both return, walk the shared border and assert every face pair agrees. Repeat over several adjacent pairs so the case does not rest on one direction. `[derived → AC5]`
- **AC6:** many goroutines call `EnsureChunkAt` for the same **absent** chunk; assert exactly one `chunk` row, exactly one `chunk_created` event, and identical returned maps. Then the same fan-out against an **already existing** chunk; assert the row's blob, type and cause unchanged and no event added. `[derived → AC6, AC15]`
- **AC7:** open a caller transaction, write in it, call `EnsureChunkAt` from inside that scope, roll the caller's transaction back, and assert the chunk row and its event are both still there. This is also the case that exercises the two-connections-at-once shape § Risks names. `[derived → AC7]`
- **AC10:** two goroutines activate two different chats in one maze; assert two distinct gate chunks at `ChunkDistance` of at least `k+1` from each other, over a table of `k` values, and that each chat holds exactly one gate row. `[derived → AC10, AC9]`
