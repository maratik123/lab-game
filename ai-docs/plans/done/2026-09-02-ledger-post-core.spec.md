# Ledger core — `store.Post`: double-entry postings with a global World account

**Source:** user description (free-text entry)
**Date:** 2026-09-02
**Tracked in:** none — owner's decision, 2026-09-02

Implement the quantitative ledger's write path as `docs/DESIGN.md` §11
«Учетная машина: двойная запись с глобальным счетом» specifies it — the schema
by forward migrations, the owner/scope/account catalog the owner designed on
top of it, and `store.Post`, the only way a balance moves. **Implement as
written; do not redesign §11** — the owner's instruction and the `AGENTS.md`
§ Project AXIOM (`docs/DESIGN.md` is decisions). Four §11 lines are edited in
this PR, each by an explicit owner decision — `:327` / `:331` (the player
operation, KD-29) and, after a propagation sweep, `:313` / `:323` (the
singular table name and the same rename, KD-24 / KD-29); Scope 11 states the
class those edits belong to.

Everything §11 layers on top — day close, retention, the item machine, holds,
faucet/sink metrics, the scheduler — is a later task and appears here only
under *Out of scope*.

## Scope

1. **Schema, by forward migration** — the owner's model, as approved
   («готово, можно продолжать», 2026-09-02). Every migration is a new file; a
   merged migration is never edited (`AGENTS.md:92`, the data-contract
   carve-out). The DDL below is the approved sketch **verbatim**; it was
   applied unchanged to a `docker.io/library/postgres:18` container on
   2026-09-02 (PostgreSQL 18.6, Debian build) and every constraint in it was
   exercised — see *Technical constraints*.

   ```sql
   CREATE TYPE owner_kind       AS ENUM ('world', 'player', 'chat');
   CREATE TYPE ledger_kind      AS ENUM ('money', 'experience');
   CREATE TYPE operation_source AS ENUM ('telegram');

   CREATE TABLE owner (
       id          bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
       kind        owner_kind  NOT NULL,
       telegram_id bigint,                                          -- player / chat only
       created_at  timestamptz NOT NULL DEFAULT now()
   );
   CREATE UNIQUE INDEX owner_kind_telegram_id_key ON owner (kind, telegram_id) WHERE telegram_id IS NOT NULL;
   CREATE UNIQUE INDEX owner_single_world_key     ON owner ((true))            WHERE kind = 'world';

   CREATE TABLE scope_definition (
       id         smallint   PRIMARY KEY,
       code       text       NOT NULL UNIQUE,
       owner_kind owner_kind NOT NULL
   );
   CREATE TABLE account_definition (
       id                  smallint    PRIMARY KEY,
       scope_definition_id smallint    NOT NULL REFERENCES scope_definition (id),
       code                text        NOT NULL,
       kind                ledger_kind NOT NULL,
       controlled          boolean     NOT NULL,
       CONSTRAINT account_definition_scope_code_key UNIQUE (scope_definition_id, code)   -- covers the FK
   );

   CREATE TABLE scope (
       id                  bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
       owner_id            bigint      NOT NULL REFERENCES owner (id),
       scope_definition_id smallint    NOT NULL REFERENCES scope_definition (id),
       created_at          timestamptz NOT NULL DEFAULT now(),
       CONSTRAINT scope_singleton_key UNIQUE (owner_id, scope_definition_id)   -- singleton + covers owner FK
   );
   CREATE INDEX scope_definition_idx ON scope (scope_definition_id);          -- covers definition FK

   CREATE TABLE account (
       id                    bigint      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
       scope_id              bigint      NOT NULL REFERENCES scope (id),
       account_definition_id smallint    NOT NULL REFERENCES account_definition (id),
       created_at            timestamptz NOT NULL DEFAULT now(),
       CONSTRAINT account_scope_definition_key UNIQUE (scope_id, account_definition_id)   -- one per scope + covers scope FK
   );
   CREATE INDEX account_definition_idx ON account (account_definition_id);               -- covers definition FK

   CREATE TABLE account_balance (
       account_id bigint        PRIMARY KEY REFERENCES account (id),
       balance    numeric(30,5) NOT NULL DEFAULT 0,
       CONSTRAINT account_balance_nonnegative CHECK (balance >= 0)
   );

   CREATE TABLE player_operation (
       id           bigint           GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
       source       operation_source NOT NULL,
       operation_id text             NOT NULL,
       created_at   timestamptz      NOT NULL DEFAULT now(),
       CONSTRAINT player_operation_source_operation_id_key UNIQUE (source, operation_id)
   );
   CREATE TABLE manual_correction (
       id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
       actor      text        NOT NULL,
       reason     text        NOT NULL,
       created_at timestamptz NOT NULL DEFAULT now()
   );

   CREATE TABLE journal_entry (
       id                   bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
       ts                   timestamptz NOT NULL DEFAULT now(),
       player_operation_id  bigint      REFERENCES player_operation (id),
       manual_correction_id bigint      REFERENCES manual_correction (id),
       CONSTRAINT journal_entry_exactly_one_basis CHECK (num_nonnulls(player_operation_id, manual_correction_id) = 1)
   );
   CREATE UNIQUE INDEX journal_entry_player_operation_key  ON journal_entry (player_operation_id)  WHERE player_operation_id  IS NOT NULL;
   CREATE UNIQUE INDEX journal_entry_manual_correction_key ON journal_entry (manual_correction_id) WHERE manual_correction_id IS NOT NULL;
   CREATE INDEX journal_entry_ts_idx ON journal_entry (ts);

   CREATE TABLE posting (
       id               bigint        GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
       journal_entry_id bigint        NOT NULL REFERENCES journal_entry (id),
       account_id       bigint        NOT NULL REFERENCES account (id),
       amount           numeric(30,5) NOT NULL,
       CONSTRAINT posting_amount_nonzero CHECK (amount <> 0)
   );
   CREATE INDEX posting_journal_entry_idx ON posting (journal_entry_id);
   CREATE INDEX posting_account_idx       ON posting (account_id);

   INSERT INTO scope_definition (id, code, owner_kind) VALUES (1, 'world', 'world'), (2, 'attributes', 'player');
   INSERT INTO account_definition (id, scope_definition_id, code, kind, controlled) VALUES
       (1, 1, 'money', 'money', false), (2, 1, 'experience', 'experience', false),
       (3, 2, 'money', 'money', true),  (4, 2, 'experience', 'experience', true);
   INSERT INTO owner   (id, kind)                            VALUES (1, 'world');
   INSERT INTO scope   (id, owner_id, scope_definition_id)   VALUES (1, 1, 1);
   INSERT INTO account (id, scope_id, account_definition_id) VALUES (1, 1, 1), (2, 1, 2);
   SELECT setval(pg_get_serial_sequence('owner',   'id'), 1, true);
   SELECT setval(pg_get_serial_sequence('scope',   'id'), 1, true);
   SELECT setval(pg_get_serial_sequence('account', 'id'), 2, true);
   ```

   How the pieces map onto §11, and what each decision fixes:
   - **`owner`** — the address space of §11 («одно пространство адресов»,
     `docs/DESIGN.md:338`): `kind` is the enum `owner_kind` (`world`, `player`,
     `chat` — open, extended by `ALTER TYPE … ADD VALUE`), `telegram_id` keys
     players and chats, a partial unique index makes the pair unique where
     present, and `owner_single_world_key` makes the World a singleton. Future
     holders — corpse, construction, door (`:338`, `:92`) — carry `owner_id`
     in **their own** domain tables; `owner` never gains a per-kind column
     (KD-19).
   - **`scope_definition` / `account_definition`** — two seeded catalogs
     (KD-18, KD-23): a scope definition names a scope and which owner kind
     has it; an account definition names an account inside a scope, its
     `ledger_kind`, and whether it is **controlled** (`:318-319`). Controlled-
     ness therefore comes from the catalog, never from the caller (KD-28).
     Seeded now: the World scope with uncontrolled `money` / `experience`
     accounts, and the player scope `attributes` («характеристики») with
     controlled `money` / `experience` — «Только то, у чего есть kind».
   - **`scope` / `account`** — instances per owner, singleton per
     `(owner, scope_definition)` and per `(scope, account_definition)`
     (KD-20). Plain single-column FKs; no composite FK, no trigger, no
     move-control anywhere (KD-21).
   - **`account_balance`** — rows **only** for controlled accounts, created
     with the owner at zero (`NOT NULL DEFAULT 0`, KD-28); never for World
     (`:319`, `:346`). `CHECK (balance >= 0)` is the overdraft line (`:318`).
   - **`player_operation`** and **`manual_correction`** — the two basis tables
     of KD-2: the client-initiated player action (`source` is the enum
     `operation_source`, seeded `telegram`; `UNIQUE (source, operation_id)` is
     the idempotency rail, `:327`) and the compensation document with its
     `actor` and `reason` (`:326`, `:329`). Boundary (KD-29): raid-session
     transitions, cron / one-time / recurring tasks, season close stay
     separate basis types per `:331`.
   - **`journal_entry`** — the transaction (owner's name, KD-24): carries the
     timestamp (KD-25) and the **exclusive arc** `CHECK (num_nonnulls(…) = 1)`
     with a real FK per basis type (`:323`); each document has **at most one**
     entry, enforced by the partial unique index per FK column (KD-22).
   - **`posting`** — the half-entry: `(journal_entry_id, account_id, amount)`,
     `amount <> 0`. It carries **no kind** (the kind is the account's, via
     `account_definition`) and **no basis columns** (they are the entry's):
     «проводке остаются счет/amount/ссылка» (`:326`).
   - **Identity columns** (KD-27): `GENERATED BY DEFAULT` where a migration
     seeds explicit ids (`owner`, `scope`, `account`), `GENERATED ALWAYS` on
     everything only Post writes.
   - **Naming** (KD-24): singular tables; none of these names is a PostgreSQL
     keyword (measured).
   - **Every FK is index-covered** (KD-26) — the comments in the DDL name the
     covering index; a migration test proves it (AC17).
   - **Enums are forward-only contracts** (KD-15, `AGENTS.md:92`): a new
     member is its own migration (`ALTER TYPE … ADD VALUE`, committed before
     any use), never `RENAME VALUE`, never `DROP VALUE`.
2. **Migration tooling — goose** (KD-1): SQL files embedded with `embed.FS`,
   applied through goose's `fs.FS` provider against a `*sql.DB` bridged from
   pgx. A library entry point applies all pending migrations forward to a
   given database; the tests call it; `cmd/bot` wiring is out of scope.
   Forward-only — no `-- +goose Down` sections (KD-13).
3. **Owner creation from the catalog** — a `store` function (name is design's)
   that, in one transaction, creates an owner of a given kind (with its
   `telegram_id` where the kind has one), its scopes — every
   `scope_definition` whose `owner_kind` matches — its accounts — every
   `account_definition` of those scopes — and a zero `account_balance` row
   for each **controlled** account. Compatibility «owner kind ↔ scope» is
   simply what this function does; nothing controls a move afterwards
   (KD-21). The World is seeded by migration, not created by this function.
   Tests create players through it. Measured: the catalog walk yields for a
   player exactly two controlled accounts with `0.00000` rows and, for the
   seeded World, two uncontrolled accounts with **no** rows.
4. **`store.Post`** — package `store` under `internal/`
   (`ai-docs/code-style.md:7`; KD-12), signature shape
   `Post(ctx, tx, basis, postings...) error` [source:
   `ai-docs/go-api-naming.md:26`; `docs/DESIGN.md:320`]; a posting is
   **`(account_id, amount)` only** — «wrong kind on wrong account» is
   unrepresentable. The caller owns the transaction; Post neither commits
   nor rolls back. Inside one call, in this order (`:324`):
   a. **Static shape check, before any SQL**: the batch is non-empty (KD-6),
      every amount is non-zero and exactly representable at scale 5 (KD-5),
      every `account_id` appears with a valid amount; a batch failing any
      test is rejected and nothing is written.
   b. **One SELECT** over the batch's distinct accounts returns each
      account's `ledger_kind` and `controlled` flag (through
      `account_definition`). An unknown account is a rejection with nothing
      written (a SELECT writes nothing).
   c. **Zero-sum per kind** (`:314`), computed in exact decimal arithmetic
      from the kinds just read; an unbalanced batch is rejected, nothing
      written.
   d. **INSERT the basis document** from the `PostingBasis` value, then
      **INSERT the `journal_entry`** referencing it through exactly one FK
      column.
   e. **UPDATE balances** of the touched **controlled** accounts —
      deduplicated (deltas summed per account, exactly), sorted by
      `account_id` (one axis — the capture order of `:320` collapses to it),
      **one plain `UPDATE … SET balance = balance + $delta WHERE account_id =
      $1` per account**, in that order; never an upsert, never a sign split,
      never a multi-row `UPDATE` whose lock order the planner picks. **Zero
      rows affected is a broken invariant** — a controlled account without
      its balance row — surfaced as an infrastructure error, never as
      overdraft (KD-28). Uncontrolled accounts (World) get no statement.
   f. **INSERT the postings**, each referencing the entry.
   Both deadlock disciplines are Post's, never the caller's (`:320`;
   `ai-docs/domain-invariants.md:18`).
5. **`PostingBasis` sum type** — a Go interface with one implementation per
   basis table (two: `PlayerOperation`, `ManualCorrection`); the mapping to
   the `journal_entry` FK column lives inside Post (`:325`). A posting batch
   without a basis, or with two, must be **unrepresentable at compile time**;
   the `CHECK` is the second line.
6. **Typed outcomes** a handler can branch on with `errors.Is`
   (`ai-docs/code-style.md` § Errors): unbalanced batch; empty batch;
   unrepresentable amount (zero, excess scale, beyond 25 integer digits);
   unknown account; replayed player operation — no document, no entry, no
   postings, the sentinel says "already posted" (`:327`); overdraft on a
   controlled account — the database's `CHECK` violation (`23514`) surfaced
   as a domain rejection. A missing balance row is an **infrastructure**
   error, distinguishable from all of these. Names are design's.
7. **Append-only history — enforced in code only** (KD-3): no code path in
   `store` issues `UPDATE` or `DELETE` against `posting` or `journal_entry`;
   a correction is a compensating batch under a `manual_correction` document
   (`:329`). The database stays permissive (no trigger, no role grant); the
   criterion is AC9's grep with its positive control.
8. **Tests — TDD, Postgres tested against Postgres** (`AGENTS.md:302`;
   `ai-docs/go-test-conventions.md:42-44`), in a `postgres:18` container
   (KD-16, KD-30). The owner's four families plus what the schema needs:
   - property test of the zero invariant, written against `rapid` (KD-17):
     generated balanced batches of scale-5 decimals over accounts of both
     seeded kinds (player `attributes` accounts and World accounts) pass; any
     single-`amount` mutation of a passing batch is rejected and leaves no
     row behind. The library supplies the framework and the shrinking; the
     ledger's rules stay this spec's, the generator's bands are design's;
   - anti-deadlock: parallel `Post`s over **overlapping** controlled account
     sets complete without deadlock, under `-race`. Reference shape is §11's
     stress case [source: `docs/DESIGN.md:345`]: «крафт» — N debits plus one
     credit across **3–5 controlled accounts**, concurrently with a second
     operation by the same player;
   - `CHECK`: a debit below zero on a controlled account — integer or
     fractional — is refused by the database; a missing balance row is the
     infrastructure error, not an overdraft;
   - idempotency: the same `(source, operation_id)` posted twice yields one
     document, one entry, one set of postings;
   - exclusive arc and 1:1: a `journal_entry` with zero or two basis
     references is refused; a second entry for the same document is refused;
   - enum contract for all three enums and catalog mirrors (AC16);
   - FK coverage with positive control (AC17); balance-row invariant (AC18);
   - scale and precision edges of `numeric(30, 5)` (AC15);
   - migrations: apply cleanly to an empty database; re-applying is a no-op;
     hygiene — no `Down`, no `RENAME VALUE`, no `DROP VALUE`;
   - phase and capture order: the observable statement order matches Scope 4
     (one SELECT; document, entry; balance `UPDATE`s ascending by
     `account_id` without repeats; postings).
   Every test owns its data (`go-test-conventions.md:44`).
9. **Test database provisioning — container only** (KD-30): testcontainers-go
   pulls `docker.io/library/postgres:18` (KD-16). A DSN environment variable
   remains as the mechanism by which CI or a developer points the suite at an

   local instance**, and this task exercises the container path only.
   **Never a silent skip**: with neither a reachable container runtime nor a
   DSN, the store tests **fail**. They run inside the existing `make test` /
   `make test-race` gates — no new gate command — and CI's Test job executes
   them.
