## Approach

Implement the spec's approved DDL verbatim as migration 1, expose three library entry points — `Migrate`, `NewPool`, `CreateOwner` — and `Post`, whose six phases are the spec's Scope 4 exactly: a static shape check, one `SELECT` that yields each account's kind and controlled flag from the catalog, the zero-sum check per kind, the document and `journal_entry` inserts, one plain `UPDATE account_balance` per controlled account in ascending `account_id`, and the posting inserts. Nothing in `docs/DESIGN.md` §11 is redesigned; the four §11 lines the owner ordered changed are edited in Russian with the owner's date (D16). This is what shipped: the whole suite is green on the branch `[measured on 809355d: go test -count=1 ./internal/... and go test -race -count=1 ./internal/... → ok for both packages, no failures; wall-clock figures in § Risks]`.

### The shape in one paragraph

`internal/store` exports the Go mirrors `OwnerKind`, `Kind`, `OperationSource` (three enums) and `ScopeDefinition` / `AccountDefinition` (two catalogs), the ids `OwnerID` / `AccountID` with the seeded `WorldOwner`, `WorldMoney`, `WorldExperience`, the types `Owner` / `Account` / `Posting`, the sealed `PostingBasis` with `*PlayerOperation` and `*ManualCorrection`, the `Err…` sentinels of D10, `NewPool`, `Migrate`, `CreateOwner` and `Post` `[measured: go doc ./internal/store → exactly those funcs, types and vars]`. `internal/testdb` provisions the container (or a DSN) and hands each test a schema-scoped pool config; it does not import `store`, so `store`'s in-package tests import it freely. A posting is `(AccountID, Amount)` — the kind is the account's, read from `account_definition` inside `Post`, so «wrong kind on wrong account» is unrepresentable (spec Scope 4).

**Telemetry and balance constants — two explicit non-items.** `Post` and `CreateOwner` are infrastructure, not mechanics: no event, no posting signature (spec KD-11). No tuning value exists in this task: the constants it introduces are structural — representational bounds, pool sizing, timeouts, seeded catalog ids, the database's own labels and error codes, test credentials — not `docs/DESIGN.md` §16.5 balance values. The §16.5 values — stamina cap, step cost, timers, shop rates, the door price curve, `budget(dist)`, combat dice — have no counterpart in this package: `Post` takes its amounts from the caller and its kinds from the catalog, and `CreateOwner` reads the catalog too, so there is nothing here for a season's balance to tune.

**D3 — `store.Migrate(ctx, pool *pgxpool.Pool, logger *slog.Logger) (err error)`.** Bridges the pool with `stdlib.OpenDBFromPool` (closing the `*sql.DB` leaves the pool usable — every test queries the pool after `Migrate` returns), builds `goose.NewProvider(goose.DialectPostgres, db, fs.Sub(migrationsFS, "migrations"), goose.WithSlog(logger))` and calls `Up`; `db.Close()`'s error is joined into the named return with `errors.Join` `[measured: migrate.go as shipped]`. Tests pass `slog.New(slog.DiscardHandler)`. goose creates its version table in the connection's `search_path` schema, which is what makes per-schema tests work `[measured: TestMigrate_shape_and_seeds lists goose_db_version among the schema's tables]`. No session locker (a database-wide advisory lock would serialise unrelated test schemas).

**D4 — Codec registration point: `store.NewPool(ctx, cfg *pgxpool.Config) (*pgxpool.Pool, error)`.** Wraps `cfg.AfterConnect` so every connection runs `pgxdecimal.Register(conn.TypeMap())`, chaining a caller's hook, then `pgxpool.NewWithConfig` `[measured: store.go as shipped]`. Per-call registration is impossible: `Register` prepends wrappers on every call `[measured: pgx-shopspring-decimal decimal.go, Register body]`. Precondition, documented on `NewPool`: `cfg` from `pgxpool.ParseConfig` — pgxpool itself panics otherwise `[measured: pgxpool/pool.go, NewWithConfig's createdByParseConfig check]`; every caller (`testdb.Schema`, the tests) obtains it that way, so `ai-docs/panic-index.md` stays empty. Enum labels travel as text through named Go string types with no `LoadType`; a named `int64` and a slice of it encode as `bigint` / `bigint[]` `[measured: the shipped tests bind OwnerKind / Kind / AccountID / []AccountID as parameters and scan them back]`. The codec round-trips `numeric(30,5)` digit for digit against pgx v5.10.0 + shopspring v1.4.0 `[measured: TestPost_numeric_edges/25_digit_amount_round_trips → amount::text equals the input's String()]`.

**D5 — Amount representation and scale normalisation.** `Posting.Amount` is `decimal.Decimal`; `store` never re-scales. `validAmount` is by value: non-zero, `a.Truncate(5).Equal(a)`, `a.Abs().LessThan(maxIntegerDigitsBound)` with `maxIntegerDigitsBound = decimal.New(1, 25)` `[measured: post.go as shipped]`. Comparisons use `Equal` / `IsZero`, never `==`. `22003` is unreachable through `posting.amount` (rejected in phase a — `TestPost_numeric_edges`, `TestPost_sentinels/excess_magnitude_amount`) but **reachable through `account_balance.balance`**, which accumulates; it is wrapped, not sentinelled — a capacity limit of the persisted type, not a game rule — and `Post`'s doc comment says so `[measured, session-local probe: a credit to 25 nines succeeds, then +1 raises 22003; durable record: spec KD-5]`. AC2's generator is bounded structurally so the property never depends on it. **`decimal.RequireFromString` and every `Must…`/`Require…` are forbidden in non-test `store` code** — a panic the `panic-gate` hook cannot see `[measured: grep -rn 'Require\|Must' internal/store --include='*.go' | grep -v _test.go → no hits]`.

**D6 — Go mirrors of three enums and two catalogs, and how they are used.** `type OwnerKind string` (`OwnerWorld`, `OwnerPlayer`, `OwnerChat`) with an unexported `known()` used by `CreateOwner`'s pre-SQL rule; `type Kind string` (`KindMoney`, `KindExperience`) and `type OperationSource string` (`SourceTelegram`) with unexported member slices (`kinds`, `operationSources`) that exist for AC16's equality test only — **only `OwnerKind` has `known()`**, because nothing in `store` validates a kind or a source in Go: the database enum does, and `Post` never receives a kind from the caller `[measured: enums.go as shipped]`. `type ScopeDefinition struct { ID int16; Code string; OwnerKind OwnerKind }` and `type AccountDefinition struct { ID, ScopeDefinitionID int16; Code string; Kind Kind; Controlled bool }` with unexported seeded slices `scopeDefinitions` / `accountDefinitions` mirroring the migration rows exactly `[measured: catalog.go; TestCatalog_mirrors_database compares them with the tables field by field]`. Nothing in `store` decides controlled-ness or kind from a mirror — both come from the database rows `Post` and `CreateOwner` read (KD-28), so a mirror that drifts fails AC16, never a balance. **Comparison rule for the capture order** is one axis, `account_id` ascending as an integer (spec Scope 4e); no `kind` ordering exists anywhere in `Post`. No `switch` over a mirror exists in non-test code (`createPlayer` in the tests switches on `Kind` to pick an account) `[measured: grep -n 'switch' internal/store/*.go | grep -v _test.go → only CreateOwner's tagless switch on conditions]`.

**D7 — Ids and the seeded World.** `type OwnerID int64`, `type AccountID int64` (distinct from Telegram ids, also `int64`); `WorldOwner OwnerID = 1`, `WorldMoney AccountID = 1`, `WorldExperience AccountID = 2` — the migration's seeded ids `[measured: ids.go; TestMigrate_shape_and_seeds → the seeded owner is the World; TestPost_world_may_go_negative sums posting.amount for WorldMoney]`.

**D8 — `PostingBasis`, sealed, two unexported methods, total under nil before any SQL.** `type PostingBasis interface { entrySQL() (string, error); insert(ctx context.Context, tx pgx.Tx) (int64, error) }`. `entrySQL` issues no SQL: it returns this type's constant `INSERT INTO journal_entry (<its FK column>) VALUES ($1) RETURNING id`, or `ErrNoBasis` on a nil receiver — the no-SQL method that keeps a typed-nil `(*PlayerOperation)(nil)` (which is `!= nil` as an interface) in the pre-SQL family. `insert` writes the document and returns its id: `PlayerOperation{Source OperationSource; OperationID string}` uses `INSERT INTO player_operation … ON CONFLICT (source, operation_id) DO NOTHING RETURNING id`, and `pgx.ErrNoRows` from `Scan` is a replay → `ErrAlreadyPosted` with the transaction still healthy; `ManualCorrection{Actor, Reason string}` inserts plainly. Both use **pointer receivers** with nil guards on **both** methods `[measured: basis.go; TestBasis_nil_returns_ErrNoBasis_without_panicking → entrySQL and insert on both typed-nils return ErrNoBasis, and the typed-nil stored in the interface is != nil; TestPlayerOperation_insert_replay_returns_ErrAlreadyPosted → replay returns the sentinel and SELECT 1 still succeeds]`. The FK-column mapping is two constants inside `store` (spec Scope 5). `OperationID` is opaque to `store` (§ Open questions).
