# Design: World generation rework — hexagonal chunks on a super-lattice

**Issue:** #119
**Date:** 2026-09-14

## Approach

The shipped core generates per coordinate over rhombic chunks. `hexgrid.Dims{Cols, Rows}` maps a cell to its chunk by floor division, and `maze.Generator.Cell(coord)` builds the whole chunk and reads six faces. `Cell` asks a `PrefabClaimer` first, and every border carries one or two portals `[measured 3fff413:internal/hexgrid/chunk.go:11-45 · Read → Dims{Cols,Rows}, ChunkOf by floorDiv32] [measured 3fff413:internal/maze/generate.go:21-125 · Read → New(seed, params, claimer); Cell(coord) builds own chunk then reads faces] [measured 3fff413:internal/maze/portal.go:33-52 · Read → count := boundedDraw(s, 2) + 1]`.

The amended `docs/DESIGN.md` §2.2.2 changes what generation's unit is, not only the chunk's shape. A chunk is generated once and stored with its generation version. Its fabric depends on its type. Its border with an existing neighbour comes from that neighbour's stored map. A per-coordinate `Cell(coord)` that is a function of `(seed, coord)` alone cannot express any of that. So the rework keeps the pure pipeline shared by all generation passes: the key chain, the draw reductions, the spanning-structure algorithms and the cycle pass. It replaces the entry point with a **chunk-level** one that returns a chunk map, and it adds a validating constructor through which a stored map becomes a `Map` again.

### Key decisions

| # | Decision | Why / rejected alternatives |
|---|---|---|
| D1 | **The super-lattice geometry.** `hexgrid.Chunk` stays an axial `(Q, R)` pair, now read as a coordinate *on the super-lattice*. Chunk `(i, j)` has its centre at cell `i·(2R+1, −R) + j·(R, R+1)` in axial coordinates. So the super-lattice is itself an axial hex lattice. A chunk's six neighbours use the same six direction deltas as a cell's (`Chunk.Neighbor(d)`), and the existing `ChunkDistance` formula stays correct on it. A chunk holds exactly the cells within hex distance R of its centre, `3R²+3R+1` of them. Each of its six borders is `2R+1` faces, and those faces form one contiguous path from one three-chunk corner to the other. | These are DESIGN §2.2.2's hexagon-of-hexagons tiling written in this package's coordinates. A scratch enumeration confirmed them for small radii before they went into this design. The implementation's own tests establish them `[derived → AC1, AC2, AC5 tests in internal/hexgrid/lattice_test.go]`. Rejected: a new chunk-coordinate type per lattice. `Chunk` already is an axial pair, and a second one would only duplicate `Neighbor` and the distance. |
| D2 | **The mapping is a hand-roll, argued.** The standard library has no hex topology. Of the packages the search found: `github.com/pmcxs/hexgrid` is a 2019 pseudo-version with no hexagon-of-hexagons mapping, no local coordinate and no border enumeration, and its pixel conversions are `float64` `[measured 2026-09-14:https://pkg.go.dev/github.com/pmcxs/hexgrid · WebFetch → no super-hex API, NewFractionalHex(float64), v0.0.0-20190126]`. `github.com/gravitton/hexagon` v1.4.0 likewise has no chunk mapping and no edge enumeration between larger hexagons, and its `FractionalHex` is `float64` `[measured 2026-09-14:https://pkg.go.dev/github.com/gravitton/hexagon · WebFetch → no hierarchical/chunking features; FractionalHex float64]`. Search also returned further `hexgrid` modules described as ports of the Red Blob Games implementation guide. None was inspected, and the guide's own treatment of chunking only links to a notebook by Sander Evers `[measured 2026-09-14:https://www.redblobgames.com/grids/hexagons/ · WebFetch → "Sander Evers has a nice explanation of how to combine small hexagons into a grid of large hexagons"]`. That notebook refused the fetch (see § Open questions). | This is the `AGENTS.md` § Dependency Versions standard for an argued wheel. The mismatch is specific: no package inspected offers the hexagon-of-hexagons mapping or a border's face enumeration, which is the whole requirement. The one primitive such a package could supply is the axial distance, a one-line formula `hexgrid` already carries in `ChunkDistance` `[measured 3fff413:internal/hexgrid/chunk.go:47-55 · Read → (|dq|+|dr|+|dq+dr|)/2]`. Importing a module for it would add a coordinate type beside `hexgrid.Coord` and a float path the determinism guard would have to police. Escape hatch: `hexgrid.Lattice` is the single seam. An established package that gains an integer super-lattice mapping replaces its method bodies without touching `maze`. |
| D3 | **`Locate` is integer-only and exact.** Solve for the chunk index with the inverse super-basis in `int64`: `i* = ((R+1)q − R·r) / N` and `j* = (R·q + (2R+1)·r) / N`, both floor-divided, with `N = 3R²+3R+1`. Then take whichever of the four chunks `(i*+di, j*+dj)`, `di, dj ∈ {0, 1}`, has its centre within distance R. The local coordinate is the cell minus that centre, computed in `int64`. Its inverse, `At(chunk, local)`, adds in `int64` and converts back, so the round trip is exact for every `int32` coordinate. | `internal/detguard` bans `math` and floats on this path `[measured 3fff413:internal/detguard/detguard.go · Read → bannedImports includes "math"; bare float32/float64 banned]`. Why four candidates and not a closed form: the candidate set is checkable. In a scratch probe it located every cell exactly once, and a one-candidate mutant of the same probe failed. The tests are what establish it for the code `[derived → AC1 exhaustive and rapid round-trip tests]`. `int64` is the natural width for the products, not a provision for the seam (D4). Rejected: rounding in cube coordinates, which needs fractional arithmetic; and searching all chunks near the cell, which does the same job with more candidates. |
| D4 | **The `int32` seam is not designed for.** The owner ruled that a design provides for what the game reaches, not for what it never will [answer 5.2: "Может, оценивать реально? Зачем закладывать то, что никогда не будет достигнуто?"]. The seam lies more than 2³¹ cells from the world centre, where gates spiral from (DESIGN §2.2). So AC1, AC2 and AC3 are designed and tested over the world around its centre. Nothing here promises what a chunk, a face or a distance does across the seam, and no stage adds code for it. `Coord.Neighbor` keeps its defined wrapping `[measured 3fff413:internal/hexgrid/coord.go:58-64 · Read → "Arithmetic at the domain's extremes wraps"]`, and a `Map` answers faces in its own local frame. | Answer 5.2 settles the review's point on the seam; it is not re-raised. Rejected: making the seam agree. That needs a modulus the lattice divides, which means changing `Coord`'s width, and the owner ruled the case unrealistic. |
| D5 | **Border enumeration lives in `hexgrid`, in a chunk's local frame, in path order.** `Lattice.Border(d)` returns the `2R+1` canonical `Face`s between a chunk centred at the origin and its neighbour in direction `d`, ordered along the border path. For `d ∈ {DirE, DirNE, DirNW}` (the directions `FaceOf` treats as canonical) the list is built directly, and it runs from the three-chunk corner shared with the neighbour in the previous canonical direction to the corner shared with the neighbour in the next one. For the opposite three, the list is the opposite direction's list translated by `Lattice.Offset(d)`, in the same order. Seen from the chunk's own side, that order runs the other way: from the corner shared with the neighbour in the *next* canonical direction to the corner shared with the *previous* one. For `DirW`, that is from the `DirSW` corner to the `DirNW` corner. So both chunks of a border enumerate identical faces in identical order by construction. | This is topology with no seed, so it belongs to `hexgrid` (KD-38's split). A local frame keeps enumeration clear of the seam (D4). Path order means *consecutive in the list* coincides with *sharing a vertex*. That makes the non-touching rule (D6) a rule over list positions, and the tests check it against an independent vertex predicate, not against the order itself. Two chunks walk their shared border in opposite rotational senses, so a single previous-to-next rule for all six directions cannot also give both sides one order. That is why the rule is stated for the canonical three only. |
| D6 | **The portal rule.** A border of `L = 2R+1` faces reads two bounds: `lo = ⌈PortalShareLower × L⌉` and `hi = ⌈PortalShareUpper × L⌉`, using `decimal.Ceil` `[measured 3fff413:go doc github.com/shopspring/decimal Decimal.Ceil → "Ceil returns the nearest integer value greater than or equal to d"]`. From the border's own stream (`borderKey`, unchanged `[measured 3fff413:internal/maze/seed.go:112-119 · Read → canonical-ordered chunk pair]`), the rule draws `count = lo + boundedDraw(s, hi−lo+1)`. It then places `count` pairwise non-consecutive positions using the standard bijection: shuffle positions `0..L−count` from the same stream, take the first `count`, sort them ascending (`sort.Ints`), and add each one's rank. `New` refuses: either share outside `[0, 1]`; lower above upper; `lo < 1`, because a border with no portal breaks world connectivity; and `hi > R+1`, because more non-touching positions do not exist on a path of `L` faces. Each rejection names the input it refuses. | `docs/DESIGN.md` §2.2.2 fixes the count range, the rounding up and non-touching within one border. The bijection is exact and uniform over non-touching placements with no rejection loop, and it is integer-only. Rejected: rejection sampling of placements, which has an unbounded draw count. Also rejected: a greedy skip-next-face walk, which biases toward the start of the path. The border's inputs are seed, generation inputs and the two chunks only: no chunk type, no third chunk `[derived → AC8 test]`. |
| D7 | **Island candidates for the hexagon.** A candidate is a local cell at distance ≤ R−1 from the centre, since a border cell has at least one face leaving the chunk. In a gate chunk the centre is also excluded. The target keeps KD-40's denominator: `round(IslandShare × 3R²+3R+1)` using the existing `floor(x+½)` rounding. The connectivity guard stays unchanged, flooding over the chunk-induced subgraph from a border cell, which is never an island `[measured 3fff413:internal/maze/island.go:22-82 · Read → candidates non-border, shuffled, guard flood from firstBorder]`. `New` checks capacity against the *gate* chunk's smaller count, `3R²−3R`, so one valid input is valid for every chunk type. The degenerate-shape rejection goes away: at R ≥ 6 a chunk always has non-border cells `[measured 3fff413:internal/maze/params.go:55-58 · Read → capacity == 0 && IslandShare.IsPositive() rejection]`. | Implements §2.2.2 as amended (islands never touch a border; the gate cell is never an island; D29, D30). The gate centre stays reachable because the spanning structure spans every non-island cell `[derived → AC10 test]`. Rejected: checking capacity per chunk type at generation time. It would turn a generation-input error into a per-call error that `New` could have refused once. |
| D8 | **`maze.ChunkType` is a closed Go enum over an open persisted set.** `ChunkTypeFabric` and `ChunkTypeGate`, with a **zero value that is not a type**. `Generate` and `NewMap` (D9) refuse the zero value and any value they do not know, naming it. `String()` renders `fabric` / `gate`. | A zero-valued `ChunkType` field forgotten by a caller would otherwise silently generate fabric, and the gate's centre could become an island. Post-MVP types (boss area, ruins; DESIGN §2.2.4) add members. `exhaustive` runs with `default-signifies-exhaustive` `[measured 3fff413:.golangci.yml:44-45 · Read → default-signifies-exhaustive: true]`, so a switch over `ChunkType` must be total or carry a `default`. |
| D9 | **The chunk-level entry point, and the way back from storage.** `New(seed int64, params Params) (*Generator, error)` validates once. `(*Generator).Generate(ch hexgrid.Chunk, typ ChunkType, neighbors ...Map) (Map, error)` builds one chunk in a pinned pass order: islands (island stream) → algorithm draw → spanning structure → extra passages → the six borders in canonical direction order. A border comes from the matching neighbour's map when one is supplied, otherwise from the portal rule. The `Map` value exposes `Version() int32`, `Chunk() hexgrid.Chunk`, `Type() ChunkType`, `Radius() int32` and `Faces(local hexgrid.Coord) ([6]FaceState, bool)`. `ok` is false outside distance R. A border face reads the border's state. `Generate` refuses a supplied map that is not adjacent to `ch`, a map for `ch` itself, a map at a different radius, and two maps for the same neighbour, naming each. Its result does not depend on the order of `neighbors`. **`NewMap(ch hexgrid.Chunk, typ ChunkType, version int32, faces [][6]FaceState) (Map, error)`** rebuilds a `Map` from what a stored map holds: the chunk, its type, its generation version, and each cell's six face states in `LocalCells` order. The radius is the one whose cell count equals `len(faces)`. `NewMap` copies `faces`, and it refuses, naming each: an unknown or zero type; a version below 1; a length that is not the cell count of a hexagon of radius `MinRadius` or more; a face state that is neither wall nor passage; and an interior face on which the two cells it joins disagree, naming both local coordinates and the direction. Faces leaving the chunk are taken as given. `Generate` does not distinguish a constructed map from a generated one, so the neighbour checks above apply to both. `(*Generator).CellSeed(c hexgrid.Coord) uint64` keeps the per-cell content seed that `Cell.Seed` carried `[measured 3fff413:internal/maze/generate.go:32-39 · Read → Cell{Prefab, Faces, Seed}]`. `Cell` and `chunksConsulted` are deleted. | DESIGN §2.2.2 makes a chunk's map the stored unit and its neighbours' stored maps a generation input. #29 reads a neighbour's map from Postgres, often in a later process and under an older `Version`. Without a constructor its only route to a `Map` would be regenerating the neighbour. That is the "deriving it again" Scope 7 excludes, and it gives the wrong border once `Version` moves. `NewMap` is an in-memory contract, not a storage encoding. It fixes no byte layout, column or field name, and its only order is `LocalCells`, which `hexgrid` already owns (D13). How the map is stored stays #29's, as the spec's second key decision requires. The radius comes from the length so that no two `int32` arguments sit side by side where a swap would compile. Taking neighbour `Map`s rather than raw border slices lets `Generate` check adjacency and radius, so a border cannot land on the wrong side. Rejected: an exported `Border` value with its own constructor. It would make a border's in-memory shape a second contract beside the map's, and #29 stores whole maps. Rejected: keeping `Cell(coord)` beside `Generate`. It cannot be a function of `(seed, coord)` once type and stored borders are inputs (clean break, `AGENTS.md` § API Stability). Rejected: `NewMap` checking islands, portal counts or connectivity. A stored map from another `Version` may follow other rules, and AC14 takes its border as it is. |
| D10 | **The generation version is an exported `maze.Version int32 = 1`, separate from the hash-chain domain tag.** Every generated `Map` carries it. `domainTag` stays `"lab-game/maze/v1"` `[measured 3fff413:internal/maze/seed.go:10-13 · Read → const domainTag = "lab-game/maze/v1"]`. Every bump would then re-key `cellSeed`, and so re-roll the content of already-stored chunks for whatever layer samples content from it (#34), which is not this task's decision to make. Rejected: tying the tag to `Version` by formatting, for the same reason. |
| D11 | **The prefab hook is removed.** `PrefabClaimer`, `New`'s claimer argument, `Cell.Prefab` and `FaceDeferred` go `[measured 3fff413:internal/maze/prefab.go:5-19 · Read → type PrefabClaimer interface] [measured 3fff413:internal/maze/algorithm.go:71-82 · Read → FaceDeferred FaceState = iota]`. `FaceState` becomes `FaceWall` (zero) and `FacePassage`. ## Test Design

Every claim in this section is about a test this task writes: `[derived → the test named]`.

### `internal/hexgrid` (subtask 1)

- **`TestLattice_LocateRoundTripsAndPartitions` (AC1)** — exhaustive over a region of several chunk diameters around the origin at R ∈ {6, 7, 9}. `Locate` returns a local coordinate at distance ≤ R. `At` returns the original cell. A brute-force scan over a wide chunk window finds exactly one chunk whose centre lies within R, and it equals `Locate`'s. Every cell `At(ch, l)` for `l` in `LocalCells()` locates back to `(ch, l)`, and `LocalCells()` has no duplicate and contains exactly the offsets within R.
- **`TestLattice_LocateRoundTripsFarFromOrigin` (AC1)** — `rapid` over `int32` coordinates at R ∈ {6, 9}: `At(Locate(c)) == c`. This checks D3's `int64` arithmetic; it promises nothing about the seam (D4).
- **`TestChunk_SixSymmetricNeighboursJoinedByAFace` (AC2)** — over a window of chunks: six distinct neighbours; `n.Neighbor(d.Opposite()) == ch`. Brute force over cells: two chunks are neighbours exactly when some cell of one has a face-neighbour in the other.
- **`TestDistance_EqualsLatticeStepCount` (AC3)** — breadth-first step counts on the open lattice from several sources over a small region equal `Distance`; a hand-computed table; symmetry. Pairs straddling chunk borders at radii 6 and 9 give the same values as pairs within a chunk at equal step count.
- **`TestLattice_BorderHasTwoRPlusOneFacesInOneOrderFromEitherSide` (AC5)** — at R ∈ {6, 7, 9}, for every direction: the list has `2R+1` faces; its set equals a brute-force enumeration of faces joining the chunk to that neighbour; translating the neighbour's `Border(d.Opposite())` by `Offset(d)` gives the identical list, order included; consecutive entries share a vertex under the independent predicate (Risks). For the canonical three directions, the list starts at the corner shared with the previous canonical direction's neighbour. For their opposites, it starts at the corner shared with the next one (D5). The six borders together are every face leaving the chunk, each once.
- `ChunkDistance`'s existing tests stay; the `Dims` tests are deleted in subtask 3.
