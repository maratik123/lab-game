# Design: Posting-signature contract tests

**Issue:** #26
**Date:** 2026-09-15

## Approach

A new package, `internal/contract`, holds the vocabulary a signature is declared in, the declared set itself as one Go table literal, the contract check, and the completeness audit. Only tests import it, so the bot binary does not carry it. The completeness test lives in `cmd/bot`, which is the one package that knows every task type the process declares. It runs under `go test ./...`, so a basis-document type with no signature fails CI's Test job and `make verify`.

**What exists to build on.**
- **Basis tables.** A journal entry references exactly one basis document. The arc columns are:
  - `player_operation_id` and `manual_correction_id` `[measured 037064d:internal/store/migrations/00001_ledger_core.sql:67-73 · Read → CONSTRAINT journal_entry_exactly_one_basis CHECK (num_nonnulls(player_operation_id, manual_correction_id) = 1)]`;
  - `deferred_task_id` and `recurrent_task_id` `[measured 037064d:internal/store/migrations/00002_scheduler.sql:38-44 · grep -n journal_entry → ADD COLUMN deferred_task_id … recurrent_task_id]`;
  - `event_id` `[measured 037064d:internal/store/migrations/00003_event_log.sql:71-76 · Read → num_nonnulls(player_operation_id, manual_correction_id, deferred_task_id, recurrent_task_id, event_id) = 1]`.
- **Types within those tables.**
  - An event's type is a row of `event_type_definition` `[measured 037064d:internal/store/migrations/00003_event_log.sql:14-36 · Read → CREATE TABLE event_type_definition … INSERT … ('bot_added_to_chat' … 'bot_kicked')]`.
  - A task type is Go-only text: `[measured 037064d:internal/scheduler/task.go:11-14 · Read → "The database stores it as text and validates nothing about it; the Registry is the sole authority on which types exist."]`.
  - The composition root declares no task type `[measured 037064d:cmd/bot/assemble.go:284 · Read → taskRegistry, err := scheduler.NewRegistry()]`.
- **Postings.** A posting row carries the journal entry, the account and a non-zero amount `[measured 037064d:internal/store/migrations/00001_ledger_core.sql:78-84 · Read → posting (journal_entry_id, account_id, amount) … CHECK (amount <> 0)]`. An account's definition is unique per scope definition and code, and carries the kind `[measured 037064d:internal/store/migrations/00001_ledger_core.sql:20-27 · Read → account_definition (scope_definition_id, code, kind, controlled) … UNIQUE (scope_definition_id, code)]`.
- **Item movements.** A movement references its journal entry and two holder scopes `[measured 037064d:internal/store/migrations/00007_item_machine.sql:107-120 · Read → item_movement (item_id, prev_movement_id, from_holder_id REFERENCES scope, to_holder_id REFERENCES scope, journal_entry_id)]`.
- **Nothing in production writes under any basis today.** `git grep -n -E '(Post|Move|AppendEvent)\(ctx' -- '*.go' ':!*_test.go'` finds only the definitions of `Post`, `Move` and `AppendEvent` `[measured 037064d:internal/store/post.go:77, internal/store/move.go:86, internal/store/event.go:88 · git grep → func Post / func Move / func AppendEvent only]`. The control line matched the same pattern family: `printf 'x := store.Post(ctx, tx, b)\n' | grep -c 'store\.Post('` → `1`. `git grep -n -E 'PlayerOperation|ManualCorrection|DeferredTask|RecurrentTask|store\.Event\b' -- '*.go' ':!*_test.go' ':!internal/store/*'` finds a comment and no construction `[measured 037064d:internal/scheduler/schedule.go:27 · git grep → "// SQLSTATE 23505, exactly as the ledger's own PlayerOperation basis does,"]`.
- **The design corpus.** It gives signature examples (`craft_succeeded`, `shop_sale`, the manual correction) and calls the structural comparison the economy's contract test `[measured ~/lab-private@48f7c2e:DESIGN.md:302-354 · sed -n 302,354p → «Проводочные сигнатуры по типу документа: … (craft_succeeded: списания ресурсов + зачисление предмета; shop_sale: ресурс↔деньги; ручная коррекция: любая сбалансированная пачка). Структурная сверка … — контрактный тест экономики»]`. It also says both machines' signatures are checked for one document `[measured ~/lab-private@48f7c2e:DESIGN.md:302-354 · sed -n 302,354p → «Один документ → проводки в обеих машинах → обе сигнатуры в контрактном тесте»]`.

### Key decisions

| # | Decision | Why / rejected alternatives |
|---|---|---|
| D1 | **A new package, `internal/contract`, imported only by tests.** Exported surface: <br>• the `DocumentType` with its `Basis`; <br>• the `Signature` forms `Nothing`, `AnyBalanced` and `Expect`; <br>• the `Leg` constructors `PostingLeg` and `MovementLeg`; <br>• `Sign` (`Positive`, `Negative`); <br>• `Cardinality` (`Exactly`, `AtLeast`); <br>• `Declaration`, `Registry`, `NewRegistry` and `Declared`; <br>• `Queryer`, `Mark`, `NewMark` and `(Registry).Check`; <br>• `Catalog`, `TaskType`, `ReadCatalog` and `(Registry).Audit`; <br>• the sentinels `ErrInvalidDeclaration`, `ErrNonconforming`, `ErrNoDocument`, `ErrNoSignature`, `ErrIncomplete`, in the `"contract: …"` form the store's sentinels use `[measured 037064d:internal/store/errors.go:10 · Read → errors.New("store: posting basis is nil")]`. | **The name.** The design corpus's own word is «контрактный тест», and `contract.Signature` does not stutter. `internal/signature` would force `signature.Signature` `[measured 037064d:ai-docs/go-api-naming.md:21 · Read → "No stutter. … The package name is part of the identifier at the call site."]`. <br><br>**Not `internal/store`.** Every mechanic's pull request would edit the ledger package to declare its signature, and the read-back path is test support the binary would then carry. <br><br>**Not a `_test.go` helper per package.** The mechanic issues that depend on #26 each call the check from their own package, so it is a shared package by the ≥3-site rule: in the MVP roadmap issue, the dependency rows of #31, #36, #40, #41 and #45 list #26 (https://github.com/maratik123/lab-game/issues/47, read this turn with `gh issue view 47 --json title,state,body`). <br><br>**Import gate.** The gate's only rule forbids the container runtime under `cmd/bot` `[measured 037064d:cmd/importguard/run.go:38-44 · Read → Package: ".../cmd/bot", ForbiddenPrefixes: testcontainers-go]`, and a test-only import never enters that graph `[derived → subtask 6 verification: go list -deps ./cmd/bot has no internal/contract]`. |
| D2 | **A basis-document type is `DocumentType{Basis, Code}`.** `Basis` names the basis table: `player_operation`, `manual_correction`, `event`, `deferred_task`, `recurrent_task`. `Code` is the event type for `event` and the task type for the two task tables. It is empty for the player operation and the manual correction, which are whole-table types (spec Scope 4, 10). <br>Constructors: `PlayerOperation()`, `ManualCorrection()`, `Event(store.EventType)`, `DeferredTask(code string)`, `RecurrentTask(code string)`. <br>A task type's table is decided by its scheduler declaration: a nil `Recurrence` means `deferred_task`, a non-nil one means `recurrent_task` `[measured 037064d:internal/scheduler/registry.go:20-29 · Read → Declaration{Type, Handler, Recurrence *Recurrence} "Recurrence is non-nil for a recurring task type, nil for a one-shot."]`. | **Task codes are strings** so `contract` does not import `scheduler`. <br><br>**`Basis` values are the table names** so the audit can compare them with the tables the database's arc references, with no second mapping. <br><br>**A type moving between one-shot and recurrent changes its key**, and that shows in the declared set's diff (D8). |
| D3 | **A signature takes one of the forms `Nothing`, `AnyBalanced` and `Expect`, and the zero `Signature` is none of them.** <br>• `Nothing()` is the explicitly empty signature: no posting and no movement may be written. <br>• `AnyBalanced()` admits any postings that sum to zero per kind, and any movements. <br>• `Expect(legs ...Leg)` admits exactly the declared legs. <br>`NewRegistry` refuses: <br>• the zero `Signature`; <br>• `Expect` with no legs, because empty is spelled `Nothing` and only `Nothing`; <br>• `AnyBalanced` on any type other than `ManualCorrection()`. <br>`Registry`'s fields are unexported and `NewRegistry` is its only constructor, so a registry that loosens another type cannot be built. | **An unset or accidental empty cannot pass for "declared empty".** Spec Scope 5 and AC11 ask for an *explicit* empty, and a forgotten entry and an empty entry must not look alike. <br><br>**Confining the permissive form at registry construction** is what makes spec Scope 6 and AC8 structural. The check never meets `AnyBalanced` under another basis, so it carries no dead second guard. Such a guard would be an uncovered branch against the ratchet. |
| D4 | **Legs and matching.** <br>A posting leg is `(scope definition code, account definition code, kind, sign, cardinality)`. An actual posting's key `(scope code, account code, kind, sign)` is read as posting → account → account definition → scope definition, with the sign of its amount. <br>A movement leg is `(from scope definition code, to scope definition code, cardinality)`, and an actual movement's key comes from its two holder scopes. <br>A document conforms to `Expect` when: <br>• for every declared leg, the count of actual rows with its key satisfies its cardinality; <br>• and no actual row has a key that no leg declares. <br>Leg keys are unique within one signature, which `NewRegistry` refuses otherwise. | **Amounts are not in a signature.** They are balance numbers, and the corpus asks for a *structural* comparison. <br><br>**Owner identity is not in a leg.** Two players' `attributes/money` postings match one leg, and the cardinality counts them. <br><br>**Kind is declared although the account definition determines it**, because spec Scope 1 lists it. The audit refuses a leg whose kind disagrees with the catalog (D9). The check matches on the whole key, so a kind-only difference reports as the pair of mismatches D11 defines. <br><br>**The capacity legs `store.Move` derives are ordinary postings, declared explicitly** `[measured 037064d:internal/store/move.go:204-214 · Read → from.free +1, from.used −1, to.free −1, to.used +1]`. The check derives nothing from movements: a checker that re-derived Move's legs would pass a Move defect by construction. |
| D5 | **Cardinality is `Exactly(n)` or `AtLeast(n)`, with `n ≥ 1`.** `NewRegistry` refuses `n < 1`; a leg that may be absent is a leg not declared. | `AtLeast` exists because the corpus's first example, «списания ресурсов», debits as many resources as a recipe names `[measured ~/lab-private@48f7c2e:DESIGN.md:302-354 · sed -n 302,354p → «craft_succeeded: списания ресурсов + зачисление предмета»]`. An upper-bounded range has no example and is not built. |
| D6 | **"The transaction" is every journal entry past a mark.** `NewMark(ctx, q)` reads the greatest `journal_entry.id` visible to `q`. `(Registry).Check(ctx, q, mark, want)` then judges every journal entry visible to `q` with a greater id: <br>• it fails with `ErrNoDocument` when none of them has type `want`, so a mechanic that wrote nothing cannot pass vacuously; <br>• it judges each entry, of `want` or any other type, by the signature of **its own** type, read from the document itself: `event.type`, `deferred_task.task_type`, `recurrent_task.task_type` (AC5); <br>• it fails with `ErrNoSignature` for an entry whose type the registry lacks; <br>• it fails with `ErrNonconforming` for any mismatch. <br>`Check`'s doc comment states, in its precondition part: <br>• no other writer adds journal entries to the schema between `NewMark` and `Check`; <br>• `ErrNonconforming` also covers a document whose postings do not sum to zero per kind (D7), which only a write that bypasses the write path, such as raw SQL, can produce. | **Rejected (a): returning the journal-entry id from the write paths.** Both return no such id today `[measured 037064d:internal/store/post.go:77 · Read → func Post(…) error]` `[measured 037064d:internal/store/move.go:86 · Read → func Move(…) ([]ItemID, error)]`. Changing both for a test's benefit would still leave a scheduler-run handler's entry unreachable by its test. <br><br>**Rejected (b): filtering by `xmin` equal to the current transaction id.** A handler runs under a savepoint `[measured 037064d:internal/scheduler/execute.go:342 · grep -n SAVEPOINT → tx.Exec(ctx, "SAVEPOINT handler")]`, and a subtransaction that writes is assigned an id of its own (https://www.postgresql.org/docs/18/subxacts.html, read this turn: «Read-only subtransactions are not assigned subxids, but once they attempt to write, they will be assigned one.»). Which id a row's `xmin` then carries is Postgres row-header behaviour this design would have to prove before every task mechanic could rely on it; the mark needs no such proof. <br><br>**Rejected (c): judging every entry in the schema.** A test's fixture funding would be judged as the code under test `[measured 037064d:internal/store/post_test.go:57-77 · Read → fund posts a ManualCorrection …]`. <br><br>**The precondition is met by construction**: each test takes its own schema `[measured 037064d:internal/testdb/testdb.go:76-80 · Read → "Schema creates a uniquely named schema on the provisioned server" … func Schema(tb testing.TB) *pgxpool.Config]`. <br><br>**Gaps in identity values are harmless**, because the mark is the greatest *visible* id, not a sequence position. `journal_entry.id` is an identity column `[measured 97aa20f:internal/store/migrations/00001_ledger_core.sql:68 · grep -n -A 3 'CREATE TABLE journal_entry' → id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY]`. An identity column draws from a sequence (https://www.postgresql.org/docs/18/sql-createtable.html, read this turn: «It will have an implicit sequence attached to it and in newly-inserted rows the column will automatically have values from the sequence assigned to it.»), and a sequence has gaps by design (https://www.postgresql.org/docs/18/functions-sequence.html, read this turn: «transaction aborts or database crashes can result in gaps in the sequence of assigned values»). <br><br>**Later entries carry larger ids** within one schema with no concurrent writer `[derived → TestCheck_ignoresEntriesBeforeMark]`. |
| D7 | **Every document past the mark is also checked zero-sum per kind**, the same predicate the write path enforces, and a failure reports as an `unbalanced` mismatch (D11). | This is what makes `AnyBalanced` mean *balanced* rather than *anything* (spec Scope 6). For the other forms it is redundant and costs one pass over rows already read. |
| D8 | **The declared set is one slice literal in `internal/contract/declared.go`.** `Declared()` returns `NewRegistry(declarations...)`. <br>• One element per basis-document type. <br>• Every leg is spelled with catalog codes, a named sign and a named cardinality. <br>• No loop, helper or computed leg. <br>• Order: player operation, manual correction, then event types in the event-log migration's declaration order, then task types. <br>A signature change is therefore a changed line naming the account, kind, sign or cardinality that changed (AC12). | **Rejected: a YAML or JSON file.** It needs a loader and a parser this project owns, and its values are type-checked only at load, for a diff no more readable than a gofumpt'd literal. <br><br>**Rejected: a SQL table seeded by migration.** A signature is a test contract, not live data. A forward-only migration would turn every signature edit into an INSERT/DELETE delta rather than the signature itself, and would put a test-only fact into the production schema. |
| D9 | **Completeness.** <br>`ReadCatalog(ctx, q)` reads: <br>• the tables `journal_entry`'s foreign keys reference (`pg_constraint`, `contype = 'f'`); <br>• the `event_type_definition` codes; <br>• every `(scope definition code, account definition code, kind)`; <br>• every scope definition code. <br>`(Registry).Audit(cat Catalog, tasks []TaskType) error` fails with `ErrIncomplete`, listing every finding: <br>• a referenced table with no `Basis` member; <br>• `PlayerOperation()` or `ManualCorrection()` undeclared; <br>• an event type or a task type with no signature under its table; <br>• a declared event or task type that does not exist (stale); <br>• a posting leg naming a scope/account pair absent from the catalog, or whose kind disagrees with it; <br>• a movement leg naming an unknown scope code. <br>`cmd/bot` gains `taskDeclarations() []scheduler.Declaration`, and step 10 of the start-up assembly builds its registry from that list and nothing else: `scheduler.NewRegistry(taskDeclarations()...)`. `cmd/bot/signatures_test.go` audits `Declared()` against a migrated schema and those declarations. <br><br>**The step-10 link is checked.** `scheduler.Registry` gains `Declarations() []Declaration`: the declared set sorted by `Type`, each non-nil `Recurrence` a fresh copy, so a caller cannot mutate the registry through the result. `TestAssemble_HappyPath` compares the `(Type, Recurrence != nil)` pairs of the assembled registry's `Declarations()` with those of `taskDeclarations()`, and that comparison replaces its `DeepEqual` against an empty registry. | **Why `cmd/bot`.** Task types exist only as the composition root's declarations (task.go, measured above), and `cmd/bot`'s test binary is already database-backed `[measured 037064d:cmd/bot/assemble_test.go:29-31 · Read → os.Exit(leaktest.Main(m, testdb.Main))]`. <br><br>**Stale entries fail** so a signature ships with its type, never ahead of it (spec Out of scope, first row). A misspelled code would otherwise sit dead while the audit names the real type as missing. <br><br>**Rejected: a signature field on `scheduler.Declaration`.** It splits the declared set across two homes (events in one table, tasks beside each handler) and makes the check depend on the composition root to find a task's signature. <br><br>**Rejected: auditing the assembled process's registry.** That assembles the Telegram fake and the health server to answer a data question. <br><br>**Why the link needs its own check.** The audit sees only `taskDeclarations()`, so a declaration added at step 10 beside that list would run in the process and pass the audit. Today's assertion is `reflect.DeepEqual(a.taskRegistry, emptyRegistry)` `[measured 97aa20f:cmd/bot/assemble_test.go:126-131 · grep -n emptyRegistry → emptyRegistry, err := scheduler.NewRegistry() … reflect.DeepEqual(a.taskRegistry, emptyRegistry)]`, inside `TestAssemble_HappyPath` `[measured 97aa20f:cmd/bot/assemble_test.go:71 · awk, last func Test before line 130 → func TestAssemble_HappyPath(t *testing.T)]`. It holds only while the list is empty: `DeepEqual` never equates non-nil funcs `[measured go@1.26.5 · go doc reflect.DeepEqual → "Func values are deeply equal if both are nil; otherwise they are not deeply …"]`, and `NewRegistry` refuses a nil `Handler` `[measured 97aa20f:internal/scheduler/registry.go:52-54 · Read → if d.Handler == nil { return nil, fmt.Errorf("%w: type %q: nil handler", …) }]`. The assembled registry is the one step 10 hands the worker `[measured 97aa20f:cmd/bot/assemble.go:284-291 · Read → a.taskRegistry = taskRegistry … Registry: taskRegistry]`. <br><br>**Why an accessor.** `Registry` exposes its declarations only through an unexported lookup by type `[measured 97aa20f:internal/scheduler/registry.go:34-36,71-75 · Read → type Registry struct { decls map[Type]Declaration } … func (r *Registry) declaration(t Type) (Declaration, bool)]`. `Router.Kinds()` is the precedent for a sorted copy of what a composition-root component was built from `[measured 97aa20f:internal/ingest/router.go:118-123 · Read → "Kinds returns r's registered kinds, in a deterministic (sorted) order." … copy(out, r.kinds)]`. The pair compares both halves of the audit's task key (D2); handlers are not comparable and are not compared. <br><br>**Rejected: naming a replacement assertion for the first task-type pull request to write.** The link would then go unchecked until someone remembers the rule, which is the gap this closes. |
| D10 | **The declared set on the merged tree.** <br>• `PlayerOperation()` → `Nothing()` (spec Scope 10, AC13). <br>• `ManualCorrection()` → `AnyBalanced()`. <br>• Every event type in the event-log migration → `Nothing()`. <br>• No task-type entry, because none is declared. | No production code writes under any type (the grep in § Approach), so every type with no mechanic takes the explicit empty (spec Scope 5, AC11). The first mechanic replaces its own row in its own pull request. |
| D11 | **The matcher is an unexported pure function; `Check` is a thin read around it.** `conform(sig, doc)` returns sorted mismatches, and `Check` loads the documents, the postings and the movements past the mark with one query each. A mismatch carries a class and a key: <br>• `cardinality`: a declared leg's key, with the count wanted and the count found; <br>• `unexpected`: an actual row's key that no leg declares, with its count; <br>• `unbalanced`: a kind whose postings do not sum to zero (D7). <br>A row that differs from a declared leg in one key dimension (account definition, kind or sign) therefore reports two mismatches: `cardinality` on the declared key and `unexpected` on the actual key. The dimension is the one field in which those two keys differ, and the rendered `ErrNonconforming` message prints both keys whole. | Every AC2 dimension, kind-only included, is then testable without a database. A kind-only difference is unrepresentable in a real row, because `(scope_definition_id, code)` determines kind (00001:20-27, measured above). The database-error branches stay few, which is what the coverage ratchet needs. <br><br>**Classes make each check separately observable.** A test asserts which check fired, so a broken cardinality comparison or a skipped unexpected-row pass cannot hide behind an `unbalanced` entry the same document also produces. |
| D12 | **Totality without panics.** <br>Every switch over `Basis` and over the signature form names every member and returns an error from its default arm. `NewRegistry` and `Declared` return errors, and no `Must…` exists. | `exhaustive` runs with `default-signifies-exhaustive: true` `[measured 037064d:.golangci.yml:44-45 · Read → exhaustive: default-signifies-exhaustive: true]`, so the linter alone would accept a default arm hiding a missing member. The explicit cases are the design's choice. <br><br>The project holds zero production panics `[measured 037064d:ai-docs/panic-index.md:5 · Read → "The project targets zero production panics and currently holds it"]`. <br><br>`scheduler.NewRegistry` is the error-returning precedent `[measured 037064d:internal/scheduler/registry.go:38-69 · Read → every refusal wraps ErrInvalidDeclaration]`. |

**How a mechanic uses it**, which subtask 7 writes down for authors:
1. Replace its type's `Nothing()` row in `declared.go` with an `Expect(...)` row.
2. In its contract test, begin a transaction, set up fixtures, call `contract.NewMark`, run the mechanic, then call `Declared()` and `.Check(ctx, tx, mark, contract.Event(store.EventShopSale))`.
3. A new event type, or a new task type declared in `taskDeclarations()`, without a row fails `cmd/bot`'s audit. A task type is declared in that list and nowhere else, because it is the list the audit reads and the one step 10 builds from.

## Risks

- **A shared schema breaks `Check`'s precondition and can yield a false pass.** If another writer commits a document of type `want` between `NewMark` and `Check`, a mechanic that wrote nothing passes. Mitigation: the precondition is in `Check`'s doc comment, and every test takes its own schema (D6, measured). The failure mode is named so a mechanic's concurrency test does not reach for `Check` — `[derived → Check doc comment; TestCheck_noDocumentOfWantedType]`.
- **The completeness test is vacuously green today on the task-type axis**, because no task type is declared (D9, measured). Mitigation: `TestSignatures_coverEveryBasisDocumentType` carries red probes (a probe event type row, a probe one-shot and a probe recurrent declaration), each asserting the audit fails and names the probe — `[derived → TestSignatures_coverEveryBasisDocumentType/probe_*]`.
- **The task-type axis rests on step 10 building its registry from `taskDeclarations()` and nothing else.** A declaration added at step 10 outside that list would run in the process and pass the audit, and the current `DeepEqual` assertion stops being writable the moment the list is non-empty (D9, measured). Mitigation: `TestAssemble_HappyPath` compares the assembled registry's `(Type, Recurrence != nil)` pairs with `taskDeclarations()` through `scheduler.Registry.Declarations()`, a comparison that stays valid for a non-empty list; subtask 7 states the rule on the domain page. With today's empty list both sides are empty, so the discriminating run is the probe: step 10 given `append(taskDeclarations(), probe)` must turn the test red — `[derived → TestAssemble_HappyPath probe; TestRegistry_declarationsSortedCopies]`.
- **The comment-reference ban.** A comment in `internal/contract`, `internal/scheduler` or `cmd/bot` that names `store.Post`, a design section, an issue number or a markdown path fails `make comment-refs`: `[measured 037064d:ai-docs/doc-convention.md:55-58 · Read → "A comment says what the thing is, states its call contract, and carries what the linter requires. It names nothing outside itself that moves when this tree moves."]`. Mitigation: subtask 6 runs `make comment-refs`, and comments say "the write path" rather than a qualified symbol — `[derived → subtask 6 gate]`.
- **The coverage ratchet.** The new package adds database-error branches (query and scan failures) that ordinary tests do not reach. Mitigation: D11 keeps them in a few read functions, and a cancelled-context test drives each read's query-error branch, the precedent being `TestPost_cancelled_context_writes_nothing` `[measured 037064d:internal/store/post_test.go:337 · grep -n 'func Test' → func TestPost_cancelled_context_writes_nothing]` — `[derived → TestCheck_cancelledContext, TestReadCatalog_cancelledContext]`.
- **A new basis table lands without `contract` learning it.** A raid-session transition, day close or season close adds an arc column. By design `Audit` fails, naming the table, until a `Basis` member and its signatures exist, and `Check` fails that entry with `ErrNoSignature` — `[derived → TestReadCatalog_probeArcColumn, TestAudit_unknownBasisTable]`.
- **Catalog drift in declared legs.** A leg naming a scope/account pair renamed by a later migration would silently never match. Mitigation: `Audit` refuses a leg absent from the catalog or of the wrong kind — `[derived → TestAudit_legNotInCatalog, TestAudit_legKindDisagrees]`.
- **Data migration and idempotency:** none. The task adds no migration, writes no persisted enum, and `contract` issues no write outside a test's own fixtures — `[derived → subtask 6 verification: git diff --name-only shows no internal/store/migrations path]`.
- **Panic surface:** none added (D12) — `[derived → the panic-gate hook on write; subtask 6 lint]`.

**`registry_test.go`** — entry point `NewRegistry`.
- `TestNewRegistry_refuses` is a table asserting `errors.Is(err, ErrInvalidDeclaration)` and that the message names the offending type, for each of: <br>• a duplicate type; <br>• the zero `Signature`; <br>• `Expect()` with no legs; <br>• `AnyBalanced()` on `Event(shop_sale)`, on `PlayerOperation()` and on `DeferredTask("x")` (AC8); <br>• an event or task type with an empty code; <br>• `PlayerOperation`/`ManualCorrection` with a code; <br>• an unknown `Basis`; <br>• `Exactly(0)`, `AtLeast(0)`; <br>• an unset sign; <br>• duplicate posting-leg keys, and duplicate movement-leg keys.
- `TestNewRegistry_acceptsEveryForm`: `Nothing`, `AnyBalanced` on `ManualCorrection()`, and `Expect` with posting and movement legs.

**`conform_internal_test.go`** (package `contract`) — entry point `conform`.
- `TestConform_postingDimensions` (AC2) is a table over a `shop_sale`-shaped `Expect`. Each case changes exactly one dimension, and keeps the document summing to zero per kind wherever that change allows: <br>• account definition: the credit row `world/money` → `attributes/money`; <br>• kind alone: both rows keep their codes and take `KindExperience` — representable only here (D11); <br>• sign: both rows' signs reversed; <br>• cardinality: two debit rows against `Exactly(1)`, with amounts the credit balances; no debit row against `Exactly(1)`; one debit row against `AtLeast(2)`. <br>Each case asserts the exact mismatch list by class and key. For the account, kind and sign cases it is a `cardinality` entry on each changed declared key and an `unexpected` entry on each actual key, each pair differing only in the changed dimension, and no `unbalanced` entry. For the cardinality cases it is one `cardinality` entry on the debit key, plus an `unbalanced` money entry for the no-debit case alone, which cannot stay balanced. The unchanged document is the control and must return none.
- `TestConform_movementDimensions` (AC3): direction reversed, a second movement against `Exactly(1)`, and a movement between an undeclared scope pair each report; the exact document reports nothing.
- `TestConform_undeclaredRows` (AC4): an extra balanced posting pair of undeclared keys, and an extra movement key, each report `unexpected` on those keys.
- `TestConform_nothing` (AC6): one posting alone, and one movement alone, each report.
- `TestConform_anyBalanced` (AC8, AC9): any balanced set with any movements reports nothing; a set unbalanced in one kind reports `unbalanced` for that kind and nothing else (D7).
- `TestConform_property` (`rapid`): draw an `Expect` in which every kind has a positive and a negative leg, and a document satisfying it whose amounts sum to zero per kind. Then: <br>• any permutation of the rows conforms; <br>• removing a row that an `Exactly` leg counts yields a `cardinality` mismatch on that leg's key (an `unbalanced` entry may accompany it; the property asserts the `cardinality` entry); <br>• adding a pair of rows in one kind, one per sign, with keys the signature does not declare and amounts that cancel, yields an `unexpected` mismatch on each added key and no `unbalanced` entry. Synthetic codes are fine for the added keys, since `conform` does not read the catalog.
- **Mutants that must go red:** treating a key as matched when only the account matches (kind ignored); skipping the unexpected-row pass; skipping the cardinality comparison.
